## 0. 最终目标和不做事项

### 0.1 最终目标

1. DLL 扫描阶段以召回率优先，所有可能包含自然语言的 `ldstr` 条目均进入全域编辑器。
2. 宽松扫描之后运行纯代码静态数据流分析，为每条候选生成内部细分类，并映射为用户可见三态：
   - 需要翻译；
   - 不需要翻译；
   - 不确定。
3. 只把“不确定”条目送入云端判断缓存或 Policy Agent，避免让规则已经能够证明的条目继续消耗 Token。
4. 所有条目始终可搜索、可人工纠错；人工决定永远不会被重新扫描、云端或 Agent 自动覆盖。
5. 智能术语一致性作为独立可选子功能，默认关闭，可针对单个 Mod 开启，并支持多个系列 Mod 共享一个术语组。
6. 云端判断缓存的任何故障均自动降级，不中断翻译任务，但用一次非阻塞警告和诊断日志提醒用户及研发。

### 0.2 明确不做

- 不把第三方 DLL 改写后覆盖回 Mod 目录。
- 不把“驼峰命名”“首字母大写”等启发式规则当成扫描删除条件。
- 不让 UI 拦截、静态规则、Agent 和云端各自维护一套互相竞争的最终判断。
- 不把模型第一次生成的术语直接提升为全局永久术语。
- 不因为云端超时、断网、5xx 或返回格式错误而暂停、取消或回滚当前任务。
- 不在关闭智能术语一致性时执行术语 Agent 调用。

### 0.6 当前源码续作与验收边界

- 0.5 节记录的是 `0828` 测试包生成时的历史证据，不自动覆盖此后继续修改的源码。
- 2026-08-12 后续静态实现补充了翻译中断/异常时的增量断点：网络层已成功返回的普通、结构化和 DeepSeek 响应会完成解析，不再因随后到达的停止标志被直接丢弃；Keyed 在策略、术语和翻译批次边界保存；DefInjected 在每个 DefType 的 `finally` 中保存；DLL 硬编码 UI 在内置词典完成后及每个 LLM 批次完成后更新批准清单；未解决项人工重试与全域编辑器当前范围翻译会先接纳已成功返回的本批结果，再响应停止。术语 Agent 的有效决定和云端判断缓存成功响应也按同一原则写入本地状态。旧 UI 拦截器的分类队列、待组批翻译队列和活动批次现也纳入统一停止边界：停止后禁止重新入队、立即排空未发送项目、异常路径清除待处理标记，并在活动 UI 批次收口后才报告主流程完全停止。
- P0 请求链的后续静态审计又收口了并发名额授予与取消同时发生时的租约泄漏，以及主线程调度信号完成与停止同时发生时可能遗漏定向中止的竞态。429 恢复锁等待现直接响应停止；恢复成功后不再固定串行两分钟再突然恢复，而是按单并发、约二分之一、约四分之三和配置上限分阶段恢复。普通、结构化与 DeepSeek 的用户错误统一进入同根因聚合入口，底层只保留完整开发日志；主扫描使用自己的任务级聚合入口，避免首个失败重复弹窗。本地任务用量上限也与服务商余额/配额分开分类。
- 仅有全域编辑器、DLL 工作台或后台 UI 请求而主扫描未运行时，停止动作现在会启动带代次保护的独立排空监视；API 与旧 UI 活动批次归零后记录“翻译已完全停止”。若用户已重置取消并开始下一项任务，旧监视自动失效，不会把新任务误报为已停止；主扫描仍由原有 `finally` 自己完成排空和状态切换。
- 停止状态机的进一步静态复核修复了“主流程刚完成 API 排空、用户恰在切换空闲前点击停止”的收尾竞态：取消请求、取消代次与 `IsRunning` 现共用状态锁；主流程在锁内重新读取停止状态和所有活动计数，发现停止或旧 UI 批次尚未排空时继续等待，只有最终确认归零后才切换空闲并记录完成。跨线程读取的取消标志同时改为 `volatile`。该修正未经运行验证。

## 1. 单一裁决链

正式判断链收敛为：

```text
宽松扫描：只负责抽取
    ↓
静态数据流：能证明则给出自动判断
    ↓
静态结果仍为“不确定”
    ↓
精确命中的云端缓存：复用既有判断
    ↓
云端未命中或异常
    ↓
Policy Agent：只处理剩余不确定项
    ↓
用户可随时覆盖最终结果
```

角色边界：

| 组件 | 职责 | 是否独立裁决来源 |
|---|---|---:|
| 宽松扫描器 | 抽取候选及稳定身份 | 否 |
| 静态数据流分析器 | 证明 UI、非 UI 或无法确定 | 是，自动判断基线 |
| 云端判断缓存 | 复用相同指纹下已有的自动判断 | 否，属于缓存 |
| Policy Agent | 判断静态分析无法证明的条目 | 是，仅限不确定项 |
| UI 全局拦截 | 保留旧功能；可用于研发验证 | 否，不进入正式裁决链 |
| 内置词典 | 翻译已经确认需要翻译的文本 | 否 |
| 用户人工操作 | 覆盖最终生效状态和译文 | 是，最高优先级 |

有效状态按固定公式计算：

```text
effectiveDecision = userOverride ?? automaticDecision
```

静态分析、云端和 Agent 不直接争夺同一条目：静态分析能够证明时不查询云端、不调用 Agent；只有静态“不确定”才进入后续流程。

### 1.1 输入范围与判断步骤的 2×4 组合

DLL 开关只改变输入文件范围：

| DLL 模式 | 输入范围 |
|---|---|
| 关闭 | XML |
| 开启 | XML + 已启用且程序集已加载的 DLL |

云端判断缓存与 Agent 预判只改变“不确定”条目的后续判断步骤：

| 云端判断缓存 | Agent 预判 | 判断流程 |
|---|---|---|
| 关闭 | 关闭 | 静态固定规则；不确定项保持待判断 |
| 开启 | 关闭 | 静态固定规则 → 精确云端命中；未命中项保持待判断 |
| 关闭 | 开启 | 静态固定规则 → Agent 处理剩余不确定项 |
| 开启 | 开启 | 静态固定规则 → 精确云端命中 → Agent 处理剩余项 |

云端判断缓存必须能够独立于 Agent 开启。它不是现有云端共享译文，也不能继续作为 Agent Coordinator 的附属开关。

### 1.2 模型路由与命名

- “Policy Agent”“Agent 审核”在普通用户界面统一称为“Agent 预判”。
- Agent 预判只给出 `需要翻译 / 不需要翻译 / 不确定`，不生成译文，不具有高于用户人工决定的审核权。
- Agent 预判归属三级模型池中的标准分析任务，不再维护第二套供应商、地址、密钥和模型配置。
- 标准模型缺失时固定按 `标准 → 精细 → 批量` 路由；精细任务按 `精细 → 标准 → 批量`，批量基础任务只使用批量模型。
- 开关下方明确说明模型选择、可能产生的 Token 消耗，以及只有静态不确定项才会调用模型。

### 1.3 操作按钮与一键语义

智能补翻窗口固定提供：

```text
本地规则试跑
开始翻译
```

按功能开关条件显示：

```text
同步云端判断
Agent 预判
```

这些中间按钮用于预览、诊断和手动重跑，不应成为用户必须依次点击的门槛。点击“开始翻译”时，程序自动补跑所有已启用但尚未完成或已经失效的判断阶段，保留真正的一键体验。

- [x] 同一原文在不同方法中允许得到不同判断；回归夹具分别覆盖 UI 与日志汇点。
- [x] 无法证明的条目保持“不确定”，不能为了提高自动率强判。
- [x] 每条自动判断都保存原因码和证据路径，可在研发诊断中还原，不要求普通用户理解 IL。

## 4. 阶段 C：全域编辑器和人工覆盖

### 4.1 双层状态模型

每个条目同时保存：

```json
{
  "automaticDecision": "do_not_translate",
  "automaticReasonCode": "NON_UI_REFLECTION_KEY",
  "analyzerVersion": 1,
  "analysisInputFingerprint": "...",
  "userOverride": "translate",
  "effectiveDecision": "translate"
}
```

`effectiveDecision` 可以在运行时计算，也可以持久化后在加载时校验；不能只保存一个可被重扫覆盖的布尔值。

### 4.2 恢复与重分析

“恢复自动判断”：

```text
清除 userOverride
恢复最近一次仍有效的 automaticDecision
不在 UI 线程同步重新运行分析器
```

“重新分析此条目”：

```text
后台重新运行数据流分析
更新 automaticDecision、reasonCode 和指纹
不主动清除 userOverride
```

当程序集、IL 指纹或分析器版本变化时，旧自动判断标记为过期。若用户此时恢复自动判断而新结果尚未产生，条目暂时显示“不确定”，并进入后台分析队列。

### 4.3 列表要求

所有候选都留在列表中，包括“不需要翻译”。提供筛选：

```text
全部
需要翻译
不需要翻译
不确定
已人工覆盖
已翻译
未翻译
分析结果已过期
```

每条至少提供：

- 标记为需要翻译；
- 标记为不需要翻译；
- 交给 Agent 重新判断；
- 调用翻译模型；
- 手工填写译文；
- 恢复自动判断；
- 查看研发诊断详情。

用户对“不需要翻译”条目点击翻译或手填时，必须同时设置 `userOverride=translate`。重新扫描、云端和 Agent 均不得覆盖它。

### 4.4 编辑器验收

- [ ] 183 个当前基准候选均可在游戏内全域编辑器搜索。
- [x] 三态由单一 `effectiveDecision` 映射，静态回归同时验证 Translate、DoNotTranslate、Uncertain 及对应原因码。
- [x] 人工覆盖后重扫仍保留；程序集输入变化时保留覆盖并标记旧分析过期。
- [x] 恢复自动判断只清除覆盖，不改变自动判断结果。
- [x] DLL 条目手填非空且不同于原文的译文时，立即设置 `userOverride=translate` 并启用该条目。
- [x] 条目源程序集变化后显示过期，而不是继续套用旧补丁。运行时继续使用程序集哈希、MVID 与方法指纹拒绝旧项；全域编辑会统计当前扫描已无法匹配的旧清单项，明确提示“通常是 Mod/DLL 已更新、旧项已停止应用”，并允许通过“保存并应用”清理该 Mod 的失效项。

### 4.5 来源树、搜索与来源专属操作

选中 Mod 后，左侧改为简单来源树：

```text
全部
XML
  Keyed
  ThingDef
  AbilityDef
  ...
DLL
  按程序集或声明类型分组
```

- 点击“全部”显示 XML 与 DLL 的全部条目。
- 点击“XML”即显示全部 XML，不再在 XML 子级保留重复的“全部分类”。
- 点击“DLL”即显示全部 DLL；子级按程序集或声明类型继续缩小范围。
- 搜索始终限定在当前来源树节点内；“全部”节点才跨 XML 与 DLL 搜索。
- DLL 节点隐藏“导出原文 XML”“导入已编辑 XML”和仅适用于 XML 工作区的操作。
- XML 改动写入翻译 XML；DLL 改动写入带程序集与方法指纹的批准清单，不能混用持久化后端。

### 4.6 当前范围批量翻译

右侧增加“一键翻译当前范围（N）”。“当前范围”严格定义为当前来源节点、当前分类和当前搜索条件共同筛选出的全部结果，不是当前滚动视口里肉眼可见的行。

- 默认只翻译空白、未翻译或仍等于源文的条目。
- 已有人工译文默认跳过；覆盖必须二次确认。
- DLL 仅处理有效决定为“需要翻译”的条目；不需要翻译和不确定项不得自动进入批量请求。
- 批量请求沿用并发、预算、停止和断点机制，显示总数、已完成、失败和剩余数量。
- 返回结果只填入编辑器并标记未保存变更，不自动保存和应用。

### 4.7 编辑器滚动与响应式布局

- 正常可用尺寸下不使用最外层滚动条。
- 左侧来源/分类树和右侧条目列表分别维护自己的滚动区。
- 子框具有最小尺寸；只有窗口小于最小内容区时，才启用最外层滚动作为兼容回退。
- 窗口扩大时优先增加右侧编辑区和条目可视高度，不增加无意义留白。

## 5. 阶段 D：云端判断缓存的接入与降级

### 5.1 查询位置

只有静态结果为“不确定”的条目查询云端。精确身份继续遵守现有云端契约：

```text
packageId
gameVersion
sourceFingerprint
policyVersion
promptVersion
```

DLL 候选的 `sourceFingerprint` 和 Candidate ID 算法必须单独版本化；在协议确认前不得与现有 XML Candidate ID 混用。建议提升 `policyVersion`，必要时提升 `schemaVersion`。

### 5.2 故障降级

以下情况全部按“云端未命中”继续执行：

- 超时和取消；
- DNS、TLS、断网；
- HTTP 5xx；
- 401/403；
- JSON 解析失败；
- Schema 或候选身份校验失败；
- 接口版本不兼容。

行为：

```text
不中断任务
不弹阻塞对话框
不丢失中间数据
继续本地流程或 Agent
首次故障显示一次黄色小警告
后续同类故障只累计
详细信息写研发诊断日志
```

普通提示：

```text
⚠ 云端判断缓存暂时不可用，已跳过并继续本地分析，不影响当前任务。
```

恢复提示：

```text
✓ 云端判断缓存连接已恢复。
```

`404`、记录不存在、版本不匹配和 Candidate ID 未命中属于正常业务结果，不触发故障警告。

### 5.3 熔断和诊断

- 同一任务、同一接口只显示一次警告。
- 连续失败达到门槛后短时熔断，避免每个 Mod 重复等待超时。
- 冷却后只进行一次探测请求；成功则恢复。
- 诊断日志记录时间、接口、错误类别、HTTP 状态、请求 ID、受影响数量和降级动作。
- 绝不记录 API Key、管理员 Token、完整鉴权头和无必要的原文正文。

任务摘要增加：

```text
云端命中数量
正常未命中数量
因异常跳过数量
实际交给 Agent 数量
```

### 5.4 云端验收

- [x] 404 不向普通用户警告，继续本地规则或 Agent。
- [x] 超时只警告一次，任务继续。
- [x] 5xx、坏 JSON、错误 Schema 均归类并自动降级。
- [x] 连续三次故障后熔断 60 秒，期间不重复阻塞每个 Mod。
- [x] 云端恢复后只提示一次。
- [ ] 故障过程中任务断点和已完成结果全部保留。
  - 静态实现状态：Keyed、DefInjected、DLL 硬编码 UI 与未解决项人工重试均已增加增量保存边界；全域编辑器当前范围翻译也会保留本批已成功返回的结果。停止后不把未返回项伪记为 API 故障或整批未知故障。
  - 验收状态：未经运行验证；需由主人或朋友在真实云端超时、断网、5xx、停止与异常退出场景中确认文件、清单和用量账本均可续作后再勾选。

## 6. 阶段 E：确认需要翻译后的低成本路径

翻译顺序：

```text
用户手动译文
第三方人工汉化
Mod 原生翻译
已批准的本地/云端译文
内置 UI 词典
普通翻译模型
```

内置词典不能判断文本是否玩家可见，只能处理 `effectiveDecision=translate` 的条目。

词典键应考虑语义角色：

```text
button|Enabled -> 启用
state|Enabled  -> 已启用
button|Cancel  -> 取消
key|Enter      -> Enter
```

同一原文的译文可以在语义一致时去重，但“是否需要翻译”的判断必须按条目上下文保存，不能只用原文作为键。

## 7. 阶段 F：可选的智能术语一致性

### 7.1 产品开关

增加独立总开关：

```text
启用智能术语一致性分析
默认：关闭
```

开启总功能后，允许用户只给部分 Mod 勾选。例如 50 个 Mod 中只选择 9 个系列 Mod；未选中的 41 个 Mod：

- 不参加术语预扫描；
- 不贡献自动术语；
- 不调用术语 Agent；
- 不增加该子功能的时间与 Token 消耗；
- 仍可使用明确适用的官方或人工全局术语。

鼠标悬停风险提示：

> 启用后，程序会预扫描所选 Mod，并可能调用 Agent 分析术语及词形关系。这会增加处理时间和 API Token 消耗，且不能完全保证术语判断与最终翻译质量。分析结果将保存到共享术语库，请在重要翻译任务中人工检查。

### 7.2 术语共享组

用户可将选中的系列 Mod 加入命名组，例如“米莉拉系列”。这些 Mod 合并形成术语语料，可跨 Mod 交叉验证：

```text
Mod A: Milira Empire  -> 米莉拉帝国
Mod B: Milira weapon  -> 米莉拉武器
Mod C: Milira soldier -> 米莉拉士兵
```

术语库存储上全 Mod 共用，应用上必须带作用域：

```text
global    RimWorld 官方或明确的全局术语
mod_group 系列 Mod 共享术语
mod       单 Mod 专属术语
session   当前任务临时术语
```

同一个 `Empire` 可以在不同组拥有不同译法，不能因为物理上共用一份数据库而无条件跨世界观覆盖。

### 7.3 术语来源

按以下步骤自动产生，不能要求全部人工录入：

1. 通过相同 Key、Def 路径对齐游戏官方中英文。
2. 对齐 Mod 原生或第三方人工翻译中的完整短语。
3. 从选中 Mod 的全部待翻译文本机械提取高频词、TitleCase 词组、Def label 和重复 N-gram。
4. 使用可信锚点对齐和多个句对差分，生成双语术语候选。
5. 只把高价值、机械方法无法确定的候选交给术语 Agent。
6. 从结构化翻译结果中收集本批实际采用的术语，先写入任务级临时缓存。
7. 用户人工确认后提升为 Mod、系列或全局术语。

### 7.4 机械候选抽取

实现模块：

```text
TerminologyCorpusBuilder
TerminologyCandidateExtractor
TerminologyMorphology
AlignedTranslationMiner
BilingualConstraintSolver
TerminologyValidator
TerminologyCache
TerminologyPromptContextBuilder
```

候选提取至少支持：

- 去除占位符、富文本、URL、数字和明显代码噪声；
- 英文 1～4 gram；
- 连续 TitleCase 专名；
- 单复数和所有格基础归一；
- DefType、字段和 Key 上下文加权；
- 当前 Mod/组内频率；
- 跨全体语料的常见度惩罚；
- 每个候选保留少量代表上下文。

`Empire` 与 `Imperial` 这类派生关系不能只靠简单词干规则强行合并；需要已有词典证据或术语 Agent。

### 7.5 多句对交叉验证子项

多句对双语差分作为智能术语一致性内部子项，跟随总开关，默认不会运行。

算法：

1. 只使用官方、人工确认或已高置信度验证的术语作为锚点。
2. 在源句和目标句中寻找唯一、不重叠的锚点。
3. 删除锚点后，两边必须各只剩一个连续有效片段。
4. 汇总不同句对、不同锚点产生的相同候选映射。
5. 至少两个独立句对支持，且无明显冲突，才提升为任务级术语。
6. 达到更高证据门槛后才允许成为 Mod/组级自动术语。
7. 语序变化、意译、多个剩余片段、占位符不一致或冲突译法全部保持候选，交给 Agent/人工。

建议状态：

```text
candidate
session_active
mod_persistent
group_persistent
user_approved
rejected
```

模型第一次提出的术语最多进入 `session_active`，不能自动写成全局永久术语。

### 7.6 术语 Agent 和批次上下文

术语 Agent 只接收：

- 当前启用 Mod/术语组；
- 排名靠前且本地未解决的候选；
- 每个候选有限数量的上下文；
- 已有高优先级术语和冲突说明。

普通翻译批次只注入本批文本实际涉及的术语及词形，禁止发送整个术语库。

结构化输出建议包含：

```json
{
  "translations": [],
  "termApplications": [
    {
      "termId": "...",
      "sourceForm": "Imperial",
      "semanticRole": "adjective",
      "target": "帝国的"
    }
  ]
}
```

机械验证：

- 源词确实出现在原文；
- 目标词确实出现在译文；
- 占位符保持；
- 没有覆盖更高优先级术语；
- `termId` 必须来自本次请求；
- 同批次无无理由冲突。

### 7.7 术语优先级和冲突

沿用既定来源优先级：

```text
用户手动确认
> 第三方人工汉化
> Mod 原生翻译
> 云端已有术语
> 当前 Mod/组自动术语
> 当前任务临时术语
```

再叠加作用域约束。人工 Mod 专属译法不能被组级或全局自动术语覆盖。

发现冲突时：

- 不静默覆盖；
- 当前批次使用最高优先级且作用域最具体的有效项；
- 将冲突写入术语审核列表；
- 用户可以合并、限定作用域、拒绝或指定首选译法。

### 7.8 术语验收

- [x] 总开关默认关闭；所有语料观察、候选、术语 Agent 和批次注入入口在关闭或未选 Mod 时直接返回。
- [x] 50 个 Mod 只选 9 个时，仅 9 个参加候选抽取和 Agent 分析；逐 Mod 设置判断已收敛到统一选择边界，机械回归构造 50 个 Mod、选择其中 9 个，验证关闭总开关时 0 个进入，开启时候选语料和送往 Agent 的候选来源均严格只包含这 9 个。
- [x] 同一术语组内可跨 Mod 交叉验证和复用。
- [x] 不同术语组的同名词允许不同译法。
- [x] `Milira Empire/weapon/soldier` 在可信锚点充分时可机械推出一致候选。
- [x] `Empire/Imperial` 无充分证据时不得被简单词干规则错误合并。
- [x] 每批只注入实际出现在本批原文中的相关术语，条目数和提示字符数均有上限。
- [x] 任务中止后候选、术语和已完成批次可按会话与源指纹继续；源已变化时拒绝套用旧任务。
- [x] 开关提示明确说明会增加处理时间和 Token 消耗，且不能完全保证术语判断和最终译文质量。

## 8. 智能补翻、试跑结果与主控制台

### 8.1 Mod 选择与官方内容

### 8.2 试跑窗口与每 Mod 详情

### 8.3 主控制台响应式布局

主控制台以 1366×768、100% RimWorld UI 缩放为最低完整布局基准：

- 第一行放更新日志、删除翻译、教程和导出警告等管理按钮。
- 第二行放智能补翻、跳过当前、停止和热重载等任务操作；根据运行状态隐藏不适用项。
- 普通按钮高度压缩为约 28～32 像素，减少不必要行距。
- “当前任务 / 本次翻译 / 累计翻译”合并成一行；长任务名省略显示并提供悬停全文。
- 主进度与子任务进度保留两层，因为它们表达不同层级。
- 两个日志框设置约 260～300 像素的最小高度，并优先占用窗口新增高度。
- 大屏窗口动态扩大但设置最大宽高，避免超宽屏内容过度摊开。

## 9. API 请求队列、停止语义与可诊断错误

### 9.1 请求生命周期和排队

正式生命周期统一为：

```text
Created → Queued → Dispatching → Sent → WaitingResponse → Completed/Failed/Cancelled
```

- 请求在 `Queued` 阶段等待并发名额，排队时间不计入 API 响应超时。
- 删除“进入主线程调度后 5 秒未创建 UnityWebRequest 即失败”的普通请求逻辑。
- 网络请求真正进入 `Sent` 后才启动响应超时计时器。
- 前一请求无论成功或失败都必须释放并发名额，后续请求继续；失败不能传播给队列中的其他请求。
- 排队异常应归类为本地调度器诊断，而不是 API 异常；调度器健康检查可恢复、可取消，但不能对每个排队条目连续报错。
- 队列设置容量、背压和任务级取消，避免无限积压；正常等待本身不是错误。

### 9.2 停止按钮与真实活动状态

停止按钮的显示条件为：

```text
pipelineRunning || queuedRequestCount > 0 || activeRequestCount > 0 || retryWaitCount > 0
```

停止动作必须：

1. 禁止产生新扫描批次和翻译批次；
2. 从队列移除尚未发送的请求；
3. 中止已经启动的 UnityWebRequest；
4. 取消 429 降级重试、Agent 请求和其他延迟等待；
5. 等待所有请求状态进入完成或取消；
6. 请求归零后才将界面切换为已停止。

停止期间显示：

```text
正在停止……活动请求 N，排队请求 M，重试等待 R
```

主扫描、Agent 预判、工作台单条/批量翻译和后台翻译都必须注册到同一个活动请求状态源，不能再只依赖 `IsRunning`。

### 9.3 错误分类和用户可读日志

错误至少分为：

| 类别 | 确切含义 | 响应处理 |
|---|---|---|
| 本地排队 | 正常等待并发名额 | 不报错，只显示状态 |
| 本地调度异常 | 请求尚未创建或调度器失效 | 明确写“请求未发出”，不提示余额问题 |
| 响应超时 | 请求已经发出，但截止时间前没有完整响应 | `Response=无`，记录超时秒数 |
| HTTP 错误 | 已取得非成功 HTTP 状态 | 记录状态码和经过清理的响应摘要 |
| 超并发 | 明确 HTTP 429 且不是余额耗尽 | 进入并发恢复流程 |
| 配额/余额不足 | 服务商明确返回配额或账单错误 | 明确提示充值、配额或密钥所属项目 |
| 返回格式错误 | 已收到响应，但 JSON、Schema、ID 或条数不符合协议 | 显示解析原因和响应摘要 |
| 用户取消 | 用户主动停止或任务取消 | 不作为 API 异常告警 |

每条失败诊断至少记录：

```text
packageId / Mod / 分类 / requestScope
输入条目数
源字符数
预计输入 Token
请求阶段
供应商和模型
HTTP 状态
超时值
尝试次数
响应摘要或“无响应”
```

超时前无法获得服务商的准确 Token 用量，必须标为“预计输入 Token”。普通控制台只显示受限长度且去除敏感信息的摘要；更完整响应写入开发日志或诊断文件。不得记录 API Key、Authorization Header 或其他凭据。

同一任务、同一根因的错误进行聚合去重：首次显示用户提示，后续累计受影响批次数和条目数；逐批细节保留在异常报告。

### 9.4 HTTP 429 并发恢复

- 只有明确的 429 并排除配额不足后，才进入超并发恢复。
- 首次 429 后降低有效并发，必要时串行发送后续探测请求。
- 最多执行三次递增等待重试；等待必须响应用户停止。
- 三次仍然返回超并发时，明确提示“服务商并发限制仍未解除”，附重试次数、等待时间和受影响批次。
- 恢复成功后只提示一次，并在冷却期内逐步恢复并发，不能立即回到导致 429 的峰值。

### 9.5 API 与停止验收

- [x] 正常并发排队和等待 Unity 主线程发送均可超过 5 秒而不失败；响应超时只从 `SendWebRequest` 启动后计时。
- [x] 连接测试和模型列表获取不再使用发送前外层超时；连接测试不会调用全局中止去误伤无关活动请求，模型获取可由显式重置取消。
- [x] 云端判断缓存也区分发送前排队与发送后响应超时；停止发生在调度前时不会晚发，发送后停止会中止该云端请求且不记录伪故障警告。
- [x] 前一请求失败后释放并发名额，下一请求独立获得名额并继续发送。
- [x] 未发出的请求固定归类为本地启动失败或用户取消，不显示 HTTP、返回格式或余额错误；用量预留同时释放。
- [x] 响应超时显示条目数、源字符数、预计输入 Token、超时秒数和“无响应”，不伪造响应内容。
- [x] HTTP 200 的格式错误归类为 `InvalidResponse/ResponseParsing`，显示具体解析原因和最多 320 字符的返回摘要；完整返回写开发日志。
- [x] 主线程创建请求异常固定标记为 `LocalDispatch/Dispatching`；结构化与 DeepSeek 解析/术语验证失败继承条目数、源字符数、预计输入 Token 和超时值；缺少任务级模型单独标记为配置错误，不再伪装成网络故障。

  - 后续静态实现：恢复探测锁等待每 100 毫秒检查停止；首次成功后进入三个 20 秒冷却阶段，有效并发依次为 1、约 1/2、约 3/4，随后恢复用户配置上限。
- [x] 主流程、活动请求、调度等待、并发排队或重试等待任一存在时均显示停止按钮。
- [ ] 点击停止后队列、活动请求和重试等待全部归零。
  - 静态实现状态：停止按钮的工作判断现包含旧 UI 拦截器尚未进入 API 生命周期的分类/翻译队列和活动批次；发出停止请求会同步禁止新入队、排空未发送 UI 项目、终止活动 API 请求，并让主流程排空屏障继续等待活动 UI 批次退出。该项仍需主人或朋友实际点击并观察计数归零后方可勾选。
  - 非主扫描调用也有独立停止完成监视，不再依赖主扫描 `finally` 才能记录完全停止；监视不修改主扫描运行状态，并受取消代次约束。
- [x] 同一根因按失败类型、供应商、模型、HTTP 与阶段聚合，不为每个 Def 分类重复弹窗。
  - 后续静态实现：供应商适配层不再额外弹出一轮简化 HTTP/解析错误；普通调用统一聚合，主扫描显式关闭底层用户报告后继续按任务范围聚合。结构化供应商和 DeepSeek 异常也纳入同一故障记录边界。
