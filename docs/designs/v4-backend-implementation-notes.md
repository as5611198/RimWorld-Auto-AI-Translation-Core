# V4 后台重构实施记录

本文只记录实施过程中发现的问题、已作出的后台处理和需要留给后续 UI/接线阶段的事项。业务基准仍以《五步独立翻译工作流与数据架构》为准；本记录不得反向修改已确认的产品规则。

## 2026-10-08：静态审阅后的五项修复

原生译文落盘与刷新、预览窗口人工保存、XML/DLL 目标语种缓存、原文更新后的原生译文接纳、延迟 Tooltip 来源定位已修改。数据库迁移 19 记录分析语种，旧分析需要重算，保存的译文不删除。用户确认扫描失败可以继续 AI，一键流程保留原行为。详见[修复状态和人工验收场景](../reports/current-changes-static-review-2026-10-08.md)。此次仅静态审阅，未编译或运行验证。

## 2026-10-07：RJW 文件规则与数据库参考字典

- 用户特许运行文件扫描器；直接使用当前扫描器和分类器读取两个 RJW ZIP 的源码文件。Fluid Empire 确认漏掉两条 `stuffAdjective`，补入共享字段规则后候选 129→131；Milk Variations 346 条保持不变。未启动游戏，也未运行其他测试。
- XML 分析器升级到 `xml-5`。第 18 版数据库迁移新增 `ReferenceDictionaryEntries`，提供按语种与可选 Mod 范围的查询及用户维护接口；初始化补入 65 条来源明确的原版/官方 DLC 简体中文词条，修改及停用不被覆盖。
- 设置页新增参考字典窗口，支持新增、复制、编辑、义项语境、词性、例句、Mod 范围和停用。AI 翻译正常批次、试跑提示与单条补试共用参考提示构造；读取运行快照，仅匹配本批相关词条，并保持同形异义词整组。
- 修改字典不清除译文、不清除用户分类、不触发翻译。旧自动术语提取/学习模块没有接入此功能。数据库迁移、窗口及提示生成只做静态审阅，未经运行验证。

## 2026-10-06：Mod 名录与原生译文缓存

- 数据库新增第 17 版迁移：Mod 安装存在状态、按 Mod/语种保存的扫描结果与译文条目。名录同步使用事务，保留现有分析指纹及用户成果；同身份多个安装目录保留在安装表。
- 首次打开页面增加独立同步弹窗，等待已有后台任务结束，显示动态准备状态、读取/写入进度和估计剩余时间；成功显示汇总，失败允许重试。同步结束前不允许关闭弹窗，避免后台修改仍在进行却没有入口状态。
- XML/DLL 分析入口接入全体实际加载 Mod 的当前语种译文收集，记录成功扫描指纹、条数与错误。缓存以文件元数据指纹为准，不是逐字节内容哈希；只修改内容且人为保留文件大小和修改时间时不能自动识别。
- XML 已有译文检测接入缓存，未重新分析的 XML 候选也刷新译文对应关系；DLL 独立入口在结束时刷新已有 XML 候选。来源记录沿用现有译文表及 AI 跳过条件，不让生成包伪装成第三方来源。
- 本轮仅静态阅读和代码审阅，未编译、未运行测试、未启动游戏。动态效果、主线程调度、数据库迁移和真实 Mod 补漏行为均待人工验收。

## 2026-08-17：第一阶段后台实现

### 已处理

1. 新后台任务协调器与旧 `AutoTranslatorSettings.IsRunning` 建立单向兼容桥：旧界面可以识别新后台忙碌状态；新后台不依赖旧界面的按钮布局或旧流程顺序。
2. DLL 新分析器不能复用旧扫描入口的默认行为。旧入口会读写旧 JSON 裁决并把用户覆盖结果合入自动结果，违反“DLL 本地分析层、AI 复核层、手动层分别保存”的规则。因此为扫描器增加无旧持久化模式，新后台只读取自动分析结论，不读取旧用户覆盖，也不写旧裁决文件；原入口保持原行为。
3. XML 和 DLL 分析各自拥有独立版本号和指纹生成方法。分析按钮服务只负责按 XML → DLL 顺序调用两个“按 Mod 串行”的独立步骤；是否强制分析由两个分析器分别处理。

### UI/接线实施状态

1. 主工作台的分析、试跑、AI 复核、AI 翻译、一键翻译和停止按钮已改接 `WorkflowBackend` 的独立入口；六个按钮固定使用同一行等宽布局。旧主页面及其专属的 Mod 选择、删除翻译、过滤列表和 Policy 预检窗口已移除；其中仍被现行流程使用的共享扫描判断继续保留，不再携带窗口实现。
2. 主工作台统一读取 `WorkflowTaskCoordinator` 的任务名称、完成量、总量、当前 Mod 和阶段说明；任务运行时其他执行按钮禁用，详情／日志仍可只读打开。
3. 停止按钮直接请求新协调器取消；旧管线运行时同时桥接旧取消链。新旧入口继续共用 `AutoTranslatorSettings.IsRunning` 的全局忙碌语义。
4. XML/DLL 组合分析改为串行调度：先完整执行 XML，再在开关开启时执行 DLL；两步各自在内部按 Mod 串行。任务区主进度按串行阶段连续推进，子进度只显示当前 Mod 的当前分析器，因此阶段文字和进度不会在两个通道间切换。串行是按钮编排策略，不改变两个分析步骤各自判断范围、版本、指纹和保存结果的独立性。
5. 新 SQLite 运行需要发布包携带共同的 `System.Data.SQLite.dll` 和四个平台原生文件及 `.sha256` 清单。当前只实现加载、复制、校验和错误边界；依赖提取与发布打包要在准备交付产物时完成，不能把 NuGet 缓存目录当发布内容。
6. 云端翻译标签页本轮作为现有可用初版保留。下载成功后的旧收尾仍未改接新数据库同步；数据库需等启动同步或用户在主工作台点击“刷新状态”后看到刚下载的云译文，后续改云页时必须收口。
7. 主工作台的 DLL 分析开关和 AI 复核范围已通过 `WorkflowBackend.GetConfiguration/SaveConfiguration` 读写 Schema v3 设置；待判定保持必选，需要翻译／无需翻译分别可切换。旧设置页中的同名历史功能尚未全部迁移，应避免形成第二个设置真源。
8. 主工作台 Mod 数据源已与旧 `ValidMods` 重扫描缓存解耦。`PlayDataLoader` 完成后在主线程只读取 RimWorld 当前 Mod 元数据，形成名称、Package ID、`mod_identity`、Root、Active、安装实例数和受保护标记的轻量快照；后台只读取该不可变字符串／布尔快照。首次列表显示不再递归读取 Defs、Languages、XML、DLL 或强制候选路径，重型可翻译源判断延迟到具体分析步骤或旧功能自己的渐进缓存。
9. 工作台汇总读取不再调用 `GetCandidates` 和实体化 `CandidateRecord`。SQLite 直接按 `mod_identity × source_domain` 聚合当前存在候选，SQL 内按“手动 > 当前 AI > 当前 DLL > 当前 XML > 待判定回退”解析有效分类，并把原文哈希与 `source_text_hash_at_translation` 不匹配的旧译文计为未翻译。数据库只返回每个 Mod 每个来源域的计数行，再与当前轻量 Mod 快照做左连接；历史中已卸载 Mod 不进入列表。读取复杂度由候选实体数降为当前 Mod 汇总行数，Ancient urban ruins 的 696,819 个 XML 候选不会再因打开主工作台创建同等数量的 `CandidateRecord`。
10. 主工作台默认范围为“已启用”。列表按实际内容区高度和 39px 行高计算可见行数，以 3 倍可见行数作为预取窗口，只绘制实际可见行；列表／任务区高度变化时沿用筛选、排序、选择集合与滚动位置并把 scrollY 限制在新合法范围。工具栏现拆成两排：第一排为“搜索｜Mod 范围｜分析状态｜刷新状态｜管理”，第二排为“已选统计｜全选筛选结果｜反选筛选结果｜清空选择”。全选／反选只影响当前筛选结果，筛选外选择保留；统计同时显示总选择数和筛选外数量。
11. 选择集合统一以稳定 `mod_identity` 保存，Package ID 只用于显示和搜索。相同逻辑身份的多个安装实例保留实例计数，并优先绑定当前启用实例；无 Package ID 的本地 Mod 继续使用既定 `local:` 回退身份。编辑页从主工作台跳转和后台读取也传递 `mod_identity`，不再按 Package ID 回查首个安装项。
12. 固定不可翻译系统包只有一个代码入口 `AutoTranslatorScanner.IsNonTranslatableSystemPackage`，顺序为本体、Royalty、Ideology、Biotech、Anomaly、Odyssey、ATC 本体、`AITranslation.Pack`。范围判断与普通 Mod 一致：“已启用”显示游戏实际启用的保护 Mod，“全部”显示 RimWorld 实际识别到的本地安装项，不根据固定清单虚构未安装 DLC。保护项始终在普通排序结果后按固定顺序显示灰叉只读保护区，状态明确为“系统／官方内容，不作为翻译目标”；只有“分析状态：全部”允许显示保护项，任何具体状态筛选都隐藏它们。UI 全选／反选、编辑入口、选择解析和所有公开工作流后端入口均忽略它们；旧数据库记录暂不删除。`IsOfficialBaseGameOrDlcPackage` 只保留官方子集语义，OfficialLanguageTar、Memory Injection 等只读参考路径不受影响。
13. 主列表选择输入改为单一自绘状态机：只在勾选热区 `MouseDown` 启动并立即逐行 toggle，`MouseDrag` 每次首次划过一个 `mod_identity` 时按进入时状态再 toggle 一次，`MouseUp` 只清理 visited 集合。受保护行、不可见行和 busy 行不进入状态机。有效手势越过列表上下边缘且仍位于勾选列水平容差内时自动滚动；越界 4px 后启动，按平方 ease-in 从 35px/s 增至最多 420px/s，以 `Time.unscaledDeltaTime` 归一化并 clamp 到合法 scrollY。滚动带入边缘的新行仍共用本次 visited 集合。MouseUp、失焦、切换标签、重新打开后未按键及任务进入 busy 均结束手势。
14. 日志级别为 Debug 时分别记录 `lightweight-mod-snapshot`、`database-summary`、`ui-apply` 三阶段耗时；默认 Info 运行日志不输出这些性能行。
15. 现行消息与确认入口统一改用 ATC 弹窗组件，现行自定义窗口中的原生棕金按钮和自动生成关闭按钮改用 `WorkflowUiStyle`；普通确认使用主操作色，危险确认使用红色，取消／关闭使用中性色。译文编辑分页移到条目列表底部并显示总页数、首尾页、前后页和相邻页码；手动分类状态与下拉入口合并为一个带箭头的控件。设置页每个 API 配置改为独立卡片，启用勾叉、删除图标和备注位于同一顶栏，连接测试固定在卡片底部。

### 实施中纠正的结构偏差

1. 第一轮落表时曾把当前译文状态临时放入 `Candidates`。静态对照已确认这会错误地让多个目标语言共享一份译文，已经在本轮代码中纠正：`Candidates` 只保存条目身份和四层分类；译文改由 `TranslationResults(candidate_id, target_language)` 独立保存。该临时结构未运行、未建库、未发布。
2. 分析输入不仅包含待翻译源语言目录，还必须单独读取目标语言目录，用于识别 Mod 原生或第三方已有译文。目标译文不会写回第三方 Mod，只作为 `TranslationResults` 的只读来源；已有有效译文不进入 AI 翻译和试跑翻译耗量。
3. 生成包文件与数据库不能假装处于同一事务。现在所有 AI 翻译/手动写入和删除均先登记 `PendingFileOperations`，原子修改 XML/清单后再提交数据库状态；启动同步会按文件实际内容处理未完成操作。
4. 云翻译下载仍沿用现有文件和 provenance 机制。同步器读取有效 provenance，把云下载识别为 `Cloud`，而不是误判为手动修改；数据库丢失且旧文件没有可信 provenance 时，按已确认规则建立为 `AiTranslation` 基线。
5. 译文覆盖优先级在存储层固定为：手动 > 第三方人工翻译 > Mod 原生翻译 > 云翻译 > AI 翻译。较低来源不得覆盖数据库中仍有效的较高来源。
6. 新 AI 复核依赖结构化 JSON 输出，通用工作流模型路由会排除 DeepL。DeepL 仍保留给旧的纯文本机器翻译路径；如果用户只配置 DeepL，新 AI 复核/新结构化 AI 翻译入口会明确报告没有可用的结构化模型配置，不能伪造复核结果。后续 UI 需要在模型配置和按钮提示中说明这一点。
7. 静态复核发现首版 `modIdentity` 错把 Workshop ID 或安装目录混入了有合法 Package ID 的身份。现已纠正为 `pkg:<规范化 Package ID>`；同一批分析目标若有两个不同根目录解析成相同身份，后台直接拒绝并报告冲突，禁止后写入者静默覆盖先写入者。
8. 首版启动同步会重复解析生成包内全部 XML，和大数据量目标不符。Schema v2 增加 `TranslationFileCache`，Schema v7 又增加文件长度与最后写入时间：长度和 UTC 修改时间均未变化时直接复用已解析条目，不再读取文件全文；元数据变化时才读取字节并计算真实 SHA-256，内容哈希仍相同则复用解析结果，哈希变化才重新解析。缓存只在一次文件索引完整建立后整体替换，读取失败的文件保留上次缓存并标记 `ReadError`。该快速路径以正常文件系统／编辑器会更新修改时间为前提；若外部工具刻意在保持长度的同时恢复旧时间戳，本轮可能到下一次真实元数据变化才发现，实施选择接受这一极端边界以避免每次启动线性读取全部译文文件。
9. 同步器为了贯彻来源优先级，可能把第三方／Mod 原生译文镜像进生成包。该路径最初直接执行“写文件后改数据库”，没有进入崩溃恢复日志；现已与 AI/手动写入统一，先登记 `PendingFileOperations`，原子写文件，再完成数据库记录。
10. 手动编辑最初在“提交译文”和“写手动分类层”之间存在极小的崩溃窗口。现将两项数据库变更合并进同一个待处理写入完成事务；启动恢复手动写入时也会同时补齐手动分类。AI 翻译被用户停止时，尚未完成的条目恢复为“未翻译”，不误记为“失败”；真实调用或输出错误才记为“失败”。
11. 分析编排静态复核时发现：单个 Mod 的致命异常会终止同一分析器后续 Mod，且 `forceAnalysis` 只绕过缓存。最终采用强制分析的原子替换语义：强制参数使该分析器无条件重算，但不在计算前删除旧结果；新结果完整生成后，由 `SaveAnalysisResult` 在单个 Mod 的短事务内切换当前条目和分析运行记录。分析失败或取消时保留上一次完整结果，同时单独落 `AnalysisRuns=Failed`，并继续同一步骤后续 Mod；步骤结束后汇总抛错。组合入口采用 XML → DLL 串行调度，因此 XML 步骤整体失败时本次不再启动 DLL，但历史 DLL 结果不受影响。该取舍实现了用户要求的“删除旧结果并重新分析”的最终状态，又避免中途失败把可恢复旧数据先行清空。
12. 实施中一度为了报告分栏，把“需要翻译”和“待确定 50%”拆成两次 AI 翻译模拟调用；这会改变真实任务的提示词拼接与批次开销，违反“试跑直接调用正式步骤”的规则，已立即撤回。最终试跑对整批选中 Mod 只调用一轮 AI 复核模拟和一轮 AI 翻译模拟：AI 翻译把全部有效“需要翻译”与每个 Mod 的“待确定”中按稳定顺序取前 `ceil(50%)` 合并进自己的队列，剩余 50% 放弃。两个步骤内部再按 Mod、来源文件和上下文上限拆批，并把各批 Token 归集回对应 Mod 报告；它们互不把对方的模拟结果当输入。
13. 直接用 `IN (@mod0, ... @mod999)` 查询会在大批 Mod 上触碰 SQLite 参数上限。候选批量查询和 Package ID 到 Mod 身份解析现改为连接级临时选择表，再用 JOIN 查询；因此选择 500～1000 个 Mod 不依赖驱动的变量数量上限。临时表名和列名只从仓储私有常量传入，在唯一 SQL 拼接边界按 ASCII 标识符语法校验（首字符为字母或下划线，其余为字母、数字或下划线）；不再维护固定名称白名单，实际数据值继续参数化。保护目标检查的临时表只保存 `mod_identity`，查询只连接 `Mods` 并读取身份与 Package ID，不接触 `Candidates`。
14. 启动同步最初跳过了翻译状态为“失败”的条目，这会漏掉玩家在失败后直接写入生成文件的手动译文。现只跳过仍处于“翻译中”的瞬时状态；“失败”条目若出现与当前原文匹配的有效文件值，仍按 provenance／文件基线识别来源，玩家改动可提升为手动来源。
15. 步骤契约进一步收口为“外部只给选择范围和本次临时选项”。Schema v3 增加 `WorkflowSettings`，持久保存 DLL 分析开关、AI 复核范围和试跑待确定比例；分析入口仍以当前 `ModMetaData` 建立文件快照。试跑按钮在主线程冻结并解析稳定 `mod_identity` 列表，之后试跑编排器和两个 AI 子能力之间只传身份列表、`isSimulation` 与本次选项，不传候选、目标语言或数据库筛选结果。
16. （历史实现，已由第 107 项取代）DLL 分析与旧 UI 即时翻译曾保持互斥；保留此项仅解释既有后台保护来源，不再定义当前采集探针的最终产品语义。
17. AI 复核和 AI 翻译不能把“选中 Mod 没有任何本地分析结果”静默解释成正常的零条任务。早期实现选择了整批拒绝，但与最终第 12 节“未分析 Mod 仍可选中、逐 Mod 处理 0 条并说明原因”冲突，现按更新后的基准纠正：两个步骤内部用临时选择表批量检查 XML 或 DLL 任一分析完成记录，只跳过缺失 Mod，并在 `SkippedMods` 记录“未完成本地分析，无可用条目”；同批已分析 Mod 继续执行。两类分析保持独立，不强制 DLL-only 结果依赖 XML。试跑仍生成 `MissingLocalAnalysis` 逐 Mod 报告。
18. 试跑逐 Mod 报告不再由编排器查询候选或在内存按 Mod 分组。编排器仅各调用一次 AI 复核和 AI 翻译的模拟入口；资格检查、SQL 过滤、逐 Mod 游标分页、批次规划、提示词和 Token 估算均属于两个子能力，子能力返回的逐 Mod 汇总直接切分为报告。
19. 稳定条目 ID 静态对照发现首版哈希材料误用短前缀 `atc1` 作为规范版本，并用换行连接字段。现已在任何数据库建立和发布前纠正：输出仍为 `atc1_<完整 SHA-256>`，哈希内版本固定为 `atc-candidate-v1`，各字段经过 NFC/大小写规范化后按“字段名长度、字段名、UTF-8 值字节长度、值”序列化，杜绝字段内换行或分隔符造成歧义；原文、译文、绝对路径和 Mod 版本仍明确排除。
20. 静态收口步骤入口时发现：启动器仍在解析目标语言、构造 `ModAnalysisTarget`，AI 公共入口还要求 UI 先把 Package ID 查成数据库身份。这会让启动器重新获得任务范围裁定权。现已下沉：分析服务自行读取目标语言并构造目标；AI／试跑／同步／手动译文步骤自行读取目标语言；公开 AI／试跑入口直接收选中 `ModMetaData`，稳定身份在后台内部统一解析。没有 Package ID 的本地 Mod 使用既定 `local:` 回退身份，不会在选择转换时被静默丢弃。
21. 身份实现与基准文档静态对照时发现两处未落准：本地 Mod 回退身份误用了 Workshop ID；候选 ID 对 `entryKind/logicalLocator` 复用了 Package ID 的全小写规范。现已分别改为“规范化作者＋名称＋根文件夹名”和“保留语义大小写、只做外围空白／路径分隔符／NFC 规范化”。Package ID 与来源域仍使用 invariant lowercase。修正发生在数据库建立和发布前，不需要迁移既有身份。
22. SQLite 依赖组合经过官方 NuGet 包结构和程序集静态字符串复核：`System.Data.SQLite 2.0.4` 的 `net471` 程序集直接导入基名 `e_sqlite3`，`SourceGear.sqlite3 3.53.4` 正好提供四个目标 RID 的同名原生库，因此不是旧版 `SQLite.Interop.dll` 部署模型。继续采用“一份约 400KB 的托管 ADO.NET Provider＋按平台选择一个原生文件”；Unix 预加载使用 `RTLD_NOW | RTLD_GLOBAL`，确保随后按基名解析的 P/Invoke 能复用绝对路径加载的模块。依赖仍需四个平台实机验收，静态包结构不能替代运行验证。
23. 稳定身份是 AI 数据路径的唯一选择键。公开 AI 复核／翻译入口可从当前 Mod 快照解析身份后下沉；试跑则在按钮触发时冻结明确的稳定身份列表，编排器原样传给两个模拟子能力。身份解析只确定允许涉及哪些 Mod，不替子能力裁定候选范围；两个子能力都在数据库侧二次排除受保护目标。AI 复核由当前有效候选分页 SQL直接裁定范围；AI 翻译另执行本地分析／同步与译文状态资格检查。
24. 一键翻译的失败传播在设计中未写死，实施选择“步骤级尽力继续、用户取消立即停止”。分析、AI 复核或 AI 翻译发生普通错误时保留该步骤已经提交的逐 Mod／逐批结果并继续调用下一独立步骤；下一步骤仍按数据库当前有效状态自行确定范围，因此失败或未就绪 Mod 会被明确跳过，其他 Mod 可以继续。全部步骤结束后由一键运行汇总抛出错误并标记失败；`OperationCanceledException` 不继续后续步骤。该策略不把一键入口重新变成强耦合事务，也不掩盖局部错误。
25. 再次按“启动器只传选中 Mod 与运行策略”静态核对时发现，组合分析服务仍会先统一构造目标快照、判断缓存，再把同一批目标交给 XML/DLL 通道；这让组合入口掌握了两个步骤的数据准备职责。现拆成两个完整的 `AnalysisStepService`：XML 与 DLL 分别接收原始 Mod 列表和 `forceAnalysis`，分别读取目标语言、建立目标快照、检查自身版本／指纹、按 Mod 串行处理并保存结果；组合分析服务只读取 DLL 开关并按 XML → DLL 顺序调用两个步骤。两步可能各自执行一次目标快照读取，这是为保持步骤可独立调用和消除双重范围逻辑接受的开销，后续只能优化步骤内部共享的只读底层缓存，不能把候选范围裁定重新上移到启动器。具体步骤服务均收为程序集内部类型，UI 只能通过 `WorkflowBackend` 的独立入口或编排入口调用，不能绕过启动器直接传递内部数据。
26. 分类位图的全零值静态核对时发现实现曾直接向上返回 `NotAnalyzed`，与基准规定的“无来源结果时工作流回退为待确定”不一致。现统一解析器在四层全为 `00` 时返回有效分类 `Undetermined`，同时 `GetEffectiveLayer` 仍返回空值，从而既让范围查询按待确定处理，又能在报告中区分“系统回退”与某一来源明确给出的待确定。数据库原始位图不被改写。
27. DLL 候选稳定定位最初直接复用了扫描清单中的 `LiteralOrdinal`；该值会把方法内明显不可翻译、已被召回器排除的字符串也计入序号，与基准的“只对可翻译字符串使用点编号”不一致。现 DLL 分析步骤按程序集逻辑路径、声明类型和规范方法签名分组，在扫描器已按 IL 顺序返回的候选中独立从 `0` 编号，候选 ID 不再因前面新增一个不可翻译内部字符串而改变。旧硬编码补丁清单的 `EntryId` 仍用于运行时补丁绑定，不进入新数据库 `candidateId` 的哈希材料。由于候选定位算法发生变化，DLL 分析器版本同步提升为 `dll-3`，旧 `dll-2` 结果会按版本规则自动失效。
28. 启动同步静态审阅发现，新后端创建时调用旧 `EnsurePackInitialized()` 会在建立目录后额外排队一次延迟 750ms 的旧翻译包维护；它不受新任务协调器租约约束，可能在启动同步建立文件索引时并发清理或迁移 XML。现新增仅建立生成包骨架和说明文件的 `EnsureWorkflowPackStorageReady()`，新后端只调用该入口，不再暗中启动第二个文件写任务。旧扫描流程仍可按原入口显式排队旧维护，UI 迁移后应继续把旧文件维护纳入统一任务协调器，而不能恢复隐式并发。
29. 启动同步原先若恰逢旧任务或另一新任务占用协调器，只记录一次“后台繁忙”并重置排队标志；由于游戏数据加载钩子通常只触发一次，本次启动可能永远没有完整同步代次。现启动同步请求在后台等待现有任务结束，并处理“检查后被其他任务抢先获得租约”的竞态，直到成功取得自己的独占租约或发生取消／真实错误。等待期间不建立半份数据库快照，也不会和当前任务并发执行。
30. 为便于研发调试和故障回溯，手动译文保存／删除及分类撤销／还原也把安全的输入摘要写入 `WorkflowRuns.input_json`：单条编辑记录候选 ID、操作类型及手动译文字符数；批量分类记录候选总数、排序后选择集指纹和最多 100 个 ID 样本，避免 10 万条选择把运行表膨胀成巨型 JSON。任何入口都不记录译文正文、API 密钥或提示词内容。这样这些独立步骤与分析、试跑、AI 复核和 AI 翻译一样，都能从运行记录确认实际作用范围。
31. 公共 `WorkflowBackend` 曾保留一个把 Package ID 预解析成数据库 `modIdentity` 的辅助入口；虽然新步骤已经不再使用它，继续公开会诱导 UI 恢复“启动器先查身份、再把内部身份传给步骤”的旧结构。现删除该公共入口，稳定身份解析只存在于步骤内部共享实现和仓储内部查询中。UI 的选择模型始终保留原始 `ModMetaData`，运行记录只保存其安全摘要。
32. SQLite 的外键、忙等待、WAL 与同步级别最初只写在连接字符串中，不同版本 Provider 对扩展关键字的解析兼容性存在不确定性。现每次打开连接后再显式执行 `foreign_keys=ON`、`busy_timeout=5000`、`journal_mode=WAL` 和 `synchronous=NORMAL`，确保 XML/DLL 独立步骤使用各自短连接时仍具有一致的外键约束和锁等待行为。该设置仍需后续三平台真实运行验收，静态代码不能证明原生库行为。
33. 基准要求启动同步与随后 Memory Drop 不得把生成包 XML 连续解析两次。新数据库索引与旧运行时注入原本各自有缓存，但两份缓存互不相通，首次启动仍会各读一遍。现 `TranslationFileIndex` 在读取／复用每个 XML 后，把同一份键值结果连同当前长度和修改时间填入旧运行时的 `XmlParseCache`；Memory Drop 随后通过原入口加载时命中该缓存，不再读取或解析同一文件。读取失败的文件若存在上次可靠索引，也把保留的旧键值按当前元数据注入缓存，使本轮保持上一次可用运行时翻译并把数据库标为 `ReadError`，而不是因一个损坏文件清空所有旧注入。
34. `CandidateEvidence` 在设计早期被列为建议实体，但当前每个条目只需要一份当前证据，单独建表会让 AI 复核的常用查询增加联表或 N+1 风险。首版选择把它实现为 `Candidates.context_json` 内联逻辑实体：XML 保存 Def/规则上下文，DLL 保存不可变补丁上下文和直接调用目标；AI 复核指纹包含完整 JSON 供诊断，但证据变化不再自动使旧 AI 位失效。暂不计算完整跨方法调用图，因为当前扫描器能够可靠提供的是字符串所在方法及其直接消费调用，伪造不完整的“全调用链”反而会误导模型；以后引入 Cecil 全调用图时再增加证据版本和一对多迁移。
35. AI 批次按 Mod 和来源文件分组，并只在候选条目边界拆分。若单个条目连同不可分割的 JSON 上下文本身已超过 12000 的软估算上限，首版不截断原文、定位符、占位符或 DLL 补丁证据，而是把该条目作为单独批次提交；真实模型若拒绝该批次，只把该条目标为失败并记录逐 Mod 错误，后续文件和 Mod 继续。选择这一策略是因为把一个可翻译条目切成多次模型调用无法安全合并固定 JSON 输出，静默截断又可能破坏格式参数和语义证据。
36. 工作流固定设置保存原先虽然取得全局租约，却没有写入 `WorkflowRuns`，导致 DLL 开关、AI 复核范围或试跑比例发生变化时缺少可追踪的成功／失败记录。现配置保存与其他独立操作一致：先记录不含密钥的配置 JSON，互斥校验或数据库写入失败时落失败终态，成功时落完成终态。普通按钮运行仍只传临时覆盖，不能借运行记录反写固定设置。
37. AI 翻译取消／顶层异常收尾最初会对本次所有候选逐条重新查询数据库，以判断哪些已经成功；5～10 万条任务在停止时会形成明显 N+1 查询并延迟释放全局租约。现步骤在内存维护已到达批次终态的候选 ID：成功、校验失败或已处理的批次错误均加入集合，取消只把尚未进入终态的剩余 ID 批量恢复为未翻译，顶层异常则批量标为失败。真正发生文件批次部分写入异常时仍只对该失败小批逐条核实现状，避免覆盖已经落盘并完成数据库提交的条目。
38. 同一状态写给大量条目的仓储方法原先虽在一个事务内，仍逐条创建并执行 SQL。现 `SetTranslationState`、批量手动分类／撤销以及“还原到本地分析”统一使用连接级临时候选表和单条集合式 `INSERT…SELECT`／`UPDATE`，不受 SQLite 参数数量限制，也避免 10 万次命令往返。AI 复核和翻译完成写入因每条分类、理由或译文不同，继续按受控小批短事务提交。
39. `AnalysisRuns.result_fingerprint` 最初只包含候选 ID、原文哈希和分类位，无法区分“分类相同但上下文证据、输出绑定或规则原因发生变化”的两次结果。现结果指纹同时纳入内容指纹、结构化证据哈希、托管输出路径／键及 XML/DLL 原因码；诊断列表仍单独保存为受限长度 JSON，不把不稳定错误文本混入确定性结果指纹。
40. 同步分支的调试日志补齐来源变更镜像、高优先级恢复、文件改动接纳和无效译文四类关键裁决；日志只写 `candidateId`、规范文件／键、来源和数据库／文件哈希前 12 位，不写原文或译文。这些开发字段仅在日志级别为 Debug 时记录；默认 Info 只保留关键运行节点、汇总与真实错误。
41. 三平台路径审阅还发现 DLL 运行时扫描器判断程序集是否位于 Mod 根目录时写死了不区分大小写；这在 Linux 的大小写敏感文件系统上可能把不同路径错误视为同一路径。现改用统一 `WorkflowPath.Comparison`：Windows 使用 `OrdinalIgnoreCase`，Linux/macOS 使用保守的 `Ordinal`；Package ID、语言键等语义字符串继续使用各自规则，不与文件系统比较混用。
42. 为从类型可见性上落实“UI／启动器不能自行查数据库并筛候选”，SQLite 连接工厂和 `WorkflowRepository` 收为程序集内部类型；对外唯一业务门面是 `WorkflowBackend`。内部仓储仍保留少量迁移期辅助方法，但它们不能被其他 Mod 程序集或 UI 插件当成稳定 API 绕过任务租约、文件操作日志和步骤范围解析。
43. （历史实现，已由第 107 项补充）组合分析仍先完整执行 XML；旧 DLL/UI 互斥保护的背景保留，但 UI 拦截现已改为只采集、不翻译的临时探针。
44. 对“新发现的第三方／Mod 原生译文是否一律复制进生成包”作了边界选择：没有托管镜像时，实际外部来源文件本身就是 `TranslationResults.source_file` 对应的有效译文，不额外复制，避免分析步骤偷偷变成文件写入／热重载步骤；只有数据库已绑定托管输出而外部高优先级内容发生变化时标记 `SourceChanged`，刷新同步再更新该镜像。处于 `SourceChanged` 的 Mod 暂不进入 AI 复核／翻译，防止一键链末尾的 Memory Drop 又加载旧镜像；用户刷新状态后即可继续。外部来源消失的 `SourceMissing` 条目已是未翻译，可由后续 AI 翻译合法覆盖旧镜像，不整 Mod 阻塞。若明天 UI 设计决定提供“把未启用翻译补丁导入生成包”的显式功能，应作为独立操作而不是分析副作用。
45. 外部译文消失时的仓储更新最初只把状态改为未翻译，却保留了第三方／原生的高优先级 `translation_origin`。后续 AI 翻译即使成功写入文件，也会被数据库的来源优先级条件拒绝更新，造成文件与数据库分裂。现 `SourceMissing` 同时清空当前译文、哈希、原文绑定及外部来源字段，把来源归零，但保留 `managed_output_file/key` 供同步删除或下一次合法译文覆盖；分类位完全不受影响。
46. DLL 候选定位的程序集字段最初只取文件名，若同一 Mod 的不同子目录存在同名程序集会生成相同定位。现改为 Mod 内规范相对路径（去扩展名、分隔符统一为 `/`），既避免碰撞，也不把机器绝对路径写入稳定 ID。该修正在新身份架构正式启用前完成，`atc-candidate-v1` 尚无已发布数据需要迁移。
47. 旧翻译管线的停止操作会保留全局取消标志，旧网络请求层也会读取该标志。若新工作流只创建自己的取消令牌，用户停止一次后，下一次 AI 复核／翻译仍可能被网络层立即取消。现所有公共后台入口在成功取得全局任务租约后统一重置上一次管线取消状态；本次任务自己的租约令牌和外部取消令牌仍独立生效。该重置属于后台启动契约，不依赖 UI 在点击每个新按钮前额外清理状态。
48. 原文变化的初版失效更新只把翻译状态改为未翻译，却保留旧译文和高优先级来源；随后 AI 翻译虽可能写入新文件，数据库会因来源优先级拒绝接纳，形成分裂。现原文哈希变化时立即清空当前译文、译文哈希、来源和外部来源绑定，并标记 `SourceTextChanged`；暂时保留 `source_text_hash_at_translation` 作为“旧译文基于哪份原文”的同步清理证据。若用户先刷新，同步会凭哈希不一致删除旧托管文件并清空记录；若用户直接重新翻译，新译文可合法覆盖且会把该字段更新为当前原文哈希。
49. 运行汇总最初只按 Mod 保存候选数与输入／输出 Token，而 AI 复核的“产出判断、有效分类改变、受人工层保护”和 AI 翻译的“完成、失败”只有整批总数，明天 UI 无法可靠展示每个 Mod 的步骤结果。现 `AiStepEstimate` 为这些指标补齐逐 Mod 字典，真实步骤和模拟步骤在每个文件批次更新，最终随 `WorkflowRuns.result_json` 和逐 Mod 试跑报告持久化；UI 只负责读取展示，不重新推导业务裁决。
50. 仅把逐 Mod 字典嵌在整批 `WorkflowRuns.result_json` 中仍不适合作为列表查询接口，也会让一键编排内部调用的 AI 步骤缺少自己的可定位报告。Schema v11 增加 `WorkflowModReports(run_id, mod_identity, task_kind)`：独立试跑／AI 步骤完成时拆分保存，一键编排内部完成 AI 复核或 AI 翻译后也立即各存一组独立报告。分析结果继续由更细粒度的 `AnalysisRuns` 保存，当前分类／译文状态继续以候选表和译文表为权威；报告只保存当次计数、Token、跳过原因和错误摘要。
51. 旧 DLL 扫描结果会按字符串 `EntryId` 排序，原始使用点序号达到两位数后可能出现 `10` 排在 `2` 前面的字典序；新候选编号若直接沿用该列表顺序，会偏离规范 IL 遍历顺序。现 DLL 分析器先按程序集相对路径、类型、方法和整数 `LiteralOrdinal` 排序，再在每个方法内只对已召回候选从 `0` 编号；因此排除不可翻译字符串后仍保持原始 IL 相对顺序。
52. 主工作台不能在每帧直接查询 SQLite，也不能为 500～1000 个 Mod 逐个读取候选和分析状态。只读 `WorkflowWorkbenchSnapshot` 门面使用 SQLite 直接按 `mod_identity × source_domain` 聚合分类和译文状态，只返回每 Mod 汇总行；另一次轻量查询读取分析运行状态。UI 只在首次打开或后台任务从忙碌转为空闲后异步刷新，不做固定频率轮询，也不在 C# 中实体化候选再聚合。
53. 试跑总览不再常驻占用列表高度。主工作台只有存在历史报告时才在按钮上方显示“上次试跑预计 N 总 Token／查看详细”一行；完成新试跑后自动打开中型汇总窗口。窗口固定分开显示 AI 复核输入／输出、AI 翻译输入／输出、基础合计、1.2 安全预算和逐 Mod 报告，不由 UI 重新估算。
54. 主页面底部状态区采用一个可变区域而不是分散的顶部进度和底部日志：任务运行时左侧显示总体与当前 Mod 两级进度；展开后左侧保留进度，右侧在任务详情、运行日志和错误日志之间切换。没有任务时保留约 25px 的固定折叠入口，日志和最近任务不会因 idle 消失；Mod 详情跳转第二个标签页，不占用底部任务区。
55. 云端翻译和设置标签页本轮保留现有实现；全局 `IsRunning` 已包含新协调器状态，因此这些页面原本基于该属性的写操作会在新后台任务期间禁用。译文编辑页使用新数据库候选模型：左侧选择 Mod，右侧可按当前有效分类、翻译状态和文本筛选候选。详情区只展示条目自身来源域对应的 XML 或 DLL 本地层，再展示 AI 与手工层；当前有效层使用独立高亮。手工分类收束为“未设置（跟随自动结果）／需要翻译／待复核／无需翻译”四项下拉，并在分类层旁提供单条“清除 AI 复核结果”。分类保存成功后只更新当前页快照，不立刻重新执行当前筛选使条目从用户眼前消失；搜索、切换筛选、Mod 或页码时才重新查询。
56. 云翻译下载仍沿用旧文件下载与注入逻辑，本轮不把它暗中接入新版数据库同步。单个下载和批量下载成功后都会明确提示用户返回“翻译工作台”点击“刷新状态”；只有该独立同步步骤完成后，数据库候选状态才与新下载的译文重新对齐。
57. 主工作台列表把三个对象严格分开：列表只展示 Mod 当前状态；底部可变区只展示当前后台任务；试跑列和顶部摘要只展示历史试跑结果。列表“详情”不再复用底部任务详情，而是切换到第二个“译文编辑”标签页、自动选中该 Mod，并加载它的候选条目。
58. “本地分析结果”根据 `AnalysisRuns`、当前 Mod 内容指纹和当前分析器版本把 XML／DLL 区分为未分析、已过期、当前有效或失败；仅当前有效时才分别按 `source_domain` 和对应本地分类层展示“需要翻译／待判定／无需翻译”。分析器版本和 Mod 指纹均按不透明字符串精确比较。历史成功但版本或指纹不匹配时显示黄色“已过期”并在悬停说明旧→新版本或指纹变化；当前失败显示红色“任务失败”，不用旧候选统计掩盖失败。
59. 工作台列表只允许一个主排序字段。默认选中 Mod 名称正序，重复点击在正序／逆序间切换；点击“最近试跑”后改由逐 Mod 保护预算排序，首次为逆序，再次为正序，Mod 名称按钮同步进入未选中状态。未包含在最近试跑中的 Mod 始终排在有报告的 Mod 后面。
60. 本地分析任务使用真实计数进度：总体层表示串行 XML／DLL 工作流中已完成的 Mod 数并显示当前 Mod `x/y`；XML 详情显示真实文件 `x/y`、相对路径和流式读取字节／总字节（可取得时附当前行号），DLL 详情显示扫描单元或候选整理的真实计数。没有真实分母的层级不显示伪造数字，不再把每阶段归一为 1000，也不再用 10%／90% 或 92%／8% 人为权重拼接不同工作量。
61. 底部任务区收起时只有“展开”，展开后右侧使用“任务详情／运行日志／错误日志”互斥页签，不再保留重复的“查看日志”。运行日志自动跟随只在用户仍位于底部时生效；用户向上滚动后立即解除跟随，禁止使用距离底部 100 像素的强制吸附。顶部试跑摘要、逐 Mod Token 和本地分析文本分别打开整批试跑报告、单 Mod 试跑报告和 XML／DLL 原始分析统计。
62. XML 分析器版本提升为 `xml-2`，唯一语义基线是提交 `622d6af`（v3.0）的完整 XML 分析逻辑。V4 扫描器冻结当时的 `ExactTextTags`、`BlacklistedFields`、`IsTranslationTarget`、`IsProtectedDefPath`、`LooksLikeDefReferenceValue`、`ShouldForceTranslateListItem`、`IsKnownTranslatablePath` 和 `TraverseDefNode` 条件与执行顺序；没有大型数据子树剪枝、数值比例、候选数量／密度阈值、熔断或额外失败态，也不使用后来扩展的字段后缀和保护路径改变候选集合。V3 选出的条目直接作为 XML“需要翻译”结果写入 V4 数据库；Keyed／DefInjected 继续按 V3 只读取文件根容器直接元素子项的语义。旧分析器版本候选在初始化时仅标记 `is_present=0`，不物理删除历史；本次完整分析成功后，仓储在单 Mod／XML 域事务内先失效旧当前结果，再 upsert 本次完整 V3 结果，强制分析沿用同一原子覆盖规则。
63. 译文编辑页改为仓储级数据库分页。SQLite 分别执行 `COUNT` 与行查询，搜索、当前有效分类（手动 > AI > DLL > XML > fallback）、译文是否匹配当前原文哈希及稳定排序全部下推；默认页长 100，内存只保留当前页和后一页预取，不再对单 Mod 创建全部 `WorkflowCandidateEditorItem`。Schema v12 增加与稳定排序一致的组合索引。请求携带 Mod、搜索、筛选和页码查询键，旧请求即使稍后完成也不会覆盖新选择；页面显示已加载范围、总数和前后翻页状态。
64. 无活动任务时底部仍保留 25px 折叠栏和“任务／日志 ▸”入口；展开后继续提供任务详情、运行日志、错误日志与打开日志文件。协调器在释放活动租约前保存最近终态快照，包括成功／取消／失败、完成时间、范围、最终步骤和错误摘要，idle 不再等同于丢失最近任务。
65. 试跑编排器只依次调用 `AiReviewService.ExecuteAsync(modIdentities, options, true)` 与 `AiTranslationService.ExecuteAsync(modIdentities, true, options)`，汇总返回值并保存逐 Mod／整批报告；它不读取 `CandidateRecord`，也没有独立的复核／翻译估算算法。两个子能力按传入身份顺序逐 Mod 工作，仓储用 `CountAiCandidates` 分离轻量计数，再由 `GetAiCandidatePage` 以 `(source_file_relative_path, source_line_number, candidate_id)` 稳定键执行 keyset 分页；`is_present=1`、候选 Mod 指纹等于当前 `Mods.version_fingerprint`、当前 XML／DLL 分析器版本、有效分类和译文是否匹配当前原文哈希均下推 SQLite，过期分析候选不会进入计数或页面。每页只在当前子能力内按文件拆批，复用正式运行的批次规划、完整提示词和统一模型网关，处理后清空页面集合并释放 reader／connection；`isSimulation` 只阻止真实 API 和分类／译文业务写入。AI 翻译内部按每个 Mod 的稳定顺序取 `ceil(待判定数 × 比例)`，再与“需要翻译”条目合并进入同一游标流和批次规划；编排器不复制比例算法。报告中的未译文分类池与当前有效译文覆盖数也由翻译子能力用轻量 `COUNT` 返回。Schema v13 增加与 AI 游标一致的组合索引。两个 AI 阶段向协调器报告真实总候选、Mod `x/y`、当前 Mod 候选 `x/y`、实际批次序号与本批条数；流式批次规划没有预知总批次数时不制造分母。后台资格检查继续从 `Mods.package_id` 调用唯一的 `IsNonTranslatableSystemPackage`，记录 `protected-system-package` 跳过原因。
66. `xml-2` 的源文件读取改为顺序 `FileStream + XmlReader`。每个 Def 只保留当前元素栈、父路径、同父 `li` 序号和仍可能成为候选的纯文本叶子；注释／处理指令仍按 v3.0 的 `XmlDocument.ChildNodes.Count` 语义使节点失去“纯文本叶子”资格，限定名、`defName` 原值和直接子项读取也保持原行为。数值、坐标、引用值等仍仅由冻结的 V3 判定即时拒绝，没有增加任何新剪枝。Mod 文件 SHA-256 同样改为固定缓冲区流式计算，稳定内容指纹不变；文件记录不再对整份 XML 做无业务意义的 Token 估算，候选 Token 仍只估算实际入库文本。
67. 主工作台两排工具栏和三列颜色已按新语义落地。第一排为搜索、明确带前缀的 Mod 范围、分析状态、全列表“刷新状态”和管理；第二排为总选择／筛选外选择统计、全选筛选结果、反选筛选结果和清空选择。保护 Mod 由 RimWorld 当前实际安装元数据提供，已启用范围按真实 Active 过滤、全部范围按实际识别项显示；保护区只在状态“全部”时置底显示。分析列使用灰／黄／红／白＋绿点，分类列按需翻译／待判定／无需翻译分段着色，译文列按已译／未译／失败／零值分段着色，不再整行统一染色。
68. AI 复核资格已收束为“规范化稳定身份 → 从 `Mods` 排除受保护目标 → 统计／分页读取当前有效候选 → 模型判断 → 保存复核结果”。它不再检查 `TranslationSyncState`、译文状态就绪或执行与候选 SQL 重复的宽泛分析前置查询；分页 SQL 自身限定 `is_present=1`、当前 Mod 指纹和当前 XML／DLL 分析器版本，零候选 Mod 明确跳过。AI 翻译仍保留同步代次和未就绪译文状态保护。
69. `ModelInvocationRequest.EstimatedOutputTokens` 仅供 simulation 成本估算。真实模型调用由所选 `ApiKeyConfig.AtcMaxOutputTokens`（旧配置默认 10000）和当前模型已知输出能力共同决定；Google 模型列表保存 `outputTokenLimit`，OpenRouter 保存 `top_provider.max_completion_tokens`，其他无法可靠取得的提供方显示“限制未知”并只采用用户值。模型能力按模型名保存和查询，切换模型不会串用。响应携带提供方、模型、配置上限、已知能力、最终上限、实际 Token 和 `finish_reason`；触顶直接批次失败，不自动提额、重试或拆批，残缺 JSON 不进入解析。
70. `AiWorkflowStageReporter` 统一在规范化输入、保护目标排除、候选计数、游标页读取、文件分组／批次规划、提示词构造、模型等待、响应接收、结束原因检查、解析完整性校验、数据库／文件写入以及批次／Mod／整步完成前更新任务 Detail，并输出中文 Info 阶段日志；Debug 追加耗时、数量、游标、页长、提供方、模型、配置／能力／实际上限、实际 Token、finish reason 和异常类型，不记录凭据、完整提示词、完整响应或译文正文。试跑编排器另报告 AI 复核估算、AI 翻译估算和报告保存三次切换。
71. 设置页日志级别统一为 Error／Info／Debug（中文“错误／信息／调试”），新安装默认 Info。旧 `EnableDevelopmentDebugLogging=true` 迁移为 Debug，false 迁移为 Info；保存后以新枚举为真源。Error 始终写错误，Info 写关键运行节点与错误，Debug 在其上增加开发诊断，三档同时约束 ATC 持久日志与 RimWorld 日志输出。
72. 工作台 `GetWorkbenchModAggregates` 的翻译状态聚合现在只对当前有效分类 `NeedsTranslation` 计数：未翻译排除失败态，并只包含 state=0 或 state=2 但原文哈希缺失／不一致；翻译中、已翻译、失败分别限定 state=1、当前哈希匹配的 state=2、state=3。待判定和无需翻译不进入任何翻译状态。XML／DLL 行、顶部汇总和状态筛选继续消费同一聚合结果，与 AI 翻译候选 SQL 对齐。

74. 启动译文加载与手动“刷新状态”彻底拆开。启动路径只调用现有 Memory Drop 读取本地缓存译文并注入游戏，不创建工作流数据库后端、不查询 `Candidates`／`TranslationResults`、不重算或写回译文状态；工作台列表独立读取数据库已保存状态，首次进入或重新进入标签页都异步重读汇总，不等待启动文件加载。只有用户手动点击“刷新状态”才建立目标语言文件索引并更新数据库；该入口先比较 `TranslationFileCache` 的长度、修改时间和内容哈希，只把新增、内容变化、读取失败或已删除的文件路径放入临时集合，再对这些路径关联的当前候选及已有托管绑定执行 `candidate_id` keyset 分页，文件未变化时候选数为零。Schema v14 的同步游标索引保留用于变化文件涉及大量条目的分页。文件索引、变化文件数、候选计数、分页核对和最终发布均报告中文阶段和真实分母；发布仍以完整同步代次原子提交。
75. 研发库核对确认旧错误 XML 扫描留下 881,215 条 `xml-1` 过期候选，其中 `Ancient urban ruins` 占 695,785 条，并关联 1,762,430 条空的历史译文状态；分析器版本初始化已经把这些候选标为 `is_present=0`，当前 `xml-3`／`dll-3.03` 工作流不再承认它们。初始化失效 SQL 改为只更新仍处于有效状态的旧版本行，避免每次打开数据库重复改写全部历史行；重新分析只将此前仍有效的同 Mod／来源候选退场，再按稳定 `candidateId` 定点 Upsert 当前结果，不再建立全历史候选临时集合或重复更新过期行。工作台、编辑器、AI、手动同步、外部译文清理和生成译文绑定都同时限定 `is_present=1`、当前 Mod 指纹和当前分析器版本；过期行只允许在重新发现相同稳定 ID 时由主键定点复用已有译文。
76. “管理”菜单提供显式的“一键清理过期数据”。入口先在后台统计 `is_present=0` 候选及关联的译文状态、文件索引绑定和文件操作记录，再显示带真实数量的不可恢复确认；只有用户确认后才取得全局任务租约并删除这些数据库记录。当前候选、分析运行历史、磁盘译文文件和模型配置不在清理范围。删除事务提交后尝试执行 SQLite 压缩以回收磁盘空间；压缩失败不回滚已经完成的数据清理，但必须在错误／Debug 日志和完成提示中明确区分。该操作不会随版本升级、启动或重新分析自动触发。
77. 正常数据库初始化不再执行 `PRAGMA quick_check`。该命令会按数据库物理文件规模遍历页面和 B-tree；即使当前有效候选很少，历史页和索引仍会让首次打开工作台长时间阻塞。正常路径现在只执行 Schema 版本迁移和分析器版本失效标记；数据库完整性检查不属于启动／工作台读取的前置条件。
78. AI 复核与 AI 翻译在每个候选页内共用 `AiBoundedBatchDispatcher`：先串行完成跨文件组批和提示词构造，再按 `MaxThreads` 维护滚动模型请求窗口，常驻网络任务不超过上限；响应允许乱序到达，但 `finish_reason` 检查、JSON／短序号完整性校验、SQLite 分类保存、翻译文件写入及翻译状态更新按原批次顺序串行提交。窗口完成一个请求后才补入下一批，取消停止新调度并传播给在途请求；单批异常继续只影响本批。simulation 强制单路且模型网关不发真实请求。进度区分已排队、实际进行中、响应收到、批次提交和累计处理候选，不把 Task 创建数当完成数。
79. AI 翻译的“模型响应完整但本地译文校验拒绝个别条目”不再走整批失败日志。完整性校验成功后逐条应用，合格译文继续在同批写入，拒绝项仍由 `SetTranslationValidationFailure` 保存失败状态；Info／任务详情报告请求成功数、成功保存数和校验拒绝数，错误页明确记录本地校验拒绝。Debug 逐条保存批次短序号、Mod、源文件、locator、完整原文、模型实际返回译文、校验规则和拒绝原因，便于本机诊断且不丢弃模型输出；不记录 API Key、Authorization、完整提示词或未脱敏 URL。网络、超时、输出触顶、响应格式或完整性失败仍属于整批不可用错误，并继续处理其余批次。
80. AI 复核结构化协议恢复第三个成功值 `needs_review`。提示词只允许 `needs_translation`、`no_translation_needed`、`needs_review`，并限定第三值只能用于证据不足、冲突或无法可靠判断玩家可见自然语言的情况；未知值仍使批次失败，短整数索引的无遗漏／无重复校验保持不变。解析后把 `needs_review` 作为 `CandidateClassification.Undetermined` 写入 `ClassificationLayer.AiReview`，继续保存 `ReviewVersion`、fingerprint 和 reason，不新增表、迁移或领域枚举；手工层仍优先，但 AI 结果照常留存。该项计入完成数而非失败数，继续保持待复核且不进入 AI 翻译；下次用户显式复核仍可再次选中。真实运行按批和按 Mod 记录三类数量，Debug 按条记录短序号、模型分类与理由；当前轮分页 cursor 不因写回待复核而回退或重复。
81. DLL 本地裁决器提升为 `dll-3.01`。召回集合不收窄，改进仅发生在高置信度本地分类：跨方法摘要除参数流外继续携带被返回的字符串字面量来源，使辅助方法返回文本后进入明确 UI sink 的路径仍可追溯；`.Translate()` 的键、数值格式字符串、类型／字典查找键和资源路径按具体调用参数记录为无需翻译，翻译调用的返回值不再错误携带原键进入后续 UI sink。数组与常见泛型容器增加保守的局部来源传播；UI sink 补充文本框和消息框，日志 sink 补充 Unity／Console。没有明确调用证据的 `QM_` 前缀、方法名或文本外形不直接作为分类依据，字段、复杂对象图、委托等仍无法证明去向的数据继续保留待复核，不能为了降低待复核数量强猜。对 Quartermaster 的 761 条现有 DLL 候选执行只读离线分析后，本地可明确裁决 493 条无需翻译、保留 268 条待复核、0 条直接需要翻译，且无分析诊断；其中新增明确排除 366 条本地化键、89 条比较键、21 条格式串和 2 条资源路径。该数字仅代表本次指定程序集与现有候选数据的离线结果，不代表游戏运行验收。
82. DLL 本地裁决器继续提升为 `dll-3.02`：程序集内静态字段、静态数组和常见泛型容器的字面量来源参与固定点传播；加载静态字段后经过数组读取、容器枚举或常用 LINQ 序列变换仍保留原始来源；`DirectXmlCrossRefLoader`、`ParseHelper` 和 LINQ `Contains` 增加确定性的非界面语义。实例字段不按字段名跨对象全局合并，以免不同实例之间互相污染并产生错误“需要翻译”。本次版本只扩大可证明的本地裁决范围，仍不按 Mod、命名前缀或文本外形强猜。用户在测试环境对 Quartermaster 重新分析后的实际结果仍为需要翻译 0、待复核 268、无需翻译 493，与 `dll-3.01` 完全相同；数据库确认当前 761 条候选均来自 `dll-3.02`，因此该版本对指定样本没有产生任何有效分类改进，不能把实现代码本身记作优化成果。剩余项的主要缺口不是字面量未传播到静态集合，而是 StatDef 名称、格式符、存档键、字典键和真正界面标签之间缺少精确的领域语义裁决。
83. 工作流日志区在“运行日志／错误日志”页增加“清空当前日志”：只清空当前页的内存显示缓存和滚动位置，不改写或删除磁盘日志文件，两个日志页也不互相清空。普通工作流和试跑启动不再强制把检查器切换为收起状态；任务执行、完成弹出试跑报告时均保留用户当前选择的展开／收起及日志页状态，只有用户点击“收起”才折叠。
84. 工作台批量破坏性操作统一为所选 Mod 的“清除结果…”入口，不再在顶部或管理菜单复制三个独立撤销按钮。确认窗的 AI 复核结果、手工分类结果、AI 翻译结果三项默认均不选择，无选择时确认禁用，并明确提示不可恢复。分类清除使用稳定 `mod_identity` 集合式更新；AI 与手工同时清除即回落到当前本地 XML／DLL 结果。译文清除只匹配数值兼容不变的 `TranslationOrigin.AiTranslation`，按托管输出文件／键删除并同步数据库，不触碰云端下载、手工、Mod 原生或第三方译文；受保护目标仍由后端二次排除。
85. “管理 → 清理过期数据”沿用统一的过期定义 `Candidates.is_present=0`。数据库初始化会把 XML／DLL 分析器版本与当前不透明版本字符串不一致的仍有效候选标为不存在，因此该维护入口同时覆盖分析器版本升级产生的过期数据、Mod 内容版本退场及重新分析替换的旧候选；它仍只在用户显式确认后物理删除，不新增自动清理。
86. DLL 本地裁决器提升为 `dll-3.03`，不为 Harmony 或 `0Harmony.dll` 增加 Package ID／文件名黑名单。Cecil 的 `MethodDefinition.FullName` 在不同泛型参数数量、返回泛型参数同名等合法重载上并不保证唯一；此前 Harmony 的两个 `StaticFieldRefAccess` 方法因此使摘要字典重复键失败，整批结果无法进入本地数据流裁决。结构索引、依赖闭包、摘要和调用解析现在以 `Module MVID + MetadataToken` 为方法主身份，FullName 只保留作解析回退与诊断显示；方法引用解析缓存也纳入引用所在模块与元数据 Token。反射键、日志、资源路径、比较键等继续由通用非 UI sink 规则判为无需翻译，实际进入玩家界面的加载错误和提示仍可判为需要翻译。自测夹具增加两个 Cecil FullName 相同但 MetadataToken 不同的方法，要求两者各自的反射键均得到独立“无需翻译”结果，不允许用去重丢弃其中一个方法。
86. DLL 性能优化第一阶段最终采用“多个 Mod 有界并发、每个 Mod 内的 DLL／程序集严格串行”的安全边界；曾实现的单 Mod 内程序集工作池因共享分析上下文和依赖关系风险已在确认后撤销。DLL 本地并发与模型 API 的 `MaxThreads` 完全分离，新设置表示同时分析的 Mod 数，首次默认 `min(5, max(1, 逻辑处理器数 - 4))`，允许用户在 1～8 间调整。每个 Mod 独立完成召回、Cecil 分析和内存聚合，数据库读取／成功保存／失败保存通过单一门串行执行；一个 Mod 失败不会取消其他 Mod，用户取消则停止所有工作，任何 Mod 都不会保存半成品。运行时 Harmony 反射召回仍受全局串行门保护，因此多个 Mod 形成“前一个 Mod 进入 Cecil 后，下一个 Mod 才进入反射扫描”的流水线；不同 Mod 的 Cecil 阶段可以重叠，但同一个 Mod 内永不并发。第一根进度条统计已经到达终态的 Mod 数，并明确显示“已处理 Mod”（成功保存、有效结果跳过或明确失败都会终结一个 Mod，避免把失败误写成成功完成）；第二根显示全部 Mod 的等权综合进度。单个 Mod 的内存分析进度最多映射到 98%，等待数据库门及写库显示 99%，成功保存或明确终结后才进入 100%。标题显示当前并发活动 Mod 数，详情显示最近有进展的具体 Mod、阶段、程序集和真实 `x/y`。并发进度快照携带单调序号，较晚抵达的旧快照不得覆盖新状态。Info 日志记录并发启动、逐 Mod 进入队列、等待／取得运行时扫描门、静态阶段、保存、跳过、完成和失败，进度刷新本身不刷 Info；Debug 再记录程序集、类型、方法、闭包和调度细节。Cecil 通过结构化的五阶段进度上报单调总体比例和当前阶段真实数量，不使用伪造的 `/1000` 刻度。分析器在单次程序集读取中建立只读依赖索引，以候选方法和确定的 UI／非 UI 汇点为种子，保守连接调用、字段、委托、状态机、编译器生成类型和虚调用；候选映射缺失、闭包为空、触及未解析边或异常比例时回退整程序集。运行时条目与磁盘 DLL 的 SHA-256／MVID 必须一致，读取期间文件变化会明确失败并要求重启或重新加载。该优化不修改既有分类规则、`DllAnalyzerVersion` 或结果算法指纹，也不建立持久结构缓存，因此不会仅因并发数或索引实现变化使用户旧结果失效。同一 DLL 的 SCC 固定点收敛、SCC 内并发和持久结构缓存尚未实现，不得把本阶段描述为 DLL 内部并行方案。
87. 设置页按 V4 现行职责重组为“常用与界面显示、AI 接口、性能与诊断、高级兼容模式、维护与恢复”五个页面内章节，不新增标签页。旧的更新时删译文、启动自动排程、仅扫描启用 Mod、Agent 预判／预算／缓存、来源优先级、术语配置和合并黑名单入口不再展示；启动自动排程代码已移除，旧持久开关加载后强制关闭。来源优先级改为固定的“手动 > 第三方人工 > Mod 原生 > 云端 > AI 翻译”，不再保存全局或逐 Mod 自定义顺序。术语底层暂时保留但不在设置页暴露。动态 UI 拦截进入默认折叠的高级兼容章节；其旧即时翻译子选项由第 107 项的采集探针和自动关闭设置取代，历史 UI 缓存管理只用于兼容数据维护。运行 Profile 只在 Debug 日志级别显示。旧译文格式修复和最近备份恢复在维护章节内使用两个独立区域；名称和范围不正确的旧“恢复出厂设置”入口与实现已经移除，完整清理范围另行确认后重做。翻译任务用量上限保留，并在 V4 AI 翻译入口建立与旧请求传输层共用的用量账本；试跑不建立账本，真实 AI 翻译按目标语言和稳定 Mod 身份形成可恢复的运行键。该预算只限制真实翻译网络请求，不把试跑预估 Token 当作模型输出上限或其他步骤限制。
88. 云端翻译页以普通用户下载为首要路径：目标语言、“刷新云端列表”和“一键下载最佳可用译文”固定在顶部；列表和批量下载范围统一为当前游戏已经加载的 Mod／DLC，不再提供“全部已安装”切换，也不显示未加载 Mod。列表默认只展示当前语言存在可下载云端记录的已加载 Mod，并提供可组合的“汉化组精翻／人工精翻／AI 译文”本地筛选；筛选检查一个 Mod 的全部云端版本，行内默认版本及版本菜单只使用当前筛选命中的记录，“我的上传记录”使用相同筛选。云端 `Official_Group` 的既有语义统一显示为“汉化组精翻”，`IsVerified` 只显示“已审核”，不得据此改变译文来源类型；真正的官方译文在云端增加独立来源类型前不得伪造。汉化组精翻／人工精翻／AI 的限定下载收进可展开的“其他下载方式”，明确表示其中是立即执行的操作而非配置项；下载排除列表从普通设置移到云端页。贡献译文、我的上传记录和管理员凭据统一放入默认折叠的贡献章节；管理员操作只在配置管理员凭据后出现。单个 Mod 行只保留版本、下载和详情，贡献工作区、上传、纠错、下载排除和管理员删除进入详情菜单；删除本地译文不再作为云端行操作。所有单个与批量云端下载入口都必须先显示二次确认；批量下载先在本地整理实际队列，再列明下载策略、范围、目标语言、Mod 数量和内容预览。确认文案必须明确警告云端文件会替换 ATC 生成包中的现有本地译文；数据库已记录的“手动翻译”会在下载后重新恢复，但尚未通过“刷新状态”同步的外部 XML 修改可能被覆盖。只有用户点击“确认下载”后才发送网络请求。批量下载运行时必须在 V4 后台任务中显示队列总数、当前序号、成功、失败与剩余数量，并为每个 Mod 的开始、成功和失败写运行日志。两个批量上传入口先在本地整理真实上传范围，整理完成后必须显示二次确认，列明来源、目标语言、云端来源类别、Mod 数量、内容预览和更新说明状态；只有用户点击“确认上传”才开始网络请求，取消不发送任何云端数据。术语固定为：“手动翻译”只指用户在本地译文编辑器保存的结果；云端 `Manual` 来源统一称为“人工精翻”。云端“最佳可用”只在云端来源内按“汉化组精翻 > 人工精翻 > AI、同类取最新”选择，本地手动翻译仍具有全局最高覆盖优先级。单个或批量云端下载完成后以云端目标语言执行一次 V4 文件状态同步；同步器在云端文件覆盖或缺少对应键时重新发布数据库中仍有效的手动翻译，随后统一重载内存译文，不再要求用户回工作台手动刷新。
89. 翻译用量账本不得把旧请求记录变成永久任务锁。相同请求仍处于本进程 `InFlight` 时继续拒绝重复并发；但显式重试遇到上次中断留下的 `AmbiguousInFlight`，或模型调用已经计费／提交而候选仍因响应解析、完整性或本地应用失败需要翻译的 `Committed` 记录时，保留旧记录及其实际／预计用量，以带状态和序号的归档请求 ID 保存，再为本次尝试建立新的活动预留。旧的不明确请求继续按最坏情况占用预算，新尝试仍受本任务剩余字符和 Token 上限约束，因此恢复能力不能绕过预算。恢复旧任务和重试相同请求都写 Info，Debug 记录请求 ID 前缀、Mod、用途、批次范围与预计 Token。`ambiguous_or_in_flight` 不再作为“预算暂停”错误；真正同时在途的重复请求单独报告 `request_in_flight`，只有字符预算、预计 Token 预算或已锁定的预算停止状态使用“预算暂停”。AI 翻译候选查询只排除原文哈希仍匹配的成功译文，`Failed` 条目会在用户再次执行 AI 翻译时重新进入候选，因此该修复无需用户删除 Mod 数据库或手动重置失败条目。

90. 主人确认 Def 继承进入当前工作流后，XML 分析器提升为 `xml-3`。第一遍按有效内容根顺序只建立带 `Name` 的父 Def 索引；第二遍仍逐文件扫描，普通 Def 继续走 `XmlReader`，只有声明有效 `ParentName` 的单个 Def 临时构造子树并解析父链。继承后继续复用冻结的 V3 字段、路径、引用值和列表项筛选规则，稳定候选定位仍为子 Def 的 `defName + 字段路径`；同名父定义以后出现者覆盖先前定义，缺失父级或循环只记录诊断并回退当前 Def。`xml-2` 候选按现有版本失效机制变为过期，不自动物理删除；该两遍读取、覆盖顺序、候选增量和大型 Mod 内存表现均未经运行验证。

91. V4 AI 复核提示词补入玩家可见文本、路径／资源、类型／方法、Def 引用、序列化值、查找键、格式控制值及 RimWorld Grammar 控制部分的判断边界；请求同时携带 XML／DLL／手工／当前有效分类，以及明确标为“历史参考、必须独立重判”的上一次 AI 分类与理由。XML 上下文增加 Def 名、字段路径、父路径、继承标记和相邻候选；DLL 继续携带程序集、声明类型、方法签名、调用目标、发现方式和 IL 身份证据。

92. 候选身份与 AI 复核元数据分离：稳定 `candidateId` 仍只表达条目逻辑身份；AI 复核证据指纹只包含候选身份、原文哈希、定位、源文件和结构化证据，不包含当前分类、上次 AI 输出、模型或提示词小版本。`AiReviewVersion`、提示词版本、指纹和理由只用于诊断，不再充当自动失效门；只要 AI 层非零，后续复核就跳过该条目，直到用户显式清除当前 Mod 的 AI 复核结果。

117. AI 复核候选计数和分页新增统一的“AI 层必须为空”数据库条件，正式复核与试跑复核共用，因此 `needs_review` 等已有 AI 结果也不会被重复提交。重新分析候选时保留稳定条目的 AI 与手工高层位；编辑页详情区保留单条 AI 复核清除入口，当前 Mod 标题栏提供红色“清除分类数据”，弹窗可独立或同时清除 AI 复核与手动分类，且不包含译文清除；分类筛选新增按手动层非零查询的“有手动分类”。标题栏同时增加复用工作台后端的黄色“热重载”按钮。热重载只重新注入 XML 译文和重载 DLL UI 译文，不触发分析或模型调用。

99. XML 工作流分析不再把扫描器召回的每个 Keyed／DefInjected 候选一律标为“需要翻译”，而是接入既有统一 `TranslationPolicyClassifier`：明确文本为需要翻译，结构值／非语言格式为无需翻译，语义不确定项为待判定并进入 AI 复核范围。格式项通用规则会移除 `{0}`、标签等受保护 Token；剩余没有自然语言字符，或只剩 2～4 位全大写技术缩写时，判为无需翻译。因此 `{0}% / {1}%`、`DPS {0}`、`DPSA {0}` 不再进入 AI 翻译。分析器还会先判断源文本是否已经属于当前目标语言；简体／繁体中文中没有专属异体标记的中性汉字文本也按当前中文目标处理，避免原 Mod 直接写入中文的标签和说明再次送翻。候选稳定 ID 和 `xml-3` 大版本不变，分析算法指纹提升为 v3.2；用户下次执行普通本地分析时因指纹变化自动重算，无需强制分析，旧结果在重算成功前仍可恢复使用。

113. AI 翻译的逐条补试仍严格限制为每个首轮校验未通过条目最多一次，不形成递归或循环重试。补试开始时明确记录首轮未通过总数；运行详情和第二进度条改为显示“当前补试序号／总数、已完成、补试成功、仍失败”，每条完成日志携带相同累计口径，不再以重复的“失败条目单独重试”让长补试队列看起来像死循环。用户在补试途中停止时，尚未执行的条目恢复为进入本次任务前的翻译状态和失败原因，不再一律降为未翻译。

### 静态风险与待确认事实

1. RimWorld 实际加载的多个内容根可能包含同一个 XML 逻辑键。稳定 ID 按逻辑位置生成、刻意不含绝对路径；若同一有效视图中出现重复逻辑键，必须沿用游戏的内容覆盖优先级只送入最终有效文件，不能用物理路径制造两个 ID。当前分析步骤已在内部复用现有有效内容根解析器，但是否与游戏最终覆盖顺序完全一致仍未经运行验证，后续需要用真实 Mod 数据人工验收重复键场景。
2. DLL 扫描基于已加载程序集。当前所有翻译相关列表只展示已加载 Mod／DLC，DLL 分析器也会拒绝未加载目标，避免把“程序集未加载”保存为成功的零候选结果；后续若产品重新要求分析未加载 Mod，需要新增纯 Mono.Cecil 文件扫描入口。
3. 2026-08-17 在主人明确要求准备测试产物后，已使用本机确认的 VS 18 Build Tools 为 RimWorld 1.6 生成 Release DLL，并按固定依赖版本提取 SQLite 托管 Provider 与四个平台原生库。该操作只代表编译产物已生成；未运行游戏、未执行自动测试，业务与界面结论仍属于静态判断和未经运行验证。
4. “已完成同步代次”已补齐为 Schema v4 的 `TranslationSyncState`。同步先完整建立索引、恢复待处理文件操作并在内存形成译文变更集，最后在一个 SQLite 事务内提交全部译文状态变更、整体替换目标语言的文件条目索引并递增 `completed_generation`；取消发生在发布事务前时，当前代次不变。真实 AI 翻译在目标语言尚无完成代次时会按第 123 项先自动同步一次；试跑中的翻译模拟仍保持只读并提示先刷新同步状态。AI 复核不读取或依赖该状态。文件系统无法参与 SQLite 原子事务，因此同步过程中确需恢复的待处理文件操作仍以操作日志为安全边界；它们反映已经实际落盘的事实，不属于未发布的扫描判断。
5. SQLite Provider 与四个平台原生运行库已在本次准备测试产物时，使用仓库固定的 `System.Data.SQLite 2.0.4`、`SourceGear.sqlite3 3.53.4` 和提取脚本写入 `rimworld-mods/AI_TranslationCore/1.6`；每个平台原生文件均附 SHA-256 清单。该依赖组合仍未经 Windows/Linux/macOS 真实运行验证，后续准备测试／发布仍必须走既定构建技能，不能手工换用另一套驱动。
6. 新主工作台和译文编辑页已接入仓储级汇总／分页读取；单个超大 Mod 不再全量物化候选。SQLite 的 `LIKE '%词%'` 文本搜索仍无法利用普通 B-tree 索引，极端大表上的自由文本搜索耗时、预取两页的人工体验和翻页锚点仍必须在真实游戏中验收；如仍不足，应另行评估 FTS，而不是恢复 C# 全量过滤。
7. 已废弃的 Policy 云分析客户端、健康追踪、本地状态、记录模型及其专用自测已经物理删除；本地 Policy Agent／XML-DLL 分类与普通云译文下载上传继续保留。旧预检函数仍保留参数兼容外壳，但已没有云判断网络客户端或结果缓存可调用。
8. 云端批量下载的取消令牌已沿“工作流 → 并发调度闸门 → 云端客户端 → UnityWebRequest”完整下传。取消后不再启动等待中的下载，正在传输的请求会在主线程执行 `Abort`，重试退避和逐项解压也会响应取消；已预清理或部分写入的 Mod 仍进入既有回滚与临时文件清理边界。旧调用继续使用可选参数，不要求同步改造其他云端入口。该调用链仅完成静态接线，尚未经真实网络下载和游戏运行验证。
9. Def XML 继承已按 `xml-3` 接入，但 RimWorld 对多个有效内容根中同名命名父 Def 的最终覆盖顺序、复杂列表合并细节，以及继承候选把子 Def 声明行作为近似来源行的调试体验，仍需在真实 Mod 中人工验收。实现不得退回全部 XML 常驻 DOM，也不得借继承解析改变冻结的 V3 字段筛选规则。
10. “云端译文选择顺序”已按主人确认保留，并嵌入当前云端页的折叠式下载区。静态调用链确认该功能调整的是多个 Mod 生成译文文件之间的读取先后，用于决定重复逻辑键最终由哪个 Mod 的译文覆盖；它不改变固定的“手动 > 第三方人工 > Mod 原生 > 云端 > AI 翻译”译文来源优先级，也不改变“汉化组精翻 > 人工精翻 > AI”的云端版本选择顺序。窗口保存逐 Mod 顺序后通知翻译文件缓存失效并请求内存重载；实际重复键覆盖效果仍未经游戏运行验证。

### 本阶段静态收口结论

后台业务骨架已经按当前基准落地：五个步骤具有独立入口和内部范围解析，一键入口只做显式编排；分类与翻译双维状态、稳定身份、分析器版本／指纹、逐 Mod 报告、试跑模拟、翻译文件操作日志、启动同步、取消与全局互斥均有对应实现。普通步骤公开入口只接收所选 Mod 与运行选项；译文编辑器的显式单条／多选操作可额外提交稳定候选 ID 集合，后台仍会按当前 Mod 和正式候选 SQL 二次约束。SQLite 仓储和具体步骤服务保持程序集内部可见。

业务结论来自静态阅读与逐段对照。本次仅因主人明确要求准备测试产物而执行了 Release 编译和依赖提取，没有运行游戏、执行自动测试、lint、格式化或界面操作；不能据此声称功能已经运行验证。生成产物将在游戏退出后按测试部署规范同步并核对哈希。

114. 2026-09-05 静态复核修正了七处续作问题：UI 采集期间不再让按原文建立的 `PassThrough` 热缓存阻止后续调用点取证；同一原文每次采集会话按第 1、2、4、8……次出现进行指数间隔采样，最多检查 16 次调用栈，使稍后出现于其他方法／Mod 的相同文本仍有机会被发现，同时限制渲染开销，持久化仍按 Package、程序集、方法和原文复合身份去重。采集会话现在检测启用到关闭的下降沿并立即保存证据。试跑覆盖统计只在译文状态就绪的池内区分“已有当前译文”和“本次待处理”，并为所有合格 Mod 生成覆盖数据；AI 复核的“实际处理 Mod”排除零候选跳过项。编辑器将外部译文与模型译文共用的失败输出统一标为“本次被拒绝的译文”。批量上传可恢复问题进入警告日志，删除遗留问号前缀。AI 翻译取消后不再等待 Memory Drop 才结束任务，刷新改为后台继续并记录完成／失败；刷新期间协调器拒绝启动新的工作流，避免与刷新并发修改运行态。

## 122. 遗留 UI 缓存入口与危险操作确认（2026-09-07）

- “硬编码 UI 翻译管理”实际管理的是旧 UI 拦截器的 JSON 缓存（译文、忽略条目和来源归属），与“译文编辑”使用的工作流 SQLite 数据库没有直接关联，也不等同于 DLL UI 临时采集产生的运行时证据。
- 为避免用户把旧缓存误认为当前 DLL 注入译文，入口与窗口统一改称“遗留 UI 缓存”，窗口补充数据边界说明，并采用当前工作流界面的标题、面板、按钮和状态样式。
- 清理遗留 UI 缓存、修复旧译文格式、还原最近翻译备份，以及移除单条遗留缓存译文，均使用统一确认弹窗。确认文案必须说明实际修改或删除范围；危险执行按钮使用红色，取消按钮使用普通样式。
- 清理遗留 UI 缓存只删除旧拦截器的译文缓存、忽略列表和来源归属缓存，不删除工作流数据库、DLL 采集证据、已生成的 DLL 注入译文或 XML 译文文件。
- “在智能补翻清单翻译模组名称（保留原名）”改为简短、与当前页面一致的“工作台显示 Mod 中文名”。具体行为移入悬浮说明：仅按需翻译工作台当前可见的 Mod 名称，显示为“中文名 / 原名”，并明确可能产生 Token 用量。
- “常用与界面显示”的三项顺序调整为“目标语系｜底部快捷按钮｜工作台 Mod 中文名”，将基础语言设置固定在首位。
- 首项不再命名为“目标语系”，产品语义调整为统一的“当前语言（Language）”。现阶段继续兼容既有 `TargetLang` 行为，同时决定 AI 翻译与云端译文的目标语言；后续界面语言改造必须把所有按钮、标题、提示和弹窗统一接到该选择，不能只切换翻译目标或继续分散跟随游戏语言。三项显示顺序相应表述为“当前语言｜底部快捷按钮｜工作台 Mod 中文名”。
- 多语种界面切换暂不进入当前实施范围。当前阶段只收口并人工验收简体中文界面；待简体中文的功能、布局和文案全部稳定后，再以该版本为基准一次性补齐其他语种的按钮、标题、提示与弹窗，不在简中仍频繁调整时并行维护多套界面文案。
- 实机发现工作台译文计数与生成文件可能失去一致：数据库仍保存 Quartermaster 的数百条有效译文，但 XML 输出文件只剩单条时，旧热重载只重读磁盘，无法恢复缺失内容。热重载因此调整为全局恢复操作：先分页读取当前 Mod 版本、当前分析器版本、原文哈希仍匹配且具有受管输出位置的全部已保存译文，按数据库结果重建 XML 与 DLL 清单，再执行 Memory Drop 和 DLL 补丁清单重载。该操作不依赖 Mod 勾选、不重新分析且不调用 AI；任务详情显示“全部已保存译文”和条目进度，不再误报“0 个 Mod”。

## 123. 首次 AI 翻译自动建立译文状态同步（2026-09-13）

- 启动流程继续只负责读取本地缓存译文并注入游戏，不为了建立数据库同步代次而执行完整文件扫描；此前真实 AI 翻译却直接要求同步代次已存在，导致首次正常执行“一键翻译”或“AI 翻译”时只能报错并要求用户手动刷新。
- 工作台 AI 翻译、一键翻译，以及译文编辑器的单条／批量 AI 翻译统一改为：当前语言没有任何完成同步代次时，先在同一个全局互斥任务内自动执行一次译文状态同步，确认代次已提交后再进入翻译；已有完成代次时直接跳过，不会每次重复扫描。
- 自动同步是翻译的数据安全前置，不计入一键翻译的三个业务步骤。外部修改译文文件后仍需用户点击【刷新状态】；只读试跑为了不写数据库，也继续要求已有同步代次。
- 一键翻译的步骤失败包装统一使用中文，外层只报告一次“一键翻译未全部完成”的总结果，并保留内部异常供错误日志查看，不再额外暴露 `AI translation step failed.` 这类英文摘要。
- 本项仅完成代码与文案的静态复核，未经编译和游戏内运行验证。

## 124. 真实 Workshop 样本的 XML／DLL 召回修正（2026-09-13）

- Def 扫描此前会先把无空格的纯英文值视作 Def 引用，因此即使字段明确为 `label`，`lantern`、`respirator` 等单词物品名仍会在统一分类器之前被丢弃。现对 V3 明确文本字段放行这道引用外观检查，结构路径与黑名单保护不变，并将 XML 分析器提升为 `xml-4` 以淘汰旧结果。
- 多语言源目录此前在目标工厂中再次按物理路径排序，同一稳定键去重时又保留最后一条，可能让 Spanish 等低优先级回退覆盖 English。现保留语言解析器既有优先级并对重复候选取首项。
- DLL 直接 UI 调用识别补齐 RimWorld 常用的 `Verse.TaggedString` 与 Unity `GUIContent` 末参数，不再只接受 `System.String`；后续真实样本复核进一步将分析器提升为 `dll-3.06`。工作流文件快照不再只查看 Mod 根目录的 `Assemblies`，而是按 RimWorld 当前有效 LoadFolders 收集版本目录中的程序集；已加载程序集若被运行环境放到 Mod 根目录之外，则以磁盘 DLL 与运行时程序集共同的 MVID 建立安全映射，扫描和应用补丁两端使用同一回退。目标文件快照包含程序集、但运行时扫描一个程序集也未找到时，任务明确失败并拒绝保存“DLL 0”的成功结果。定向补丁解析同时补齐构造函数，不再出现扫描得到但永远无法应用的构造函数条目。
- 真实样本静态读取确认：Modern Learning Menu 有 247 条符合宽召回条件的字符串，其中包括面板标题、说明、按钮和状态文字；Radius UI - Mission Control 与 Colonist Bar 分别有 2323、996 条宽召回字符串。后两者虽有大量 Keyed XML，但 DLL 内仍存在 `Rename or recolor`、`No squads yet`、`Defend` 等未走 `.Translate()` 的玩家可见英文，因此“DLL 0 正常”不是可靠结论。UI 临时采集除 Label、LabelFit、Tooltip 外，现补充 Unity `GUI.Button` 与 `GUI.Box` 的 string／GUIContent 入口，使按钮、方框标题和经包装器进入 Unity GUI 的文本也能形成运行时证据；该改动可迁移到采用相同 RimWorld／Unity UI 调用的其他 Mod。
- Fantasy Biotech 最新云端压缩包静态确认不含截图所示头盔、护目镜和呼吸器键，因此“下载完成但仍为英文”至少包含云端数据不完整，不能只归因于 Memory Drop 失败。本项未经编译或游戏内运行验证。
