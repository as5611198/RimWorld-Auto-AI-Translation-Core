## 1. 设计目标

新版翻译功能采用工作流模式。分析、估算、判断和翻译是可以独立执行、独立保存、独立查看的步骤；同时允许“一键翻译”等编排入口明确组合多个步骤。

核心原则：

1. 每一步都有自己的明确输入、输出、持久化结果和用户入口。
2. 单独步骤入口不得暗中触发其他步骤；编排入口可以明确声明并调用多个步骤。
3. 多个步骤可以读取同一份已有数据，但读取不等于调用数据生产步骤。
4. 每个 Mod 都能独立展示 XML 分析、DLL 分析、试跑、AI 分类复核和翻译状态。
5. 多选 Mod 只是建立一次批量任务；每个 Mod 的结果仍独立保存。
6. 当前代码中的隐式连锁需要改造成职责明确的编排调用；一键能力本身继续保留。

## 2. 统一术语与双维状态

### 2.1 条目来源域

每个候选条目必须明确属于以下一个来源域：

- `xml`：Keyed、DefInjected 或从 Def 中提取的 XML 候选。
- `dll`：由程序集字符串召回和静态 IL 分析得到的硬编码 UI 候选。
- `ui_interception`：运行时 UI 拦截产生的动态文本。它属于兼容模式，不并入标准 XML/DLL 静态分析结果。

XML 与 DLL 可以共用上层接口和查询模型，但不得共用会互相覆盖的结果记录。

### 2.2 分类状态

分类状态回答“这个条目应不应该翻译”：

| 状态 | 含义 |
|---|---|
| 待翻译 | 现有有效判断认为应进入翻译范围 |
| 不翻译 | 现有有效判断认为属于结构、标识、路径、数值或其他不应翻译内容 |
| 待确定 | 现有证据不足，暂时不能确定 |

原代码和旧文档中的“需要翻译”统一改称“待翻译”。

### 2.3 翻译状态

翻译状态回答“翻译执行到哪里”：

| 状态 | 含义 |
|---|---|
| 未翻译 | 尚无当前目标语言的有效译文 |
| 翻译中 | 已进入正在执行的翻译批次 |
| 已翻译 | 已产生并保存通过校验的译文 |
| 失败 | 本次翻译失败，保留失败原因并允许重试 |

“已翻译”不是第四种分类。分类状态与翻译状态必须分别存储、分别筛选。

示例：一个条目可以同时是“待翻译 + 已翻译”；这表示它仍然应当翻译，并且当前已有有效译文。源文本或译文失效后，翻译状态可回到“未翻译”，分类状态不必随之改变。

### 2.4 单一裁决与分类优先级

“步骤独立”不表示 XML 分析、DLL 分析、AI 和人工各自维护一套互相竞争的最终状态。每个条目可以保留多层判断记录，但任何时刻只能按固定优先级解析出一个“当前有效分类”。

优先级从高到低为：

```text
人工裁决
   ↓
当前有效的 AI 分类复核
   ↓
当前有效的 XML 或 DLL 基础分析结果
   ↓
没有有效结果：待确定
```

各层职责：

1. **基础分析层**
   - 由条目所属来源域的 XML 或 DLL 分析器产生。
   - 保存确定性规则分类、理由、证据、分析器版本和结果指纹。
   - XML 条目只读取 XML 基础分析；DLL 条目只读取 DLL 基础分析，不跨域竞争。
2. **AI 分类复核层**
   - 保存 AI 对基础分析结果的再次判断。
   - 只要结论仍然有效，就覆盖该条目的基础分析分类。
   - 本地模型新判断、本地 AI 判断缓存和云端判断缓存都是这一层的“结果来源”，不得各自形成第四、第五套当前状态。
   - 用户明确发起的新复核可以生成新的历史记录并成为当前有效 AI 结论；撤销时按历史恢复，不用时间戳粗暴覆盖。
3. **人工裁决层**
   - 用户主动修改的分类优先级最高。
   - 自动重新分析、云端缓存或 AI 分类复核不得覆盖有效的人工裁决。
   - 只有用户主动取消或恢复人工裁决，才回退到下一层有效结论。

当前有效分类不是在查询时临时猜测出来的多个布尔值，而应由统一裁决解析器计算并记录其来源：

```text
EffectiveClassification
EffectiveClassificationSource = manual | ai_review | xml_analysis | dll_analysis | fallback
EffectiveClassificationRecordId
```

分析输入或条目身份变化时，旧 AI/人工记录是否仍有效必须依据稳定条目身份和证据指纹判断。源条目已经变化或消失时，旧记录进入历史，不得继续覆盖新条目；仅仅重新运行分析但输入和结果指纹未变时，不影响高优先级有效结论。

## 3. 工作流总览

```text
选中的多个 Mod
      │
      ├─ 分析按钮 ─┬─ XML 分析（始终调用）
      │             └─ DLL 分析（仅开启 DLL 分析时调用）
      │
      ├─ 试跑 ───────── 读取已有有效分析结果，估算 Token
      │
      ├─ AI 分类复核 ─── 读取已有有效分析结果，更新分类状态
      │
      ├─ AI 翻译 ─────── 读取当前“待翻译”条目，生成并保存译文
      │
      └─ 一键翻译 ────── 显式编排步骤 1、2、4、5
```

分析结果是后续步骤可读取的数据，不代表后续步骤必须紧接着执行。单独点击试跑、AI 分类复核或 AI 翻译时，不得反向触发分析；只有用户点击明确标注的编排入口时，编排器才可以按约定调用多个步骤。

### 3.1 独立入口

五个步骤都保留自己的职责和结果。其中分析、试跑、AI 分类复核和 AI 翻译具有独立用户入口；XML 与 DLL 分析通过同一个“分析”按钮调度，但仍是两个独立分析器。

独立入口便于用户采用以下工作方式：

```text
选择 10 个 Mod → 分析 → 查看结果 → 稍后 AI 分类复核 → 再决定是否翻译
```

### 3.2 一键翻译编排

项目继续保留“一键翻译”。它不是新的分析器或翻译器，而是显式工作流编排器：

```text
步骤 1：XML 分析 ─┐
                  ├─ 并行完成 → 步骤 4：AI 分类复核 → 步骤 5：AI 翻译
步骤 2：DLL 分析 ─┘
（仅 DLL 分析开启时调用）
```

一键翻译不调用步骤 3。步骤 3 只负责 Token 和成本预估；用户点击一键翻译已经决定执行翻译，没有必要为了展示预估再阻塞正式流程。

一键翻译的约束：

- 分析器默认使用 `forceAnalyze = false`，有效结果直接复用，只补缺失或失效数据。
- DLL 分析关闭时只调用 XML 分析器。
- XML 与 DLL 分析仍按第 7 节并行，且分别保存结果。
- 分析结束后，AI 分类复核只处理其配置范围，默认处理“待确定”。
- AI 翻译仍只处理最终分类为“待翻译”的条目；“用户决定翻译”表示用户决定执行整套翻译工作流，不表示强制翻译被分类为“不翻译”的结构性内容。
- 每一步即使由一键编排器调用，也必须保存自己的结果、历史和错误，不得只保存最终译文。
- 用户仍可跳过一键入口，分别执行任一步骤。

## 4. 步骤一：XML 分析

### 4.1 职责

XML 分析器负责：

- 解析选中 Mod 当前有效的 Keyed、DefInjected 和 Def 来源；
- 生成稳定候选条目；
- 使用确定性本地规则输出“待翻译、不翻译、待确定”；
- 按 Mod 持久保存条目、证据、理由和汇总；
- 管理自己的分析器版本、输入指纹和结果指纹。

XML 分析器不负责：

- DLL 扫描；
- Token 试跑；
- 调用 AI 分类复核；
- 生成译文；
- 判断 DLL 功能是否开启。

### 4.2 执行入口

XML 分析不再假定为游戏启动时自动执行。当前确认的入口是用户在 Mod 列表中选择一个或多个 Mod 后点击统一的“分析”按钮。

将来如果增加启动后台补全，也必须调用同一个 XML 分析器接口，并遵守相同的复用与持久化规则，不能另建一套结果。

## 5. 步骤二：DLL 分析

### 5.1 职责

DLL 分析器负责：

- 扫描选中且满足条件的 Mod 程序集；
- 召回可能面向玩家的字符串；
- 运行静态 IL 数据流和本地规则分析；
- 输出“待翻译、不翻译、待确定”；
- 按 Mod 持久保存候选、证据、诊断和汇总；
- 管理自己的分析器版本、输入指纹和结果指纹。

DLL 分析器不负责 XML、试跑、AI 分类复核或翻译。

### 5.2 开关与 UI 拦截

- DLL 分析是需要用户开启的功能，默认关闭。
- DLL 分析与运行时 UI 拦截保持互斥，避免两套硬编码 UI 翻译机制同时作用而发生冲突。
- UI 拦截保留其“捕获后自动调用 AI 翻译”的兼容链路，但该链路属于 `ui_interception` 域，不得写入或覆盖标准 DLL 静态分析结果。

## 6. 共用分析按钮与强制分析

### 6.1 按钮层职责

界面提供一个共用入口：

```text
[ 分析选中的 N 个 Mod ]   ☐ 强制分析
```

按钮层只负责：

1. 获取选中的 Mod 快照；
2. 读取 `forceAnalyze` 布尔参数；
3. 始终调用 XML 分析器；
4. DLL 分析开启时，同时调用 DLL 分析器；
5. 汇总两个独立流程的进度和结果。

按钮层不得判断具体结果是否可复用，也不得直接删除 XML 或 DLL 数据。

### 6.2 分析器接口语义

概念接口：

```csharp
AnalyzeAsync(IReadOnlyList<ModAnalysisTarget> targets, bool forceAnalyze, CancellationToken cancellationToken)
```

每个分析器自行解释 `forceAnalyze`：

- `false`：逐 Mod 检查自己的分析器版本和完整输入指纹；结果有效则复用，只补缺失或失效的数据。
- `true`：不复用被选中 Mod 在该分析器域内的现有结果，重新分析并以新结果替换。

未开启 DLL 分析时，调度器根本不调用 DLL 分析器，因此 `forceAnalyze` 不会影响既有 DLL 结果。

### 6.3 分析复用条件

XML 和 DLL 分别拥有独立版本：

```text
XmlAnalyzerVersion
DllAnalyzerVersion
```

一个 Mod 的某类分析结果只有同时满足以下条件才能复用：

```text
分析器版本相同
+ 完整分析输入指纹相同
+ 结果记录完整且可读取
= 直接复用
```

完整输入指纹至少覆盖：

- Package ID；
- RimWorld 版本；
- Mod 当前有效内容根目录；
- `LoadFolders.xml` 选择结果；
- 当前分析域涉及的源文件路径、长度、时间或内容哈希；
- 会影响规则结果的分析选项；
- XML 域的 XML/Defs 内容，或 DLL 域的程序集 SHA-256、MVID 等身份。

每次结果还需保存结果指纹，用于判断重新分析后哪些条目实际发生变化。

### 6.4 强制分析的保存安全

“删除旧结果并重新分析”是逻辑语义。实现上应优先使用事务或临时结果原子替换：新结果完整生成后再替换旧结果，避免异常、取消或游戏退出造成整批数据丢失。

无论使用哪种物理实现，强制分析都不得读取旧结果作为本次分析结论。

## 7. XML 与 DLL 并行调度

DLL 分析开启时，XML 与 DLL 顶层任务并行执行：

```text
XML Analyzer Task ── XML Mod 1 → Mod 2 → Mod 3 → ...

DLL Analyzer Task ── DLL Mod 1 → Mod 2 → Mod 3 → ...
```

已确认的并行边界：

- XML 与 DLL 两个分析器同时进行；
- 每个分析器内部对选中的 Mod 串行处理；
- 两个分析器业务上互不依赖；
- 一个分析器失败不阻止另一个分析器继续；
- 用户主动取消时，统一向两个任务发送取消信号；
- 两个任务完成后生成统一汇总，但结果仍分别保存。

后台执行前，应在主线程建立不可变的 Mod 分析目标快照。后台线程只读取快照和文件，不直接修改游戏 UI 或变化中的 RimWorld 集合。

如果采用单一本地数据库，两个分析器可以并行计算，但数据库提交应使用短事务或统一写入队列，避免长期写锁。

分析进度条如何同时表达 XML 与 DLL 两条进度尚未确认，列入第 15 节待决事项，不阻塞数据和调度架构设计。

## 8. 步骤三：试跑

### 8.1 职责与输入

试跑作为独立入口，只读取选中 Mod 当前已有且有效的 XML/DLL 分析结果。它不得：

- 启动 XML 分析；
- 启动 DLL 分析；
- 调用 AI 分类复核；
- 调用翻译 API；
- 修改条目的分类或翻译状态。

如果某个选中 Mod 缺少分析数据，报告应明确显示缺少 XML 或 DLL 数据，而不是静默补跑。

### 8.2 估算内容

试跑至少输出两类估算：

1. 当前“待确定”条目执行 AI 分类复核的预计 Token 用量。
2. 当前“待翻译”条目加上“待确定”条目按比例折算后的 AI 翻译预计 Token 用量。

翻译估算范围：

```text
预计翻译范围 = 待翻译条目 + 待确定条目 × s%
```

`s` 是待确定条目最终被判定为待翻译的预测比例，具体数值和用户是否可配置尚待确认。

### 8.3 输出与保存

- 每个 Mod 独立保存本次估算、使用的分析结果指纹、估算参数和时间。
- 多 Mod 任务额外生成汇总报告。
- 后续重新试跑产生新批次，不覆盖历史批次；界面可标记最新结果。
- 分析结果变化后，旧试跑报告保留为历史，但标记其依据已过期。

## 9. 步骤四：AI 分类复核

“AI 分类复核”是当前建议名称，按钮可简称“AI 复核”；最终文案仍待确认。

### 9.1 职责

AI 分类复核读取现有分析证据，对用户选定范围内的条目重新判断并输出：

- 待翻译；
- 不翻译；
- 待确定。

它只更新分类结果，不生成译文，也不修改翻译状态。

### 9.2 默认范围与可选范围

- “待确定”是必选范围，默认处理。
- 用户可以额外勾选“待翻译”，让 AI 再判断一次。
- 用户可以额外勾选“不翻译”，让 AI 再判断一次。
- “待翻译”和“不翻译”默认均不勾选。

二次点击 AI 分类复核时，任务范围依据条目的当前有效分类，而不是第一次分析时的原始分类。例如第一次复核后只剩 10 条待确定，默认第二次只处理这 10 条。

### 9.3 判断依据

AI 判断使用：

- 最近一次有效的 XML 或 DLL 分析证据；
- 当前分类；
- 上一次 AI 分类结果与理由（如存在）；
- 必要且受限的条目上下文。

AI 分类复核不得为了获得这些材料而重新调用分析器。

### 9.4 历史、撤销和恢复

每次 AI 分类复核必须记录：

- 批次 ID；
- 条目 ID；
- 复核前分类；
- 复核后分类；
- 判断来源、模型、理由和时间；
- 使用的分析器版本和分析结果指纹。

用户可以撤销某次 AI 复核，或将条目恢复到复核前的有效分类。恢复是新增一条状态变更记录，不物理删除历史。

## 10. 步骤五：AI 翻译

### 10.1 职责与范围

AI 翻译只处理选中 Mod 当前分类为“待翻译”的条目。

它作为独立入口执行时不得：

- 自动启动 XML/DLL 分析；
- 自动执行试跑；
- 自动执行 AI 分类复核；
- 把“待确定”默认当作待翻译。

### 10.2 状态变化

翻译开始后：

```text
未翻译/失败 → 翻译中 → 已翻译或失败
```

成功条目保存目标语言、译文、来源文本指纹、模型/来源、校验结果和时间。最终译文继续输出为 RimWorld 可加载的 XML；DLL 定向翻译保存到其对应清单或运行时应用结构，不改写第三方 DLL。

分类状态不因翻译成功而变成“已翻译”。

## 11. 分析更新与下游结果失效

分析器版本和输入指纹均不变时，确定性分析结果必须视为不变并直接复用。

重新分析后的处理粒度是条目，而不是整个 Mod：

- 条目稳定身份和分析证据未变：保留 AI 分类复核历史和当前有效结论。
- 条目内容或分析证据变化：将旧 AI 结论标记为过期，当前分类回到新基础分析结果。
- 新增条目：使用新的基础分析分类。
- 消失条目：归档，不再进入当前任务范围。
- 试跑报告继续保留，但若依据的分析结果指纹不同则显示“历史/已过期”。
- 已翻译条目的源文本指纹变化：译文标记失效，翻译状态回到“未翻译”，旧译文保留为历史。

XML 分析器升级只影响 XML 域；DLL 分析器升级只影响 DLL 域。

## 12. 每个 Mod 的可见结果

Mod 列表至少能直接展示：

- XML 分析：未分析、有效、过期、分析中、失败；
- DLL 分析：未开启、未分析、有效、过期、分析中、失败；
- 分类数量：待翻译、不翻译、待确定；
- 翻译数量：未翻译、翻译中、已翻译、失败；
- 最新试跑时间与预计 Token；
- 最新 AI 分类复核时间及变更数量。

用户应能从单个 Mod 进入对应详情，不必先运行一次全局任务才能看到以前保存的结果。

## 13. 持久化架构

### 13.1 推荐方案

面对 500～1000 个 Mod、约 5～10 万甚至更多条目，推荐采用：

```text
轻量本地数据库：工作流状态、索引、历史和查询
XML/清单文件：RimWorld 实际加载、导出和分享的最终产物
```

数据库不替代最终翻译 XML，也不写入第三方 Mod。数据库属于用户本地工作状态。

SQLite 是当前首选方向，但正式采用前仍需确认 RimWorld 1.5/1.6 及 Windows、Linux、macOS 的驱动部署兼容性。业务层必须通过存储接口访问，不能直接散布特定驱动调用。

### 13.2 建议数据实体

| 实体 | 作用 |
|---|---|
| `Mods` | Package ID、名称、路径、游戏版本与当前内容身份 |
| `AnalysisRuns` | XML/DLL 分析批次、版本、输入/结果指纹、状态和错误 |
| `Candidates` | 稳定条目身份、来源域、源位置、源文本与上下文 |
| `AnalysisDecisions` | 分析器给出的基础分类、理由与证据 |
| `CurrentClassifications` | 条目当前有效分类及来源 |
| `ClassificationHistory` | AI/人工复核前后状态，用于审计、撤销和恢复 |
| `DryRunReports` | 试跑批次、参数、逐 Mod 估算和汇总 |
| `TranslationResults` | 目标语言、译文、翻译状态、校验和错误 |
| `WorkflowRuns` | 用户发起的分析、试跑、复核和翻译批次 |

关键索引至少覆盖：

```text
(packageId, sourceDomain)
(packageId, classificationStatus)
(packageId, targetLanguage, translationStatus)
(candidateId, analysisResultFingerprint)
(workflowRunId, packageId)
```

### 13.3 事务边界

- 每个 Mod 的一次分析结果以事务提交。
- 强制分析使用原子替换或版本切换。
- AI 分类复核每个批次完整记录历史后再更新当前状态。
- 翻译结果可以小批提交，避免长任务结束前全部只存在内存。
- XML 与 DLL 后台计算可以并行，公共数据库写入保持短事务。

## 14. 重构边界与建议顺序

建议按以下阶段重构：

1. 建立稳定条目身份、双维状态和存储接口。
2. 抽出独立 XML 分析器，停止由试跑、AI 复核和翻译临时生成分析结果。
3. 抽出独立 DLL 分析器，保留现有召回和 IL 分析能力。
4. 实现共用分析按钮、`forceAnalyze` 和两分析器并行调度。
5. 让 Mod 列表只从持久化状态读取摘要。
6. 将试跑改为纯读取与估算步骤。
7. 将 Agent 逻辑改为独立 AI 分类复核，并加入历史、撤销和恢复。
8. 将 AI 翻译限制为只读取当前“待翻译”条目。
9. 在独立步骤稳定后，用显式编排器重建“一键翻译”的 `1 → 2 → 4 → 5` 调用链。
10. 迁移旧 JSON/XML 缓存中仍可信的数据；无法证明身份一致的记录只归档，不自动提升为当前状态。
11. 最后再处理云端判断缓存、术语系统和旧 UI 拦截兼容链。

重构期间必须继续遵守：

- 不修改第三方 Mod 文件或 DLL；
- 最终翻译产物写入独立本地翻译包；
- Unity/RimWorld 对象修改留在主线程；
- 支持 RimWorld 1.5 与 1.6；
- 保留现有翻译复用、校验、热重载和错误诊断能力。

## 15. 尚待确认事项

以下事项尚未形成最终产品决策：

1. XML 与 DLL 并行时，界面使用双进度条、分段进度还是统一加权进度。
2. 试跑中 `待确定 × s%` 的默认比例、计算依据及是否允许用户配置。
3. “AI 分类复核”的最终用户名称和按钮短名称。
4. SQLite 具体驱动、数据库位置、跨平台原生库打包和旧缓存迁移方案。
5. 分析按钮是否需要“仅补缺失数据”的显式说明或详情提示。
6. AI 分类复核对“待翻译/不翻译”扩展范围的界面位置与批量确认方式。

这些待决事项不得阻止已确认的职责边界、数据模型和独立入口重构，也不得在实现时由开发者自行默认为产品决策。
