## 2026-10-12 DLL 显示注入与译文复用补充

本补充取代本文件中允许仅凭 UI 观察唯一匹配提升用途冲突条目的描述，以及旧的字符串读取点注入方式。UI 采集和大型 DLL 分析开销暂缓处理。

- 静态分析发现 UI 与程序用途冲突，或已明确判定非 UI 用途时，运行观察不能覆盖该反证。DLL 分析版本升级为 `dll-3.08`，旧本地分析重新计算；运行应用仍独立检查显示参数位置，AI 或人工分类不能绕过位置检查。
- 在原 Mod 的方法内，仅对能可靠定位的显示调用的字符串参数查询译文。保留原变量、查表键、比较值与其他参数。当前支持直线 IL 中的常值与局部变量传播；分支汇合、地址传递、未知流向、字段及非 string 参数不推测注入，记录未应用原因。
- 去掉共享清单 10,000 条和 32 MiB 总容量硬上限。单轮重载按程序集复用 SHA-256、按方法复用解析、指令和 IL 指纹；先读取和准备新清单，再撤换旧补丁。新应用失败尝试恢复上次成功清单，恢复异常明确报告。
- 译文复用按原文语种判断，采用下表已确认的门槛。字符按 Unicode 完整文本元素计数，包含标点和空白；词按连续空白切分非空项，包含空格、制表符和换行。没有术语、完整句子等例外；相同原文按原始内容精确匹配，目标语种必须相同。
- 复用查询可使用更新后位置改变而保留的历史候选，要求译文仍匹配原文哈希、有效且无未完成文件操作；按来源优先级和更新时间选择。在新位置生成输出，保留来源及模型元数据，不搬用旧位置补丁。当前页相同长原文只请求一份，成功后分别保存到各候选的位置。
- 待写文件操作保存复用来源快照，数据库迁移至 20，并增加原文哈希索引；重启恢复沿用同一入库事务恢复来源快照。现有译文和各语种记录保留。

**已确认的语种识别：** 优先使用 `ContextJson.sourceLanguage` 或 `source_language`。没有原文语种（包括 context 无法读取）时允许按字形识别：含假名及可伴随的汉字按日文；含汉字且无假名、韩文及其他语言字母按中文；泰文字形按泰文；拉丁、西里尔、韩文、阿拉伯及希伯来字形按空白分词规则。无可识别文字、未支持的显式语种或不能归入同一规则的混合文字不跨位置复用。不使用目标语言推断原文语言。纯汉字日文按中文门槛处理，这是本次允许字形识别的边界。

已确认并接入源码的门槛（产品规则，不是语言学等义换算）：

| 原文语言 | 计数方式 | 不复用 | 允许复用 |
|---|---|---|---|
| 中文简繁 | 字符，包含标点和空白 | ≤3 字符 | >3 字符 |
| 英、法、德、西、葡、意等空格分词语言 | 连续空白切分后的非空项 | ≤3 词 | >3 词 |
| 俄、乌等西里尔文字语言 | 同上 | ≤3 词 | >3 词 |
| 韩语 | 同上 | ≤3 词 | >3 词 |
| 阿拉伯语、希伯来语 | 同上 | ≤3 词 | >3 词 |
| 日语 | 字符，包含标点和空白 | ≤6 字符 | >6 字符 |
| 泰语 | 字符，包含标点和空白 | ≤8 字符 | >8 字符 |

### 2026-10-06 补充：Mod 名录与原生译文收集

- 每次游戏进程首次打开本 Mod 页面时弹出 Mod 列表同步窗。后台读取已安装 Mod 和启用状态，更新名录；同一进程再次打开不重复弹窗。展示准备动画、实际进度，在已有处理样本后估算剩余时间；结束报告列表是否未变、新启用、禁用、安装新增及移除数量。首次建表报告与后续变更报告区分。
- 复用 `Mods`、`ModInstallations`、版本快照和 XML/DLL 分析结果；新增按来源 Mod 与目标语种关联的 `NativeTranslationScans`、`NativeTranslationEntries`。安装移除或禁用保留历史记录，不删除用户译文和分析成果。

- 按目标语种、Keyed/DefInjected 类型、Def 类型与条目键进行对应，不使用 Mod 名称中的语言或“汉化”字样推测翻译包关系。匹配后在候选译文记录中保存提供方 Mod、来源文件和条目键。延续手工、第三方、Mod 原生、云端、AI 的来源优先级；同级来源按实际加载顺序后者覆盖。
- 当前语种文件中存在的非空对应条目作为已有原生/第三方译文，不能因为英语残留或质量启发式判断再次送翻。已有条目与原文哈希相符时跳过 AI；原文哈希变化按新内容处理。DLL 单独分析也更新已有 XML 候选的原生译文状态；纯 DLL 字符串缺少原生语言条目键时不以文本相似度猜测对应关系。
- 原生译文收集不包含批量替换；参考字典按 2026-10-07 补充实施。


新版翻译功能采用工作流模式。分析、估算、判断和翻译是可以独立执行、独立保存、独立查看的步骤；同时允许“一键翻译”等编排入口明确组合多个步骤。

核心原则：

1. 每一步都有自己的明确输入、输出、持久化结果和用户入口。
2. 单独步骤入口不得暗中触发其他步骤；编排入口可以明确声明并调用多个步骤。
3. 多个步骤可以读取同一份已有数据，但读取不等于调用数据生产步骤。
4. 每个 Mod 都能独立展示 XML 分析、DLL 分析、试跑、AI 分类复核和翻译状态。
5. 多选 Mod 只是建立一次批量任务；每个 Mod 的结果仍独立保存。
6. 当前代码中的隐式连锁需要改造成职责明确的编排调用；一键能力本身继续保留。

### 1.1 步骤入口与启动器契约

所有步骤采用同一条职责边界：启动器只传入用户选择范围、取消令牌，以及确有需要的本次临时覆盖参数；不得从外部传入已经查询／过滤／分类完成的候选条目集合，也不得逐次传入目标语言等持久设置。分析步骤接收当前 Mod 元数据以建立文件快照；试跑按钮冻结稳定 `mod_identity` 列表，试跑编排器与 AI 子能力只传该身份列表、`isSimulation` 和执行选项。

固定设置（例如 DLL 分析是否启用、AI 复核范围、试跑待确定比例）由步骤从 `WorkflowSettings` 读取。本次临时范围或特殊任务差异使用明确的 `WorkflowExecutionOptions` 覆盖，覆盖值只对本次运行有效，不反写持久设置。目标语言沿用核心 Mod 的持久设置，由步骤读取，启动器不逐次传入。

分析步骤收到选中 Mod 后自行建立 Mod/文件快照；AI 复核自行按复核范围查询当前有效分类；AI 翻译自行查询当前有效分类和翻译状态。试跑只负责编排一次 AI 复核模拟和一次 AI 翻译模拟，不替这两个步骤预先准备候选数据。试跑编排器把冻结的稳定身份列表按原顺序交给两个子能力；步骤可以返回逐 Mod 汇总结果，但不得向上暴露或转移候选队列的裁定权。

这里区分两类参数：

1. **选择参数**：仅为本次选中的 Mod 列表，确定任务允许涉及哪些 Mod，不直接确定条目。
2. **运行策略参数**：例如强制分析、模拟调用或明确的临时范围覆盖，只描述本次如何运行；步骤仍须根据该策略自行查询数据库并形成条目队列。

候选条目列表、数据库查询结果、当前有效分类、翻译状态和已经计算好的 Mod 身份都不是步骤入口参数。这样启动器只负责“何时调用哪个步骤”，步骤负责“本步骤实际处理什么数据”。

唯一例外是译文编辑器中由用户明确选择的单条／多条定向 AI 翻译：入口可以提交稳定候选 ID 集合作为本次选择范围，但不得提交候选正文、当前分类或查询结果。AI 翻译服务仍须按当前 Mod、目标语言、候选有效性和稳定 ID 在数据库中重新查询，并只处理重新核验后仍符合条件的条目。普通 Mod 级 AI 翻译、试跑和一键编排仍只接收 Mod 范围，不接受候选列表。

统一入口形态固定为：

```text
Execute(selectedMods, runOptions?, cancellationToken)
  ├─ 解析 selectedMods 的稳定身份
  ├─ 读取本步骤持久设置
  ├─ 查询数据库并锁定本步骤范围
  ├─ 执行／模拟执行
  ├─ 保存逐 Mod 结果
  └─ 返回本次汇总
```

其中 `runOptions` 只表达本次任务的临时差异，例如强制分析、模拟调用、临时 AI 复核范围或临时待判定抽样比例；普通 UI 设置必须先保存到 `WorkflowSettings`，不得每次由按钮重新拼装并传入。

每个步骤都按同一种内部模板实现，但不要求共用同一个候选队列：

| 阶段 | 步骤自身职责 |
|---|---|
| 选择归一化 | 把 `selectedMods` 解析为稳定 Mod 身份，并检查重复安装实例 |
| 设置解析 | 读取数据库中的固定设置，再叠加本次临时策略；临时策略不落库 |
| 范围查询 | 根据本步骤规则查询当前数据库，自行形成候选队列 |
| 执行 | 串行处理选中 Mod，并在步骤内部按文件／上下文拆批；组合分析入口按 XML → DLL 串行调度 |
| 持久化 | 保存逐 Mod 结果、运行记录、错误和本步骤产生的当前数据 |
| 汇总返回 | 只返回计数、耗量、跳过原因和错误摘要，不把候选队列交给启动器继续裁决 |

XML 与 DLL 尤其不能由“分析”按钮预先构造同一批 `ModAnalysisTarget` 再下发。它们各自是完整步骤，各自接收原始 `selectedMods` 和 `forceAnalysis`，各自建立快照、检查自己的分析器版本与输入指纹、决定跳过或重算并保存结果；“分析”按钮只读取 DLL 功能开关，先完整调用 XML 步骤，开启 DLL 时再调用 DLL 步骤。这样同一个步骤无论从独立入口还是一键入口启动，范围判断都只有一套实现。

## 2. 统一术语与双维状态

### 2.1 条目来源域

每个候选条目必须明确属于以下一个来源域：

- `xml`：Keyed、DefInjected 或从 Def 中提取的 XML 候选。
- `dll`：由程序集字符串召回和静态 IL 分析得到的硬编码 UI 候选。
- `ui_interception`：运行时 UI 采集探针产生的观察证据。它不再独立执行翻译，也不建立另一套候选；能够映射的证据并入 `dll` 分析裁决，不能唯一映射的记录保留为诊断。

XML 与 DLL 可以共用上层接口和查询模型，但不得共用会互相覆盖的结果记录。

### 2.2 分类状态

分类状态回答“这个条目应不应该翻译”：

| 状态 | 含义 |
|---|---|
| 需要翻译 | 现有有效判断认为应进入翻译范围；不表示当前尚无译文 |
| 无需翻译 | 现有有效判断认为属于结构、标识、路径、数值或其他不应翻译内容 |
| 待判定 | 现有证据不足，暂时不能确定 |

分类名称统一使用“需要翻译、无需翻译、待判定”。“需要翻译”描述的是翻译必要性；是否已经存在有效译文由独立的翻译状态表示。

### 2.3 翻译状态

翻译状态回答“翻译执行到哪里”：

| 状态 | 含义 |
|---|---|
| 未翻译 | 尚无当前目标语言的有效译文 |
| 翻译中 | 已进入正在执行的翻译批次 |
| 已翻译 | 已产生并保存通过校验的译文 |
| 失败 | 本次翻译失败，保留失败原因并允许重试 |

“已翻译”不是第四种分类。分类状态与翻译状态必须分别存储、分别筛选。

示例：一个条目可以同时是“需要翻译 + 已翻译”；这表示它属于需要翻译的内容，并且当前已有有效译文。源文本或译文失效后，翻译状态可回到“未翻译”，分类状态不必随之改变。

### 2.4 单一裁决与分类优先级

“步骤独立”不表示 XML 分析、DLL 分析、AI 和人工各自维护一套互相竞争的最终状态。每个条目只保存四个来源各自的当前结果，任何时刻按固定优先级解析出一个“当前有效分类”。本轮重构不保存逐次分类历史。

优先级从高到低为：

```text
手动标记
   ↓
当前有效的 AI 分类复核
   ↓
当前有效的 DLL 基础分析结果
   ↓
当前有效的 XML 基础分析结果
   ↓
没有有效结果：待判定
```

各层职责：

1. **基础分析层**
   - 由条目所属来源域的 XML 或 DLL 分析器产生。
   - 保存当前确定性规则分类、分析器版本和分析输入指纹。
   - XML 与 DLL 使用不同的稳定条目身份命名空间，正常情况下不会落在同一个条目；若未来确实出现同一条目同时具有两个结果，DLL 位优先于 XML 位。
2. **AI 分类复核层**
   - 保存 AI 对基础分析结果的当前判断、复核器版本和输入指纹。
   - 只要结论仍然有效，就覆盖该条目的基础分析分类。
   - 新复核直接替换当前 AI 位；撤销 AI 结果时清空 AI 位，并自动回落到 DLL/XML 当前结果。
3. **手动标记层**
   - 用户主动修改的分类优先级最高。
   - 自动重新分析或 AI 分类复核不得覆盖有效的人工裁决。
   - 取消手动分类时清空手动位，自动回落到 AI、DLL 或 XML 当前结果。

当前有效分类由统一位图解析器从最高优先级向最低优先级读取第一个非零状态，同时返回分类来源：

```text
EffectiveClassification
EffectiveClassificationSource = manual | ai_review | xml_analysis | dll_analysis | fallback
```

XML、DLL 本地分析结果是否仍有效依据稳定条目身份、生产者版本和输入指纹判断；对应结果失效时只更新本地来源位及其版本/指纹字段。AI 复核采用显式清除语义：只要稳定条目仍保存非零 AI 位，就始终复用并跳过后续 AI 复核，不因原文、上下文、分析器版本、复核器版本或提示词版本变化自动失效；需要重新复核时，由用户在译文编辑页清除当前 Mod 的 AI 复核结果。手动分类同样绑定稳定条目身份：同一个逻辑条目即使原文变化仍保留手动分类；条目的逻辑定位发生变化、生成新的 `candidateId` 时不继承高层分类。手动译文与手动分类是两回事，原文变化时手动译文仍会失效并回到“未翻译”。

### 2.5 当前分类的 8 位位图

每个条目使用一个 `0～255` 的整数 `classificationFlags` 保存四个来源的当前分类。每个来源占 2 个二进制位：

| 2 位值 | 数值 | 含义 |
|---|---:|---|
| `00` | 0 | 未分析或该来源当前无结果，不参与裁决 |
| `01` | 1 | 待判定 |
| `10` | 2 | 需要翻译 |
| `11` | 3 | 无需翻译 |

位布局固定为：

```text
[手动分类][AI 复核][DLL 分析][XML 分析]
   7..6      5..4      3..2      1..0
```

对应偏移量：

```text
XML_SHIFT    = 0
DLL_SHIFT    = 2
AI_SHIFT     = 4
MANUAL_SHIFT = 6
```

解析当前有效分类时按 `手动 → AI → DLL → XML` 读取第一个非 `00` 的来源；四段均为 `00` 时返回系统回退值“待判定”，来源记为 `fallback`。这里的 `00` 是“没有该来源结果”，而 `01` 是该来源明确给出的“待判定”，两者不得混淆。

统一解析器的实现等价于：

```csharp
EffectiveClassification Resolve(byte flags)
{
    int manual = (flags >> 6) & 0b11;
    if (manual != 0) return From(manual, Manual);

    int ai = (flags >> 4) & 0b11;
    if (ai != 0) return From(ai, AIReview);

    int dll = (flags >> 2) & 0b11;
    if (dll != 0) return From(dll, DllAnalysis);

    int xml = flags & 0b11;
    if (xml != 0) return From(xml, XmlAnalysis);

    return From(Undetermined, Fallback);
}
```

所有列表、统计、试跑、AI 复核和 AI 翻译必须调用同一个 `ClassificationFlagsCodec`，不得复制一套页面专用优先级。正常规模约 5～10 万条时，读取一个整数并执行四次移位/掩码足够轻量，先不冗余保存 `effectiveClassification`。如果以后真实性能数据证明数据库侧按有效分类聚合成为瓶颈，再增加同一行内的缓存列，并由位图更新事务同步刷新，不能预先引入两套可能不一致的权威数据。

设置某一来源只替换对应 2 位：

```text
flags = (flags & ~(0b11 << shift)) | (newValue << shift)
```

清除某一来源则将对应 2 位归零：

```text
flags = flags & ~(0b11 << shift)
```

因此：

- 撤销手动分类：清空手动位，自动回落到 AI/DLL/XML；
- 撤销 AI 复核：清空 AI 位，自动回落到 DLL/XML；
- 还原到本地分析：同时清空手动位和 AI 位；
- 本轮不支持恢复“上一次 AI 结果”或“上一次手动结果”，只支持清除高层当前结果并回落。

当前分类字段直接放在稳定条目记录上，不再建立分类历史表。至少保存：

| 字段 | 中文说明 |
|---|---|
| `classificationFlags` | 四来源 8 位分类标识 |
| `xmlAnalyzerVersion` | 当前 XML 位对应的分析器版本；XML 位为 `00` 时为空 |
| `xmlAnalysisFingerprint` | 当前 XML 位对应的目标/输入指纹 |
| `dllAnalyzerVersion` | 当前 DLL 位对应的分析器版本；DLL 位为 `00` 时为空 |
| `dllAnalysisFingerprint` | 当前 DLL 位对应的程序集、目标和输入指纹 |
| `aiReviewVersion` | 当前 AI 位对应的复核器/提示词版本；AI 位为 `00` 时为空 |
| `aiReviewFingerprint` | 当前 AI 位对应的条目、上下文和提示词输入指纹 |
| `xmlReasonCode` | 当前 XML 位对应的规则原因码；XML 位为 `00` 时为空 |
| `dllReasonCode` | 当前 DLL 位对应的规则原因码；DLL 位为 `00` 时为空 |
| `aiReviewReason` | 当前 AI 位对应的受限长度理由；AI 位为 `00` 时为空 |
| `manualUpdatedAt` | 最近一次手动分类时间；手动位为 `00` 时可为空 |
| `classificationUpdatedAt` | 任意来源当前分类最后更新时间 |

分析器版本号不能替代输入指纹：版本未变但目标 Mod、文件或源文本发生变化时，旧结果仍然必须失效。用户手动编辑译文时，手动分类位设置为“需要翻译”，翻译状态设置为“已翻译”，译文来源设置为“手动”；删除译文只清除译文记录并将翻译状态改为“未翻译”，不自动撤销手动分类。

### 2.6 稳定条目 ID 的固定规范

`candidateId` 标识“这个逻辑位置上的条目”，不标识“这一版原文内容”。因此 ID 计算**明确排除**：

- 原文和译文；
- 原文、译文及文件内容哈希；
- Mod 版本号和版本快照 ID；
- 文件绝对路径、盘符、Workshop 目录号；
- 文件修改时间、文件大小、XML 行号；
- DLL 的 MVID、编译时间和易变化的 metadata token/IL offset。

这些可变信息进入原文哈希、译文哈希、分析输入指纹、`contentFingerprint` 或版本快照，用于判断是否需要完整重分析和译文失效，不能混入稳定 ID。

ID 规范版本固定为 `atc-candidate-v1`。参与计算的字段先按以下规则规范化，再按 UTF-8、无 BOM、带字段名与字段值字节长度的确定性二进制格式序列化，最后计算完整 SHA-256：

```text
candidateId = "atc1_" + lowercase_hex(
    SHA256(
        version="atc-candidate-v1",
        modIdentity,
        sourceDomain,
        entryKind,
        logicalLocator
    )
)
```

不得截断 SHA-256。数据库同时保存 `identitySchemaVersion` 和可读的 `entryIdentity`，用于诊断和未来迁移；不得使用自增数字或数组序号代替数据库中的稳定条目 ID。大模型批次协议不发送该持久 ID，只使用从 0 开始的批次内短序号；短序号只映射本次内存批次，不持久化、不导出，也不参与条目身份计算。

通用规范化规则：

1. Package ID 去首尾空白并使用 invariant lowercase；不进行语言相关大小写转换。
2. XML 名称、键、DefName 和字段路径保持语义大小写，统一为 Unicode NFC；只去除规范明确允许的外围空白。
3. XML 路径分隔符统一为 `/`，但文件路径不进入 Keyed/DefInjected 的逻辑定位。
4. DLL 程序集逻辑名不含版本、公钥标记和扩展名；类型名使用完整命名空间；方法签名包含方法名、泛型元数、参数类型与返回类型。
5. 每个字段带字段名和字节长度，禁止依靠简单拼接分隔符消除歧义。

各来源的 `logicalLocator` 固定为：

| 条目类型 | 稳定逻辑定位 |
|---|---|
| XML Keyed | `key=<规范化语言键>` |
| XML DefInjected | `defType=<类型>;defName=<DefName>;fieldPath=<字段路径>` |
| XML Def 可翻译字段 | `defType=<类型>;defName=<DefName>;fieldPath=<字段路径>` |
| DLL 字符串调用点 | `assembly=<Mod 内程序集相对路径（无扩展名）>;type=<完整类型名>;method=<规范签名>;callSite=<规范调用点序号>` |

DLL 的 `callSite` 不是原始 IL offset，而是对目标方法执行固定的规范遍历后，只对可翻译字符串使用点编号：按方法体规范 IL 指令顺序遍历，对召回后保留的字符串从 `0` 开始重新编号。原始 `ldstr` 整数序号只用于恢复这一相对顺序，不直接进入新候选 ID。分析器版本升级若改变召回规则只需使分析结果失效；若改变稳定定位字段或规范遍历算法，则必须提升 `identitySchemaVersion` 并执行显式 ID 迁移，不能静默重算。相同方法中新插入更靠前且同样被召回的字符串可能使后续 ID 改变；这是无源码稳定符号情况下的确定性边界，变更后的条目按新条目处理，不继承手动分类或译文。

分析器内部的方法图不得把 Cecil `MethodDefinition.FullName` 当作唯一身份；合法泛型重载可能产生相同 FullName。程序集内部依赖图、摘要传播和调用解析使用 `Module MVID + MetadataToken`，FullName 仅用于显示和无法解析引用时的保守回退。基础库也不通过 Package ID 或 DLL 文件名黑名单直接归零：被扫描到的字符串继续沿通用 UI／非 UI sink 证据分类，只有确证为反射键、日志、资源路径、比较键等用途时判为无需翻译，真实玩家界面文本仍须保留。

程序集定位必须使用 Mod 根目录内的规范相对路径并去掉扩展名，路径分隔符统一为 `/`；不能只取文件名，也不能使用机器绝对路径。这样既避免不同子目录同名程序集发生候选 ID 碰撞，也保证跨安装目录身份稳定。

`modIdentity` 的生成规则固定为：

- 有合法 Package ID：`pkg:<normalizedPackageId>`；
- 没有 Package ID：`local:<SHA256(规范化作者 + 名称 + Mod 根目录文件夹名)>`，同时显示“缺少 Package ID，身份稳定性较弱”的诊断；
- 同一 Package ID 存在多个安装实例时，先由 RimWorld 当前实际启用实例确定 `activeRootPath`，候选 ID 仍只使用 `pkg:` 身份；若无法唯一确定启用实例，则阻止分析并提示冲突，不得把两个目录静默合并。

Mod 更新判断与条目 ID 分开：只要当前有效内容的 `contentFingerprint` 改变，就建立新版本快照，并把该 Mod 的 XML/DLL 本地结果标记失效后执行完整重分析；未开启 DLL 分析时只立即重建 XML，DLL 结果保持“过期”，待用户以后开启并分析。重分析后，逻辑定位未变的条目仍得到相同 `candidateId`，已有 AI 与手动分类保留；原文变化的译文全部失效为“未翻译”。逻辑定位消失或改变时，旧条目标记不存在，新条目不继承旧状态。

### 2.7 ID、文本哈希与任务指纹的分层

这三类值用途不同，禁止混称为“ID”：

| 层级 | 字段 | 回答的问题 | 是否随文本变化 |
|---|---|---|---|
| 逻辑身份 | `candidateId` | 这是不是同一个逻辑条目 | 否 |
| Mod 内容 | `contentFingerprint` | 这个 Mod 的有效输入文件集合是否变化 | 是 |
| 原文内容 | `sourceTextHash` | 当前原文是否变化 | 是 |
| 译文内容 | `translationHash` | 当前实际译文是否变化或被外部修改 | 是 |
| 译文绑定 | `sourceTextHashAtTranslation` | 这份当前译文生成/确认时对应的原文哈希 | 保存当时的 `sourceTextHash` 副本 |
| 任务有效性 | `xmlAnalysisFingerprint`、`dllAnalysisFingerprint`、`aiReviewFingerprint` | 某次分析/复核的完整输入是否仍一致 | 随对应任务输入变化 |

条目级不再保存含义宽泛的通用 `sourceFingerprint`。译文是否失效只比较：

```text
TranslationResults.sourceTextHashAtTranslation
    == Candidates.sourceTextHash
```

相等表示译文仍对应当前原文；不相等就清空译文状态。AI 复核是否仍有效则比较独立的 `aiReviewFingerprint`，因为它除了原文还受上下文、提示词版本、范围和调用链影响，不能只看原文。

原文和译文仍保存实际文本供显示、编辑和输出；数据库查询与同步不反复进行大字符串比较，而保存固定长度 SHA-256。文本哈希规范固定为：解析后的逻辑文本统一换行为 `\n`、Unicode 统一为 NFC、保留其他所有空格与首尾字符，然后以 UTF-8 无 BOM 计算完整 SHA-256。文件本身另有文件内容哈希，不能拿文件哈希代替某个条目的文本哈希。

## 3. 工作流总览

```text
选中的多个 Mod
      │
      ├─ 分析按钮 ─┬─ XML 分析（始终调用）
      │             └─ DLL 分析（仅开启 DLL 分析时调用）
      │
      ├─ 试跑 ───────── 模拟调用 AI 复核和 AI 翻译，估算 Token
      │
      ├─ AI 分类复核 ─── 读取已有有效分析结果，更新分类状态
      │
      ├─ AI 翻译 ─────── 读取当前“需要翻译”条目，生成并保存译文
      │
      └─ 一键翻译 ────── 显式编排步骤 1、2、4、5
```

分析结果是后续步骤可读取的数据，不代表后续步骤必须紧接着执行。单独点击试跑、AI 分类复核或 AI 翻译时，不得反向触发分析；只有用户点击明确标注的编排入口时，编排器才可以按约定调用多个步骤。

### 3.1 独立入口

五个步骤都保留自己的职责和结果。其中分析、试跑、AI 分类复核和 AI 翻译具有独立用户入口；XML 与 DLL 分析通过同一个“分析”按钮调度，但仍是两个独立分析器。

独立入口便于用户采用以下工作方式：

```text
选择 10 个 Mod → 分析 → 查看结果 → 稍后 AI 分类复核 → 再决定是否翻译
```

### 3.2 一键翻译编排

项目继续保留“一键翻译”。它不是新的分析器或翻译器，而是显式工作流编排器：

```text
步骤 1：XML 分析 → 步骤 2：DLL 分析 → 步骤 4：AI 分类复核 → 步骤 5：AI 翻译
（仅 DLL 分析开启时调用）
```

一键翻译不调用步骤 3。步骤 3 只负责 Token 和成本预估；用户点击一键翻译已经决定执行翻译，没有必要为了展示预估再阻塞正式流程。

一键翻译的约束：

- 用户点击一键翻译后先显示确认弹窗，明确告知将依次执行“分析、AI 复核、AI 翻译”三个用户可见阶段；分析说明必须根据强制分析和 DLL 开关准确提示是复用已有有效结果还是重新生成。强制分析开启时，弹窗标题和正文顶部都必须显著警告“强制分析已开启”，说明已有有效结果也会重做且耗时可能增加。AI 复核说明必须展示点击时勾选的具体分类范围。弹窗同时提示耗时和模型 Token 用量，并说明停止后已完成且已保存的结果仍会保留；只有用户明确确认后才取得任务租约并启动编排。弹窗展示的 Mod、强制分析选项、DLL 开关和 AI 复核范围均以点击时快照为准。
- 分析器默认使用 `forceAnalyze = false`，有效结果直接复用，只补缺失或失效数据。
- DLL 分析关闭时只调用 XML 分析器。
- XML 与 DLL 分析按第 7 节串行调度，仍分别判断范围并保存结果。
- 分析结束后，AI 分类复核只处理其配置范围，默认处理“待判定”。
- AI 翻译仍只处理最终分类为“需要翻译”的条目；“用户决定翻译”表示用户决定执行整套翻译工作流，不表示强制翻译被分类为“无需翻译”的结构性内容。
- 每一步即使由一键编排器调用，也必须保存自己的当前结果和错误，不得只保存最终译文；试跑与工作流运行报告可以保留批次历史，但分类只保存四个来源各自的当前值。
- 用户仍可跳过一键入口，分别执行任一步骤。

## 4. 步骤一：XML 分析

### 4.1 职责

XML 分析器负责：

- 解析选中 Mod 当前有效的 Keyed、DefInjected 和 Def 来源；
- 生成稳定候选条目；
- 使用确定性本地规则输出“需要翻译、无需翻译、待判定”；
- 按 Mod 持久保存条目、证据、理由和汇总；
- 管理自己的分析器版本、输入指纹和结果指纹。

XML 分析器不负责：

- DLL 扫描；
- Token 试跑；
- 调用 AI 分类复核；
- 生成译文；
- 判断 DLL 功能是否开启。

### 4.2 执行入口

XML 分析不再假定为游戏启动时自动执行。当前确认的入口是用户在 Mod 列表中选择一个或多个 Mod 后点击统一的“分析”按钮。

将来如果增加启动后台补全，也必须调用同一个 XML 分析器接口，并遵守相同的复用与持久化规则，不能另建一套结果。

## 5. 步骤二：DLL 分析

### 5.1 职责

DLL 分析器负责：

- 扫描选中且满足条件的 Mod 程序集；
- 召回可能面向玩家的字符串；
- 运行静态 IL 数据流和本地规则分析；
- 输出“需要翻译、无需翻译、待判定”；
- 按 Mod 持久保存候选、证据、诊断和汇总；
- 管理自己的分析器版本、输入指纹和结果指纹。

DLL 分析器不负责 XML、试跑、AI 分类复核或翻译。

### 5.2 开关与 UI 拦截

- DLL 分析是需要用户开启的功能，默认关闭。
- 2026-10-08 补充澄清：XML/DLL 文件分析与 UI 采集不互斥。分析不自动关闭采集；每个 DLL 分析目标用固定的采集键快照生成指纹和分类，期间新增观察留给下一次分析。本条仅澄清文件分析，不改变采集与运行时译文注入的关系。
- 运行时 UI 拦截改为临时采集探针：开启期间只记录实际显示过的 DLL 文本及其 Mod、程序集 MVID、方法签名和原文，不在 UI 渲染热路径调用 AI、读取旧 UI 译文或替换文本。
- 采集与 DLL 定向注入仍不同时运行。开始采集时暂停定向注入；采集手动或定时结束后恢复定向注入。后续复核、翻译和显示只依赖 DLL 工作流候选及定向注入，不依赖 UI 拦截持续开启。
- 采集证据按“Mod + 程序集 + 方法 + 原文字面量”匹配当前静态扫描结果。唯一命中时作为 DLL“需要翻译”的强证据；同一方法内重复字面量导致无法唯一定位时只标为“待判定”；统一 Policy 明确拒绝的路径、格式控制值等仍保持“无需翻译”。
- UI 渲染缓存不得以“同一原文已经处理过”为由跳过其他调用点。采集会话允许同一原文进行有限次数的调用栈取证，证据仍按完整复合身份去重；达到上限后停止继续抓栈，避免高频标签长期拖慢 UI。
- 观察证据进入 DLL 分析有效性指纹；新增证据后重新执行普通 DLL 分析即可重算，Mod 更新造成程序集 MVID 变化时旧证据不会误匹配。
- 2026-10-08 确认：UI 采集、Mod 来源匹配与候选归类作为一个整体共用流水线版本，当前为 `ui-1.01`，后续小改按小数递增；DLL 静态分析继续使用独立版本。每条观察记录保存流水线版本，未标版本的历史记录和不同版本记录保留但不参与当前归类，需重新采集。整体版本参与 DLL 分析有效性指纹，即使尚无新证据，升级后也不能复用旧流水线的分析缓存。此编号与 JSON 文件格式版本分开管理。
- UI 采集提供自动关闭设置，默认 5 分钟；可选 2～30 分钟，`0` 表示无限。倒计时从每次开启或修改时长时重新开始，到时只关闭采集、落盘证据并恢复定向注入，不清除已采集数据。
- 观察证据持久化必须串行写入并用变更版本保护脏标记；写盘期间出现的新观察不能被本次快照误判为已经保存。采集会话状态跨线程访问时必须互斥，后台自动流水线完成后的设置修改、证据落盘和补丁重载统一派发到主线程。

## 6. 共用分析按钮与强制分析

### 6.1 按钮层职责

界面提供一个共用入口：

```text
[ 分析选中的 N 个 Mod ]   ☐ 强制分析
```

按钮层只负责：

1. 获取选中的 Mod 快照；
2. 读取 `forceAnalyze` 布尔参数；
3. 始终调用 XML 分析器；
4. XML 分析完成后，DLL 分析开启时再调用 DLL 分析器；
5. 依次汇总两个独立流程的进度和结果。

按钮层不得判断具体结果是否可复用，也不得直接删除 XML 或 DLL 数据。

### 6.2 分析器接口语义

概念接口：

```csharp
AnalyzeAsync(IReadOnlyList<ModAnalysisTarget> targets, bool forceAnalyze, CancellationToken cancellationToken)
```

每个分析器自行解释 `forceAnalyze`：

- `false`：逐 Mod 检查自己的分析器版本和完整输入指纹；结果有效则复用，只补缺失或失效的数据。
- `true`：不复用被选中 Mod 在该分析器域内的现有结果，重新分析并以新结果替换。

未开启 DLL 分析时，调度器根本不调用 DLL 分析器，因此 `forceAnalyze` 不会影响既有 DLL 结果。

### 6.3 分析复用条件

XML 和 DLL 分别拥有独立版本：

```text
XmlAnalyzerVersion
DllAnalyzerVersion
```

一个 Mod 的某类分析结果只有同时满足以下条件才能复用：

```text
分析器版本相同
+ 完整分析输入指纹相同
+ 结果记录完整且可读取
= 直接复用
```

完整输入指纹至少覆盖：

- Package ID；
- RimWorld 版本；
- Mod 当前有效内容根目录；
- `LoadFolders.xml` 选择结果；
- 当前分析域涉及的源文件路径、长度、时间或内容哈希；
- 会影响规则结果的分析选项；
- XML 域的 XML/Defs 内容，或 DLL 域的程序集 SHA-256、MVID 等身份。

每次结果还需保存结果指纹，用于判断重新分析后哪些条目实际发生变化。

### 6.4 强制分析的保存安全

“删除旧结果并重新分析”是逻辑语义。实现上应优先使用事务或临时结果原子替换：新结果完整生成后再替换旧结果，避免异常、取消或游戏退出造成整批数据丢失。

无论使用哪种物理实现，强制分析都不得读取旧结果作为本次分析结论。

### 6.5 DLL 本地裁决边界

DLL 扫描继续以召回优先，本地裁决只能根据可解释的 IL 数据流证据分类：

- 字面量直接或经同程序集辅助方法返回后进入明确玩家 UI sink，可判为需要翻译；
- 字面量作为本地化键、格式参数、类型／字典查找键、序列化键、资源路径、Def 名称或日志内容使用，可判为无需翻译；
- 同时流向 UI 与非 UI、经过尚未建模的字段／复杂对象图／委托或无法解析的 IL，继续保留待复核。数组与常见泛型容器只做保守的局部来源传播，不能据此强猜界面语义。
- 静态字段可以保存数组、常见泛型容器或字符串来源；分析器在程序集范围内迭代传播这些来源。实例字段不按“字段名相同”跨对象合并，避免把不同对象的文本错误归为同一用途。

不得仅凭 Mod 名称、项目专属前缀、方法名包含 `Draw`，或字符串“看起来像英文”就自动判定。扩大本地裁决范围必须同时提升 `DllAnalyzerVersion`，使旧结果按现有版本规则过期；不得收窄候选召回集合来制造更好的分类比例。

## 7. XML 与 DLL 串行调度

DLL 分析开启时，组合入口固定先完成 XML，再执行 DLL：

```text
XML Analyzer ── XML Mod 1 → Mod 2 → Mod 3 → ...
       ↓ XML 步骤完成
DLL Analyzer ── DLL Mod 1 → Mod 2 → Mod 3 → ...
```

已确认的调度边界：

- XML 与 DLL 是互不依赖、可单独调用的两个完整步骤；
- 共用分析按钮与一键翻译中的组合入口按 XML → DLL 串行调用；
- 每个分析器内部对选中的 Mod 串行处理；
- XML 步骤失败或被取消时不继续启动本次 DLL 步骤；既有 DLL 结果不受影响；
- 用户主动取消时，当前步骤停止，尚未启动的 DLL 步骤不再启动；
- 两个步骤结果仍分别保存，按钮只展示当前正在执行的阶段和该步骤进度。

后台执行前，应在主线程建立不可变的 Mod 分析目标快照。后台线程只读取快照和文件，不直接修改游戏 UI 或变化中的 RimWorld 集合。

两个分析器各自在步骤内部建立自己的目标快照、检查缓存并使用短事务提交。串行只属于组合入口的调度策略，不合并两套分析职责，也不让 XML 步骤替 DLL 步骤准备候选范围。

## 8. 步骤三：试跑

### 8.1 职责与输入

试跑作为独立入口，只接收按钮触发时冻结的稳定 `mod_identity` 列表与本次执行选项。它依次调用真正的 AI 复核和 AI 翻译子能力并传入 `simulate = true`；两个步骤按身份顺序逐 Mod 查询，继续生成与正式执行相同的数据范围、稳定排序、跨文件批次和完整提示词，只在统一大模型调用层停止，不向外部模型发送请求。试跑编排器不得读取候选记录或维护平行估算算法。

AI 复核、AI 翻译和大模型调用方法统一接收：

```csharp
bool simulate = false
```

- `simulate = false`：真实调用大模型并处理返回内容。
- `simulate = true`：不发送网络请求，只返回输入、输出和合计 Token 估算。

模拟模式不得：

- 启动 XML 分析；
- 启动 DLL 分析；
- 向外部 AI/API 发送请求；
- 产生新的 AI 复核分类；
- 写入译文或改变翻译状态；
- 修改条目的分类或翻译状态。

模拟结果只写入独立试跑批次、逐 Mod 估算和汇总报告。若某个选中 Mod 缺少必要数据，报告应明确说明，不能静默补跑分析，也不能按 0 Token 混入汇总。

每条数据先按以下来源优先级解析出当前有效分类：

```text
手动标记 > 有效 AI 复核结果 > 有效 DLL 分析结果 > 有效 XML 分析结果 > 待判定
```

来源优先级只决定当前有效分类；“需要翻译、待判定、无需翻译”仍是分类值。得出当前有效分类后，再按用户当前设置的 AI 复核范围筛选本次复核任务。

### 8.2 估算内容

试跑输出两类互相独立的 Token 估算：

1. **AI 分类复核**：依据用户当前设置的复核范围，估算符合范围的全部条目进入 AI 分类复核时的输入 Token、输出 Token 和合计 Token。默认范围只有“待判定”；用户可以额外勾选“需要翻译”和“无需翻译”。是否已有 AI 复核当前结果不决定本次是否估算，当前有效分类和当前复核范围才决定。
2. **AI 翻译**：分别估算当前“需要翻译且没有有效译文”的条目，以及“待判定且没有有效译文”的条目按 50% 折算后可能进入翻译的 Token 用量。已有有效手动、第三方、Mod 原生、云端或 AI 翻译译文的条目不重复计入翻译消耗。

手动标记当前生效的条目，只要分类落入用户选择的 AI 复核范围，也参与复核和 Token 估算。正式复核可以保存新的 AI 建议，但这些建议不覆盖更高优先级的手动标记。

翻译估算范围：

```text
预计翻译范围 = 无有效译文的已判定需要翻译条目 + 无有效译文的待判定条目 × 50%
```

`s` 固定为 `50%`，表示试跑阶段预计有一半“待判定”条目会在 AI 分类复核后转为“需要翻译”。该比例只用于成本预估，不会修改分类状态或影响后续 AI 分类复核的真实结果；为了复用真实批次规划和提示词构造，AI 翻译子能力按稳定顺序确定本次模拟样本。

待确定折算按每个选中 Mod 的稳定候选顺序抽取 `ceil(待确定条目数 × 50%)`。抽中的条目与全部有效“需要翻译”条目合并成 AI 翻译步骤本轮自己的模拟队列，剩余待确定条目不进入调用；不得把两个来源拆成两次 AI 翻译模拟，也不得由试跑在步骤外拼接提示词。这样模拟调用和正式 AI 翻译走同一套查询、跨文件批次拆分和提示词构建路径。

```text
AI 翻译模拟队列
= 全部有效“需要翻译且未有有效译文”的条目
+ 每个 Mod 稳定抽取的 50%“待确定且未有有效译文”条目
```

各环节必须分别计算：

- **输入 Token**：系统提示、任务说明、结构化协议、条目正文和必要上下文；
- **输出 Token**：AI 分类结构化结果或目标语言译文的预计长度；
- **合计 Token**：该环节输入 Token与输出 Token之和。

Token 估算不要求每种模型都提供 tokenizer。统一兜底算法为：

```text
基础估算 Token
= ceil(汉字数量 / 3)
+ 英文单词数量
+ ceil(其他字符数量 / 4)
```

英文单词除按空格、换行、下划线和标点分隔外，还应拆分驼峰、连续缩写与普通单词边界、字母和数字边界。GUID、哈希、Base64、超长数字等不按一个单词处理，退回 `ceil(字符数 / 4)`。输入估算必须针对已经完成正式拼接的完整提示词或供应商请求载荷，而不是只计算源文本。

AI 复核输出按固定 JSON 结构、条目标识、固定分类枚举和受限理由长度估算。AI 翻译的译文正文按“译文与原文 Token 规模相近”估算，再加固定 JSON 结构开销：

```text
预计译文正文 Token = 对应原文的基础估算 Token
预计翻译输出 Token = 预计译文正文 Token + 固定 JSON 结构 Token
```

报告展示基础估算；硬性预算预留使用独立的 `1.2` 保护系数：

```text
预算保护 Token = ceil(基础估算 Token × 1.2)
```

保护值不得伪装成报告中的模型真实消耗。真实调用完成后，供应商若返回 usage，则账本保存真实输入、输出和合计 Token；没有 usage 时保留估算并明确标记。

所有数字均使用“预计”语义，界面使用 `约` 或 `≈` 标记，不得展示成精确计费结果。若能确定本次使用的供应商、模型和价格，可在 Token 估算下方附加预计费用；模型或价格无法确定时不显示虚假金额。

### 8.3 输出与保存

- 每个 Mod 独立保存本次估算、使用的分析结果指纹、估算参数和时间。
- 多 Mod 任务额外生成汇总报告。
- 后续重新试跑产生新批次，不覆盖历史批次；界面可标记最新结果。
- 分析结果变化后，旧试跑报告保留为历史，但标记其依据已过期。
- 汇总报告和逐 Mod 详情使用同一组字段，确保总览数字可以追溯到具体 Mod。
- 汇总时使用未格式化的原始整数求和，最后才进行千位分隔和近似显示，避免逐行四舍五入造成汇总偏差。
- 缺少有效分析结果的 Mod 显示“无法估算：缺少 XML/DLL 分析”，不得按 0 Token 计入。

### 8.4 建议报告文本与样式

报告主标题固定为“试跑估算结果”，不根据是否已有手动标记或 AI 复核历史切换标题。结果窗口顶部先展示范围和总量，再按“AI 复核”“AI 翻译”分成两个信息区块。AI 复核区按当前有效分类展示本次实际范围，并在每种分类下按最终生效的数据来源展开。推荐文本：

```text
试跑估算结果
已选择 10 个 Mod · 可估算 9 个 · 缺少分析 1 个

AI 复核
范围：待判定
预计复核：320 条

待判定：320 条
  手动标记：12 条
  既有 AI 复核：48 条
  DLL 分析：40 条
  XML 分析：220 条

预计输入 Token       ≈ 18,400
预计输出 Token       ≈  2,600
AI 复核小计          ≈ 21,000

AI 翻译
需要翻译且无有效译文 780 条
  预计输入 Token     ≈ 46,000
  预计输出 Token     ≈ 62,000

待判定且无有效译文折算（50%）
                       约 160 / 320 条
  预计输入 Token     ≈  9,100
  预计输出 Token     ≈ 12,400

AI 翻译小计          ≈ 129,500
全部环节预计合计     ≈ 150,500 Token
预算保护值（×1.3）   195,650 Token
```

显示规则：

- 2026-10-09 用户确认：输入和输出预算统一增加 30% 余量（×1.3）；缓存命中 Token 仍计入输入，不另外抵扣。余量是预算预留，不代表估算精度，也不承诺覆盖异常重试。

- “AI 复核”和“AI 翻译”使用独立标题或卡片，不把两类 Token 混成一行。
- AI 复核区显示当前复核范围；范围变化后重新试跑，报告必须随范围重新计算。
- 每种当前有效分类按“手动标记、既有 AI 复核、DLL 分析、XML 分析、系统回退”展示来源数量，来源与分类不得混为同一字段；云翻译是译文来源，不是分类来源，禁止出现在分类来源统计中。
- 默认只复核“待判定”时，既有复核已经使待判定归零，则再次试跑的 AI 复核估算为 0；勾选“需要翻译”或“无需翻译”后，相应范围重新产生估算。
- “需要翻译且无有效译文”与“待判定且无有效译文折算（50%）”在翻译区内分组显示，让用户知道哪些是确定范围、哪些是概率估算；已有有效译文的数量另行显示为“已覆盖，不重复翻译”。
- 主要数字右对齐并使用千位分隔；`Token` 只在标题或合计行重复，减少视觉噪声。
- 汇总窗口默认显示全部选中 Mod 的总量；下方按 Mod 展示紧凑摘要，点击后展开相同结构的详细数据。
- 建议的逐 Mod 摘要为：

```text
Quartermaster
分类复核 ≈ 4,200 · AI 翻译 ≈ 18,600 · 合计 ≈ 22,800 Token
需要翻译 112 · 待判定 38（按 50% 折算约 19）
```

- 试跑结果应同时保存估算器版本、固定比例 `50%`、预算保护系数 `1.2`、模型/路由信息、AI 复核范围和分析结果指纹，便于以后解释同一批条目为何出现不同估算。

## 9. 步骤四：AI 复核

正式名称和按钮名称统一为“AI 复核”。建议悬浮说明：

> 使用 AI 根据条目所在文件、上下文及可用的分析证据，重新判断条目应归为“需要翻译”还是“无需翻译”。默认只复核“待判定”条目，也可以将“需要翻译”和“无需翻译”加入复核范围。

### 9.1 职责

AI 复核读取现有分析证据，对用户选定范围内的条目重新判断并输出：

- 需要翻译；
- 无需翻译；

它只更新分类结果，不生成译文，也不修改翻译状态。

AI 复核不依赖译文同步代次，也不检查译文状态是否就绪。后端只按稳定 `mod_identity` 排除受保护目标，再由当前候选分页 SQL 同时限定 `is_present=1`、当前 Mod 指纹和当前 XML／DLL 分析器版本；当前有效候选为零的 Mod 正常跳过并记录原因。译文同步和文件状态就绪保护只属于 AI 翻译及写文件链路。

### 9.2 默认范围与可选范围

- “待判定”是必选范围，默认处理。
- 用户可以额外勾选“需要翻译”，让 AI 再判断一次。
- 用户可以额外勾选“无需翻译”，让 AI 再判断一次。
- “需要翻译”和“无需翻译”默认均不勾选。

二次点击 AI 分类复核时，任务范围依据条目的当前有效分类，而不是第一次分析时的原始分类。例如第一次复核后只剩 10 条待判定，默认第二次只处理这 10 条。

手动标记同样可以进入用户选定的 AI 复核范围。AI 结果写入当前 AI 位，但统一裁决解析器继续遵守“手动标记 > AI 复核 > DLL 分析 > XML 分析”，所以 AI 结果不能覆盖有效手动标记。正式结果报告必须分别显示“完成复核”“产生 AI 判断”“改变当前有效分类”和“受手动标记保护”的数量。

### 9.3 判断依据

AI 判断使用：

- 最近一次有效的 XML 或 DLL 分析证据；
- 当前分类；
- 上一次 AI 分类结果与理由（如存在）；
- 必要且受限的条目上下文。

AI 分类复核不得为了获得这些材料而重新调用分析器。

AI 复核使用一套提示词模板，三种分类范围只决定哪些条目进入任务。同一 Mod 内允许跨来源文件组批；每批最多 50 条且完整输入提示词最多 6000 Token，任一边界先达到即切批，不能简单截断后永久丢弃后续条目。

真实运行在工作流层按设置中的 `MaxThreads` 建立有界请求窗口，只有提示词已经构造完成后的模型网络请求与等待响应允许并发；候选游标分页仍保持页级边界，响应解析、短序号／数量完整性校验和 AI 分类结果保存按批次原顺序串行提交。窗口内常驻请求不超过并发上限，一个请求结束后才补入下一批；单批失败不取消其他在途批次，用户取消则停止继续调度并把取消令牌传给在途请求。模拟模式不发送真实请求，也不伪造并发。任务详情和日志分别报告排队、实际进行中数量、响应到达、顺序提交及已处理候选数，不能把创建任务当作完成。

XML 条目优先拼接文件路径、节点路径和必要的相邻节点；DLL 动态文本可以额外拼接精简的方法、类型和调用链证据。调用链是按需证据，不是所有条目的强依赖，完整长链不得无条件塞入每次请求。

批次输入用 `files` 数组去重文件路径，每条复核输入使用 `[itemIndex,fileIndex,locator,context,text]`；输出使用 `[itemIndex,classification,reason]`，理由字段应限制长度。持久 `candidateId` 只留在本地批次数组中，不发送给模型。模拟模式只依据同一输出协议估算 Token，不伪造或保存分类结果。

AI 复核允许三个成功分类值：`needs_translation`、`no_translation_needed`、`needs_review`。`needs_review` 只用于证据不足、证据冲突，或无法可靠判断文本是否为玩家可见自然语言的情况，不得作为逃避判断的默认答案。它复用 `CandidateClassification.Undetermined` 写入 `ClassificationLayer.AiReview`，并照常保存 AI review version、输入 fingerprint 和 reason；因此可由 AI 层元数据与“从未复核”区分。该结果计为复核成功，不计失败，手工分类仍保持最终优先级；有效分类继续为待复核，不进入 AI 翻译，并和其他 AI 复核结果一样在后续复核中直接跳过。只有用户先清除当前 Mod 的 AI 复核结果后，条目才允许再次提交。未知字符串继续按协议错误拒绝，批次短序号完整性校验不放宽。

真实复核的每批和每个 Mod 日志分别汇总“需要翻译／无需翻译／仍待复核”数量；Debug 按条记录批次内索引、模型分类和简短理由，不记录任何模型凭据。写回待复核不会改变当前轮次的游标边界：同一轮仍按读取页面时取得的稳定 cursor 前进，不因写入 AI 层 `Undetermined` 重复读取。

### 9.4 当前结果、撤销和恢复

每个条目只保存当前 AI 复核位，以及对应的复核器版本和输入指纹。版本、指纹和理由用于诊断，不作为自动失效条件；AI 位一旦存在，后续复核直接跳过该条目，不保留该条目的历次 AI 分类历史。

- 清除 AI 复核：在译文编辑页按当前 Mod 批量将 AI 位改为 `00`，清空 AI 版本、提示词版本、指纹和理由，自动回落到手工分类或 DLL/XML 结果；
- 撤销手动分类：将手动位改为 `00`，自动回落到 AI/DLL/XML 结果；
- 还原到本地分析：同时清空手动位和 AI 位；
- 不支持“恢复到上一次 AI 判断”，只支持清除当前高层结果后回落。

AI 复核的批次级运行报告可以保留，用于查看调用消耗和错误，但它不承担分类历史恢复职责。

## 10. 步骤五：AI 翻译

### 10.1 职责与范围

AI 翻译只处理选中 Mod 当前分类为“需要翻译”，并且当前没有有效译文或翻译状态为“失败”的条目。分类为“需要翻译”但已经存在有效第三方、Mod 原生、云端、手动或 AI 翻译译文的条目保持“已翻译”，不重复调用模型。

它作为独立入口执行时不得：

- 自动启动 XML/DLL 分析；
- 自动执行试跑；
- 自动执行 AI 分类复核；
- 把“待判定”默认当作需要翻译。

### 10.2 状态变化

翻译开始后：

```text
未翻译/失败 → 翻译中 → 已翻译或失败
```

成功条目保存目标语言、译文、`sourceTextHashAtTranslation`、模型/来源、校验结果和时间。最终译文继续输出为 RimWorld 可加载的 XML；DLL 定向翻译保存到其对应清单或运行时应用结构，不改写第三方 DLL。

分类状态不因翻译成功而变成“已翻译”。

## 11. 分析更新与下游结果失效

分析器版本和输入指纹均不变时，确定性分析结果必须视为不变并直接复用。

重新分析后的处理粒度是条目，而不是整个 Mod：

- 条目稳定身份未变：始终保留当前 AI 分类位和当前有效结论，即使条目内容、分析证据或版本发生变化。
- 只有用户在译文编辑页执行当前 Mod 的“清除 AI 复核”后，AI 位才清空并回落到本地分析结果。
- 新增条目：使用新的基础分析分类。
- 消失条目：归档，不再进入当前任务范围。
- 试跑报告继续保留，但若依据的分析结果指纹不同则显示“历史/已过期”。
- 已翻译条目的当前 `sourceTextHash` 与译文记录中的 `sourceTextHashAtTranslation` 不同：译文标记失效，翻译状态回到“未翻译”；本轮不要求在分类数据中保留旧结果历史。

XML 分析器升级只影响 XML 域；DLL 分析器升级只影响 DLL 域。

## 12. 每个 Mod 的可见结果

Mod 列表至少能直接展示：

- XML 分析：未分析、有效、过期、分析中、失败；
- DLL 分析：未开启、未分析、有效、过期、分析中、失败；
- 分类数量：需要翻译、无需翻译、待判定；
- 翻译数量：未翻译、翻译中、已翻译、失败；
- 最新试跑时间与预计 Token；

主工作台的 Mod 集合来自游戏启动后在主线程取得的轻量元数据快照，而不是“已经递归证明存在可翻译源”的扫描结果。快照只包含显示名、Package ID、稳定 `mod_identity`、Root、启用状态、安装实例数和固定保护标记；后台只能读取复制后的不可变值。Defs、Languages、XML、DLL 和强制候选目录的遍历不得成为主列表首次显示的前置条件。

列表状态由当前 Mod 快照左连接 SQLite 汇总结果得到。数据库查询必须在 SQL 内按 `mod_identity`、`source_domain`、当前有效分类和当前译文状态聚合，只返回计数行；不得为主工作台读取 `source_text`、`translation_text`、`context_json`、文件定位等候选完整字段。有效分类优先级固定为手动 > 当前 AI > 当前 DLL > 当前 XML > 待判定回退；只有 `TranslationResults.sourceTextHashAtTranslation == Candidates.sourceTextHash` 的已翻译记录才计为当前有效译文。因而主列表读取复杂度随当前 Mod 数量增长，而不随候选条目数增长；未分析当前 Mod仍通过左连接显示，已卸载历史 Mod不显示。

“翻译状态”列只统计当前有效分类为“需要翻译”的候选：翻译中为状态 1；已翻译要求状态 2 且译文记录原文哈希非空并等于候选当前原文哈希；失败为状态 3；未翻译为状态 0，或状态 2 但原文哈希缺失／不一致。待判定和无需翻译不进入任何翻译状态计数。XML／DLL 行、顶部汇总和未翻译筛选均直接复用这份 SQLite 聚合，口径与 AI 翻译候选查询一致。

试跑中的 `EstimatedOutputTokens` 只用于成本估算和展示，永不传递、推导或回退为真实 API 的 `max_tokens`／`maxOutputTokens`。每个 API／模型配置独立保存“ATC 单次最大输出 Token”，旧配置缺省为 10000；模型列表接口能可靠返回能力时，Google 使用 `outputTokenLimit`，OpenRouter 使用 `top_provider.max_completion_tokens`，实际请求上限取已知模型能力与用户配置的较小值，能力未知时仅使用用户配置且不猜统一能力。模型切换后按当前模型键重新解析，不能沿用另一模型的能力。

模型响应必须保留 `finish_reason`。只有正常结束才进入 JSON 解析和批次内短序号无遗漏／无重复／不越界校验；`length`、`MAX_TOKENS`、`max_output_tokens` 等触顶状态直接判当前批次失败，不提额、不重试、不响应后拆批，并报告提供方、模型、实际请求上限、实际输出 Token 和批次条目数。同一 Mod 内允许跨源文件组批，每批同时受最多 50 条和完整输入提示词最多 6000 Token 两个边界约束；不得发送持久 `candidateId`。AI 翻译输入使用 `[itemIndex,locator,source]`，输出使用 `[itemIndex,translation]`。提供方支持结构化输出时必须发送对应参数；DeepSeek 的自动模式使用 `response_format: {"type":"json_object"}`。解析器允许剥离且仅剥离一个完整的最外层 ` ```json ... ``` ` 或 ` ``` ... ``` ` 包装，随后继续执行同一套 JSON、短序号和条目数量校验；不完整、嵌套、多段或带额外正文的代码块仍判失败。正常结束但内容仍不是有效 JSON 时，用户错误统一说明模型未遵守结构化输出协议，底层解析位置只保留在异常链；Debug 级别为失败批次把模型原始响应正文单独保存到诊断文件，并在错误日志记录文件路径，不记录 API Key、Authorization 请求头或请求载荷。每批失败立即进入任务详情、Info 和 Error 日志，累计成功／失败／总数同步更新，剩余批次仍按既有策略继续。

AI 翻译采用与 AI 复核相同的有界请求窗口和顺序提交语义：并发只覆盖已构造请求的网络等待，XML 写入、待处理操作完成和数据库状态更新不得并发。模型正常返回完整批次后，本地译文校验器可以逐条拒绝不安全译文；这种情况记录为“请求成功 N/N、成功保存 N、校验拒绝 M”，不称为模型批次失败，也不回滚同批其他有效译文。拒绝项保持数据库失败状态，任务详情和错误页明确显示“本地译文校验器拒绝”；Debug 诊断按条记录批次短序号、Mod、源文件、locator、完整原文、模型实际返回译文及命中规则／原因，但不得记录凭据、完整提示词或未脱敏 URL。

选择集合以 `mod_identity` 为唯一键，Package ID 只用于显示、搜索和辅助匹配。同一逻辑 Mod 的多个安装实例必须保留实例信息并优先绑定启用实例；缺少 Package ID 的本地 Mod 保留 `local:` 稳定身份。列表按实际 Rect 高度动态计算可见行数，使用约 3 倍可见行数的预取窗口并只绘制实际可见行；范围／状态／搜索／排序变化不得把选择键退回 Package ID。

固定不可翻译系统包顺序为：RimWorld 本体、Royalty、Ideology、Biotech、Anomaly、Odyssey、ATC 本体、`AITranslation.Pack`。默认“已启用”范围不显示它们；“全部”范围把存在的项按该固定顺序放在普通排序结果之后，显示灰叉和只读“不处理”状态，搜索可命中但不能选择。状态筛选不把它们当作普通未分析 Mod。UI 选择、执行范围解析和后端公开入口均须二次排除；旧候选数据不自动删除。官方语言 TAR 与 Memory Injection 可继续把官方内容作为只读参考，不能把“不可作为翻译目标”扩大解释为“不可读取官方译文”。

勾选交互从勾选热区的左键 `MouseDown` 开始并立即反转当前行；按住拖动时，每个首次进入的可选 `mod_identity` 按自己的进入时状态反转一次，同一手势不重复处理已访问身份，`MouseUp` 只结束手势。越过列表上下边缘时，在勾选列水平容差内按越界距离平滑加速自动滚动，速度使用帧时间归一化并限制在合法 scrollY；滚动带入的新行继续使用同一 visited 集合。受保护、不可见、busy 行跳过，失焦、切换标签和任务进入 busy 必须清理手势。
- 最新 AI 分类复核时间及变更数量。

用户应能从单个 Mod 进入对应详情，不必先运行一次全局任务才能看到以前保存的结果。

没有当前有效本地分析结果的 Mod 不置灰，也不禁止选中；列表只显示状态说明“未完成本地分析”。这样它才能作为统一“分析”按钮的首次分析目标。试跑、AI 复核和 AI 翻译仍只消费数据库中实际存在的有效条目：选中集合中尚未分析的 Mod 本轮处理数为 `0`，逐 Mod 结果明确写“未完成本地分析，无可用条目”，不得暗中触发分析。

## 13. 持久化架构

### 13.1 推荐方案

面对 500～1000 个 Mod、约 5～10 万甚至更多条目，推荐采用：

```text
轻量本地数据库：工作流当前状态、索引、批次报告和查询
XML/清单文件：RimWorld 实际加载、导出和分享的最终产物
```

数据库不替代最终翻译 XML，也不写入第三方 Mod。数据库属于用户本地工作状态。

当前业务实施范围固定为 **RimWorld 1.6**，并保持工坊单包对 Windows、Linux、macOS 的兼容方向。RimWorld 1.5 不在本阶段改造范围；后续 1.5 工作原则上是把已经稳定的存储与业务层迁移到 1.5 工程、适配 API 差异并单独打包，不能在没有实际兼容检查时把它简化成纯复制产物。

数据库驱动固定选择：

```text
共同 ADO.NET 提供程序：System.Data.SQLite 2.0.4（net471，RimWorld 1.6 项目 net48 可引用）
共同 SQLite 构建来源：SourceGear.sqlite3 3.53.4
Windows x64：e_sqlite3.dll
Linux x64：libe_sqlite3.so
macOS x64：libe_sqlite3.dylib
macOS arm64：libe_sqlite3.dylib
```

采用“一套托管提供程序 + 各平台对应原生二进制”的混合方案，不为三个平台选择三套不同的 C# 数据库库。这样三端使用完全相同的 SQL、Schema、迁移和事务代码，只在启动时选择与操作系统/CPU 匹配的 SQLite 引擎。三个不同提供程序会带来参数语法、异常类型、事务行为和迁移测试矩阵的额外差异，不采用。

不引入 Entity Framework、Dapper、SQLitePCLRaw bundle 或第三方迁移框架，也不把包含移动端等无关架构的完整 NuGet 包复制进工坊 Mod。发布内容只提取上面四个桌面运行时文件和一个共同的 `System.Data.SQLite.dll`。`SQLiteNativeBootstrapper` 在第一次打开数据库前检测平台与进程架构，把匹配文件复制到 `!Translation_AI_Pack/Runtime/SQLite/<version>/<rid>/`，校验随包 SHA-256 后显式预加载，再创建连接；不得写入系统目录或修改用户环境变量。macOS 根据进程架构在 x64/arm64 中二选一。

业务层必须通过同一存储接口访问，不能散布驱动或平台判断。以上是静态兼容方案；四个目标仍须由对应平台玩家手动启动 RimWorld 1.6 验收原生加载、建库和最小读写。任何一个平台未经实机验收前只能标为“计划兼容”，不能在工坊说明中声称已经验证支持。

### 13.2 建议数据实体

| 实体 | 作用 |
|---|---|
| `Mods` | 稳定 Mod 唯一标识、Package ID、名称与来源信息 |

关键索引至少覆盖：

```text
(packageId, sourceDomain)

(workflowRunId, packageId)
```

### 13.3 事务边界

- 每个 Mod 的一次分析结果以事务提交。
- 强制分析使用原子替换或版本切换。
- AI 分类复核按小批事务更新条目的 AI 位、版本与输入指纹；运行批次报告可以保留，但不保存逐次分类历史。
- 翻译结果可以小批提交，避免长任务结束前全部只存在内存。
- XML 与 DLL 在组合入口中串行执行，公共数据库写入保持短事务。

### 13.5 当前译文记录和翻译文件绑定

每个“条目 + 目标语言”只保存一条当前有效译文记录，不保存多个候选译文版本。高优先级译文直接成为当前译文；来源字段只说明当前译文来自哪里。建议使用 `TranslationResults`：

| 字段 | 中文说明 |
|---|---|
| `candidateId` | 对应条目主键 |
| `targetLanguage` | 目标语言目录名或规范语言代码 |
| `translationStatus` | `Untranslated`、`Translating`、`Translated`、`Failed` |
| `translatedText` | 当前译文；未翻译时为空 |
| `translationSource` | `Manual`、`ExternalPatch`、`ModNative`、`Cloud`、`AiTranslation` |
| `sourcePackageId` | 提供译文的第三方/原生/云端目标包标识；用户手动或 AI 翻译可为空 |
| `sourceFilePath` | 当前译文实际来自的文件绝对路径或规范相对路径 |
| `sourceEntryKey` | 译文在来源文件中的 XML 键/Def 路径 |
| `managedOutputFile` | 若译文写入本 Mod 管理的翻译包，记录实际输出文件；只读第三方/原生来源时为空 |
| `managedOutputKey` | 译文在本 Mod 输出文件中的键；没有托管输出时为空 |
| `translationHash` | 当前译文标准化后的内容哈希 |
| `sourceTextHashAtTranslation` | 当前译文生成或确认时对应的 `sourceTextHash` 副本；它不是历史记录，只是当前译文与原文的绑定依据 |
| `validationStatus` | 译文结构、占位符、格式参数、目标语言等校验结果 |
| `lastSyncStatus` | `Synced`、`Missing`、`Changed`、`ReadError`、`Invalid`；它是文件同步健康度，不是翻译流程状态 |
| `lastSyncError` | 最近一次文件读取/解析/写入错误；正常时为空 |
| `lastSyncedAt` | 最近一次与真实文件完成对照的时间 |
| `updatedAt` | 当前译文记录最后更新时间 |

主键或唯一约束为 `(candidateId, targetLanguage)`。分类字段与翻译字段必须独立：删除译文只修改 `TranslationResults`，不修改 `classificationFlags`；手动编辑译文则同时把手动分类位设为“需要翻译”。

当前译文来源默认覆盖顺序沿用既有策略：

```text
用户手动 > 第三方人工翻译 > Mod 原生翻译 > 云翻译 > AI 翻译
```

本轮不把多个来源改造成云端候选库，也不重写现有云翻译服务。所谓“覆盖”是当前有效译文和本 Mod 托管输出在运行时覆盖低优先级结果；禁止改写第三方 Mod、目标 Mod 原生文件或第三方 DLL。较低优先级的当前记录被替换后不保留为分类历史；如果高优先级来源之后消失，重新扫描现有来源并选择当时仍存在的最高优先级译文。

### 13.6 当前代码的本地翻译加载时机

当前本地翻译包固定位于游戏目录下：

```text
Mods/!Translation_AI_Pack/Languages/<目标语言>/Keyed
Mods/!Translation_AI_Pack/Languages/<目标语言>/DefInjected
```

现有生效链由 RimWorld 常规语言加载和本 Mod 的运行时再次注入共同组成：

1. RimWorld 的 `PlayDataLoader` 加载启用 Mod、Defs 和当前语言数据；如果 `!Translation_AI_Pack` 已作为启用 Mod 参与加载，其标准 `Languages` 文件按游戏规则被读取。
2. 本 Mod 安装启动钩子；主线程泵建立后先请求一次 Keyed 预热。
3. `PlayDataLoader.DoPlayLoad` 完成后，启动钩子延迟约 1 秒排队一次全量 Memory Drop；若钩子没有命中，还有 `PlayDataLoader.Loaded` 轮询回退。
4. 后台准备阶段读取本地翻译包当前语言下的 Keyed 和 DefInjected XML，生成不可变注入载荷。
5. 主线程分批将 Keyed 写入 `LoadedLanguage.keyedReplacements`，将 DefInjected 写入相应 `DefInjectionPackage`。
6. DefInjected 写入结束后重新调用语言注入，并刷新部分静态翻译缓存，使新译文无需重启即可生效。
7. 翻译、云下载、工作台保存、删除或语言切换后，现有代码会请求整包或按 Package ID 再次执行 Memory Drop。
8. 用户停止已经写入部分译文的 AI 翻译时，任务取消不等待 Memory Drop 完成；刷新在后台继续并记录最终结果。后台刷新结束前，全局任务协调器仍拒绝启动新的工作流，避免多个流程同时修改运行时译文状态。
9. 协调器的忙碌状态必须覆盖 Memory Drop 的后台准备、待应用载荷和主线程应用全过程，UI 可用态与任务入口拒绝条件保持一致。主线程泵每帧最多推进一个既有应用分片；Def 条目写入完成后，“注入前、注入后、临时恢复项清理、规范化”分别在后续推进中执行并记录耗时，避免多个重阶段在同一帧连续叠加。RimWorld 提供的单个注入调用本身仍不可内部切片，阶段日志用于定位剩余的单次卡顿。

现有 Memory Drop 的目录指纹使用文件路径、大小和修改时间等快速信息来避免同一批文件重复注入；它不是条目级数据库一致性证明。现有来源索引能够用译文值哈希判断来源记录是否仍匹配，但哈希不匹配时主要回退成旧/未知来源，也不会自动把条目标成“玩家手动编辑”。因此当前代码不能在启动时可靠回答每个条目的“已翻译、失效、被手改或被删除”。

### 13.7 新版启动同步顺序

新版必须在现有加载链上新增 `TranslationFileSynchronizer`，数据库不替代 XML，Memory Drop 也不替代数据库同步。这里的“同步”专指**本机数据库与实际翻译文件之间的状态刷新**，不是云同步；云翻译下载只是可能改变本地文件、进而触发一次本地同步的事件之一。推荐顺序：

```text
初始化数据库/迁移
  → 建立当前 Mod、版本和源文件快照
  → 建立当前条目索引
  → 每个翻译 XML 只解析一次，建立 (文件, 键) → 译文 映射
  → 对照 TranslationResults
  → 批量提交状态变化
  → 生成可注入的有效译文视图
  → 沿用现有 Memory Drop 注入游戏内存
```

同步器必须先按文件分组读取，不能为了 5～10 万条记录逐条重复打开 XML。快速路径先比较文件大小、修改时间和已保存文件内容哈希；快速信息未变时可以复用上次解析索引，发生变化时计算真实内容哈希并重新解析。最终有效性不能只依赖修改时间。

启动同步不得为了建立条目映射而暗中调用 XML/DLL 分析器。翻译文件中存在但数据库尚无对应 `candidateId` 的键，先作为“未绑定翻译文件项”保存在文件索引中，不计入条目分类和翻译数量；用户之后显式执行分析并产生稳定条目后，再按文件、来源域和逻辑键完成绑定与状态同步。

启动对照规则固定为：

| 数据库当前记录 | 实际文件 | 处理结果 |
|---|---|---|
| 未翻译 | 没有对应键 | 保持未翻译 |
| 已翻译且译文哈希相同 | 有对应键且校验通过 | 保持已翻译和原来源，标记 `Synced` |
| 已翻译且译文哈希不同 | 有对应键且校验通过 | 视为玩家外部手动修改：手动位=`需要翻译`、状态=`已翻译`、来源=`Manual`，更新译文和哈希 |
| 已翻译 | 文件或键已经消失 | 清空当前译文、来源、哈希和文件绑定，状态=`未翻译`、同步状态=`Missing`；分类位不变 |
| 未翻译 | 文件中出现有效对应键 | 数据库已经建立过同步基线时，若现有来源侧车/操作日志哈希匹配则恢复已知来源，否则按外部手动新增处理，状态=`已翻译` |
| 任意状态 | XML 无法读取或解析 | 不得误判为删除；保留数据库当前值，设置 `ReadError` 并记录错误，禁止把该文件的新载荷注入内存 |
| 任意状态 | 对应值不通过占位符、格式或目标语言校验 | 状态=`Failed`、同步状态=`Invalid`，记录原因，不作为有效注入值 |

首次从旧版文件建立数据库基线时采用一次性兼容规则：

- 来源侧车或现有元数据能够证明来源时，沿用已知来源；
- `!Translation_AI_Pack` 中无法证明既有来源的有效译文统一记为 `AiTranslation`；
- 不新增 `UnknownLegacy`、`Legacy` 或其他分类/翻译状态；
- 第三方翻译包和 Mod 原生翻译仍按实际文件位置记为 `ExternalPatch` 或 `ModNative`，不能误记为 AI 翻译；
- 完成首轮基线后，同一托管文件的内容哈希再发生不匹配，就按玩家外部手动修改处理：手动分类位=`需要翻译`、翻译状态=`已翻译`、来源=`Manual`。

`sourceTextHash` 变化时不猜测译文是否已经人工适配：无论当前译文来源是 AI 翻译、云端、第三方还是手动，也无论译文文件是否同时变化，该条目的当前译文都失效，状态回到“未翻译”。本 Mod 托管输出中的旧键必须从活动文件移除；第三方/原生只读文件不改写，但旧值不得作为当前有效译文注入。Mod 整体 `contentFingerprint` 变化还会触发第 2.6 节定义的完整重分析；逻辑身份仍相同的条目可保留手动分类，但任何旧译文都不能跨原文哈希继续生效。

第三方翻译和 Mod 原生翻译属于只读来源：同步器读取并记录其来源文件和键，但不删除、不覆盖原文件。它们消失或失效时重新扫描其余来源，再选择当前仍存在的最高优先级译文。

### 13.8 写入、删除和崩溃恢复

SQLite 事务不能与文件系统写入形成真正的同一原子事务。所有托管翻译写入必须经过一个轻量操作日志或待处理状态：

```text
1. 在数据库登记 PendingWrite/PendingDelete 和预期文件、键、旧哈希、新哈希
2. 读取目标 XML 并在内存修改
3. 写入同目录临时文件并完成 XML 校验
4. 原子替换正式 XML；需要时先建立可恢复备份
5. 重新读取正式文件并核对键和值哈希
6. 更新 TranslationResults、清除待处理操作并提交
7. 请求对应 Package 的 Memory Drop
```

文件层应复用现有 `TranslationXmlAtomicFileStore` 的同目录临时文件、写穿刷新、`File.Replace` 和回滚能力，不再实现第二套直接覆盖写入。新增工作集中在数据库待处理操作、写后核对以及启动恢复。

程序启动发现未完成操作时，不得猜测写到哪一步，应直接读取实际 XML 并按第 13.7 节规则恢复数据库。文件写入成功而数据库未提交时，文件值会被识别为外部变化；若操作日志的新哈希匹配，则恢复原计划来源，不能错误标成手动。

删除某条译文时必须删除对应 XML 键，而不是只删除数据库记录。删除后：

```text
translationStatus = Untranslated
translatedText = NULL
translationSource = NULL
translationHash = NULL
managedOutputFile/Key = NULL
classificationFlags 保持不变
```

如果一个 XML 文件的最后一个有效键被删除，可以删除空文件；如果文件中还有其他 Mod/条目数据，只能原子重写该文件，不能整文件删除。

### 13.9 手动编辑入口

在本 Mod 界面内手动编辑任意条目时，单次保存必须同时完成：

```text
手动分类位 = 10（需要翻译）
translationStatus = Translated
translationSource = Manual
translatedText/translationHash = 用户保存后的有效值
sourceTextHashAtTranslation = 当前条目 sourceTextHash
```

随后写入实际翻译 XML并请求热注入。若用户只修改分类而没有填写译文，只更新手动分类位，不得伪造“已翻译”。若用户在游戏外直接编辑 XML，不在启动阶段自动核对数据库；由用户点击工作台“刷新状态”后按第 13.7 节识别并更新持久状态。

编辑器的“AI 翻译”与多选“AI 批量翻译”提交稳定候选 ID，而非候选数据快照。服务端按 ID 重新读取当前条目；用户主动翻译的条目若当前有效分类不是“需要翻译”，先写入手工“需要翻译”作为明确用户裁决。定向模式只检查所选条目，不因同 Mod 其他条目的分析或译文同步异常阻止本次操作。

### 13.10 云翻译的本轮实施边界

云分析及云端判断缓存全部废弃；云翻译继续保留为翻译包共享功能。本轮不大范围重写云端 registry、上传、下载、版本选择和 ZIP 协议，只增加与新状态模型直接相关的同步点：

- 云端下载前后的既有备份、清理、解压和 Memory Drop 流程保留；
- 云端下载写入文件后调用 `TranslationFileSynchronizer`，把实际存在的条目标记为已翻译、来源标记为 `Cloud`；
- 整包下载后原有但已消失的键必须同步为未翻译，不能让数据库残留已翻译状态；
- 云端人工/官方/AI 类型仍按现有界面和服务端字段工作，本轮不改造成逐条云端候选库；
- 现有上传继续读取实际 XML 文件，AI 上传来源过滤继续使用译文来源标识；
- 数据库和来源侧车可以增强来源识别，但不得改变云端 ZIP 的可分发性，也不得要求服务端同步分类数据。

### 13.11 查询与服务边界

所有界面和工作流必须通过同一组服务访问状态，禁止各页面自行解释位图或自行扫描文件：

| 服务 | 职责 |
|---|---|
| `ClassificationFlagsCodec` | 读取、设置、清除四来源2位状态，并解析当前分类和来源 |
| `AnalysisValidityService` | 比较本地分析器版本和输入指纹，清除失效 XML/DLL 位；AI 位只允许用户显式清除 |
| `TranslationFileIndex` | 每个 XML 文件解析一次，提供文件+键到值、哈希和校验结果的索引 |
| `TranslationFileSynchronizer` | 对照数据库与真实文件，识别一致、删除、外部手改、无效和读取错误 |
| `TranslationWriter` | 通过待处理操作、临时文件和原子替换写入或删除译文 |
| `EffectiveTranslationResolver` | 按来源优先级选择当前译文，不修改第三方文件 |
| `RuntimeTranslationRefresher` | 在同步和写入完成后调用现有 Memory Drop/清单重载能力 |

AI 翻译及试跑中的翻译模拟只读取已经同步完成的译文状态快照。若某个翻译文件处于 `ReadError` 或有未恢复的待处理操作，应把对应 Mod 标为状态未就绪并提示用户，不能按正常数据继续估算或覆盖。AI 复核只读取当前有效分析候选并写分类位，不读取译文状态快照，因此不受此条件约束。

### 13.12 同步诊断与调试日志

手动译文状态同步在默认 Info 级别只记录关键节点和汇总，避免大量 Mod 造成日志污染；启动译文加载只记录本地缓存读取与 Memory Drop 注入节点，不执行数据库同步。第四个设置标签中的日志级别可切换 Error／Info／Debug，只有 Debug 才输出逐 Mod、逐文件的开发诊断。手动同步至少记录：

- 同步批次 ID、目标语言、Mod 数、文件数、条目数和耗时；
- 一致、外部修改、文件缺失、原文哈希过期、无效译文、读取错误的数量；
- 每个异常条目的 `candidateId`、Mod、规范相对文件、键、原数据库哈希短码和实际哈希短码；
- 分类位变更前后值，以及最终解析出的分类和来源；
- 写入/删除操作 ID、待处理阶段、原子替换结果和启动恢复结果；
- Memory Drop 请求类型、Package 范围、注入/清除数量和失败原因。

普通日志不得逐条输出原文、译文、API 密钥或完整提示词。调试日志需要内容时只输出受限长度摘要，并保留可用于定位数据库记录和实际文件的稳定 ID。

### 13.13 启动加载与手动同步性能约束

启动译文加载与数据库译文状态同步是两条独立链路：

1. `PlayDataLoader` 完成后，启动任务只读取现有本地译文缓存并执行 Memory Drop 注入；不得创建工作流数据库后端，不得查询 `Candidates`、`TranslationResults` 或工作台汇总，也不得写回任何译文状态。
2. 工作台列表以数据库中已经保存的分类与译文状态为权威，首次进入、重新进入或数据修订号变化时异步查询按 Mod 汇总；列表显示不等待启动译文加载，也不扫描磁盘文件。
3. 只有用户点击工作台“刷新状态”，才建立目标语言文件索引、比较文件变化并把实际变化同步回数据库；同步完成后递增工作台数据修订号并重新读取列表汇总。

手动刷新的增量策略：

- 先以文件长度和 UTC 修改时间命中 `TranslationFileCache`；元数据变化时读取内容并比较真实哈希；内容哈希未变则继续复用缓存条目；
- 只把新增、内容变化、读取失败或已经删除的文件路径放入本次变化集合；没有变化文件时数据库候选范围为零；
- 数据库只按变化路径关联当前候选及已有托管译文绑定，使用 `candidate_id` 游标分页读取；禁止从 `Candidates` 或 `TranslationResults` 全表物化条目；
- 文件索引、变化文件数、候选计数、分页进度和最终发布必须显示真实数量并写入对应日志；
- SQLite 使用预编译语句和短批量事务，最终仍以完整同步代次原子发布；取消时继续保留上一次完整状态；
- 工作流自身完成写入或删除后，可以直接记录已知变化并刷新工作台数据修订号，不得反向触发一次全库扫描。

首次手动刷新或缓存整体失效时，可能需要读取全部本地译文文件来建立文件指纹基线，但数据库条目核对范围仍必须由实际文件路径约束，不能退化为全库候选扫描。

实施前不能预设具体毫秒指标。完成代码后应由主人在真实 500～1000 Mod 环境中人工观察启动耗时和同步进度；在当前禁止自动运行验证的约束下，文档不声称任何未经实机测量的性能数字。

### 13.14 数据库位置、结构迁移与损坏恢复

数据库固定保存在现有自动生成数据 Mod 内：

```text
Mods/!Translation_AI_Pack/Database/AutoTranslationCore.sqlite3
```

SQLite 运行时可能同时产生同目录的 `AutoTranslationCore.sqlite3-wal` 和 `AutoTranslationCore.sqlite3-shm`。数据库不放入正式核心 Mod，也不放入 `Languages` 目录，避免被 RimWorld 当成翻译文件扫描。`!Translation_AI_Pack` 的 Package ID 继续使用现有 `AITranslation.Pack`；正式核心 Mod 的 Package ID 继续固定为 `Auto.AITranslation.Core`，不得因测试、数据库或生成包而改变。

生成 `!Translation_AI_Pack/About/About.xml` 时必须写入明确描述，至少表达以下内容：

```text
这是 AI Translation Core 自动生成的数据文件 Mod，用于保存本地分析数据库和游戏可加载的翻译文件。
请不要在 Mod 列表中启用或加载它，以免产生重复加载或顺序冲突；该目录由 AI Translation Core 自动管理。
删除它会清除本地分析、分类和翻译数据，系统将在下次运行时按首次运行重新建立。
```

Schema 迁移不增加独立依赖包。固定使用 SQLite 自带的 `PRAGMA user_version` 配合程序集内按序编号的 SQL 迁移：

1. 打开数据库后读取 `user_version`；
2. 从当前版本逐个执行 `vN -> vN+1`，每一步单独事务；
3. 成功创建/修改结构并写入迁移记录后，最后更新 `user_version`；
4. 任一步失败就回滚该步，不允许数据库停在半迁移状态；
5. 数据库版本高于当前程序支持版本时只提示“核心版本过旧”，不得当作损坏删除。

损坏恢复规则固定为“删除数据库并按首次运行重建”，但只能在 SQLite 明确返回损坏类错误，或 `PRAGMA quick_check`/必要时 `integrity_check` 确认失败后执行。普通文件占用、权限不足、磁盘已满、路径不可写和瞬时 I/O 错误不得误判为损坏。确认损坏后关闭所有连接，删除主数据库及其 `-wal`、`-shm` 文件，记录一次醒目错误日志，然后创建空库并重新建立文件同步基线和分析数据；不设计复杂的数据库修复器。

### 13.15 全局后台任务互斥、热重载与停止

所有用户可见后台流程必须通过唯一的 `WorkflowTaskCoordinator` 获取全局任务租约。同一时刻只允许一个活动任务；一键翻译在步骤 1、2、4、5 之间持续持有同一租约，不能在步骤缝隙被另一项任务插入。任务范围至少包括：

- 启动译文加载、手动刷新译文状态与热重载；
- XML/DLL 分析；
- 试跑；
- AI 复核；
- AI 翻译和一键翻译；
- 云翻译上传、下载及其落盘同步；
- 工作台批量写入、删除和其他会改变数据库或翻译文件的后台操作。

有任意任务处于 `Running` 或 `Cancelling` 时，其他执行按钮统一禁用并显示当前任务名称；只读查看列表、详情、进度和日志不取得任务租约。禁止各页面只检查自己的 `isRunning` 字段，必须读取同一个协调器状态，防止不同标签页并发修改文件或数据库。

启动与手动刷新不得再合并成同一工作流。职责固定为：

```text
启动译文加载：读取本地缓存译文 → Memory Drop 注入

手动刷新状态：比较文件缓存 → 只核对变化路径关联的数据库条目
  → 提交完整同步代次 → Memory Drop 注入 → 重新读取工作台数据库汇总
```

启动任务不得初始化或刷新工作流数据库。“刷新状态”是唯一面向全列表的磁盘文件与数据库状态核对入口；工作台显示始终直接读取数据库已保存状态，不把文件扫描结果作为页面加载前置条件。

“停止”按钮对任何活动后台任务都可用，包括启动同步。停止语义固定为协作式取消：立即禁止产生新批次，取消等待、排队和网络请求；正在进行的短数据库事务或原子文件替换完成到安全边界后退出。点击停止后仍保持全局互斥，直到当前任务实际进入 `Cancelled`/`Failed`/`Completed` 终态并释放租约，不能在旧回调仍可能落盘时提前开放新任务。

同步使用“已完成同步代次”发布结果：取消途中已生成但尚未完整发布的本次代次不得成为当前快照，继续使用上一次完整同步快照，并提示“同步已停止，当前状态可能不是最新”。首次运行尚无完整同步快照时，停止后可以浏览界面和重新发起同步；AI 翻译、一键翻译以及试跑中的翻译模拟提示“尚未完成首次同步”，不能使用半成品译文状态。AI 复核只消费当前有效分析候选，不依赖同步代次。

## 14. 重构边界与建议顺序

建议按以下阶段重构：

1. 固化 `atc-candidate-v1`、双维状态、8位分类位图和存储接口；先写纯数据结构，不改工作流入口。
2. 在 1.6 工程接入固定版本的 `System.Data.SQLite.dll`、四个桌面原生文件和 `SQLiteNativeBootstrapper`，建立数据库连接工厂，禁止业务代码直接创建连接。
3. 实现 Schema v1、`PRAGMA user_version` 顺序迁移、损坏确认/删除重建和 `!Translation_AI_Pack` 的数据库目录及 About 描述。
4. 建立 `WorkflowTaskCoordinator`、全局任务租约、统一取消令牌和所有执行按钮的互斥门禁；先收口现有分散的 `IsRunning` 判断。
5. 抽出共享 `TranslationFileIndex`，实现 `TranslationFileSynchronizer`、同步代次和旧文件首轮基线导入。
6. 将启动 Memory Drop 与手动“刷新状态”拆成独立链路：启动只加载并注入本地缓存译文，手动入口才增量核对文件与数据库并在完成后刷新工作台汇总。
7. 抽出独立 XML 分析器，停止由试跑、AI 复核和翻译临时生成分析结果。
8. 抽出独立 DLL 分析器，保留现有召回和 IL 分析能力。

10. 让 Mod 列表只从持久化状态读取摘要，并显示未分析、同步中、已停止、失败等明确原因。
11. 将试跑改为通过 `simulate = true` 调用 AI 复核与 AI 翻译任务准备流程的无副作用估算步骤。
12. 将 Agent 逻辑改为独立 AI 分类复核，按8位位图写入当前 AI 位，并实现清除高层结果后的自动回落。
13. 将 AI 翻译限制为只读取当前“需要翻译”条目，并将文件写入统一收口到 `TranslationWriter`。

重构期间必须继续遵守：

- 不修改第三方 Mod 文件或 DLL；
- 最终翻译产物写入独立本地翻译包；
- Unity/RimWorld 对象修改留在主线程；
- 当前实施只改造 RimWorld 1.6；同一工坊包保持 Windows x64、Linux x64、macOS x64/arm64 的计划兼容，1.5 另行迁移、适配和打包；
- 保留现有翻译复用、校验、热重载和错误诊断能力。

## 15. 已确认的入口说明

> 2026-10-08 已确认补充：当前 XML 分析器升级为 `xml-3.01`。以下 `xml-3` 冻结规则描述作为演进背景保留；已迁移的明确文本字段／路径及本次未知字段宽召回优先于旧的严格冻结范围。三种 Def 读取方式共用收集入口：已知规则照常处理，未知字段中疑似自然语言的值收集为待复核，不直接判为需要翻译。明显的标识符、引用字段、资源路径、数值、布尔值、纯控制符和受保护路径不通过新增兜底。普通单词可能同时是名称或引用，无法从值确定的内容留给复核。保存字段路径、收集原因和最终分类原因；目标语种识别、原生译文识别以及人工／AI 分类优先级继续适用。收集本身不调用模型，也不新增自动复核任务。实施及静态审阅见 [XML 未知文本宽召回](../reports/xml-unknown-text-recall-2026-10-08.md)。

分析按钮默认复用分析器版本与 Mod 内容指纹，只补做缺失或已过期的数据；用户显式选择强制分析时才重算当前结果。AI 复核范围已经放入新版执行区域的下拉选择，不再另设重复入口。设计要求在实现后继续保留，实施状态另见后端实现记录。
当前 XML 分析器版本为 `xml-3`。字段筛选继续严格使用提交 `622d6af`（v3.0）的 Def、Keyed 和 DefInjected 规则，不叠加数据子树剪枝、数值比例、候选阈值、密度熔断、额外诊断失败态或后来扩展的字段规则；与 `xml-2` 的语义差异仅是 Def 在筛选前先解析命名父 Def 继承，因此子 Def 会增加从父级获得的有效可翻译字段。版本号用于区分数据库结果：初始化将旧分析器版本候选标为非当前；新的完整结果成功产生后，在单 Mod／XML 域事务内替换当前结果。历史行和人工译文不作物理删除。

### 15.1 `xml-3` 继承解析、流式读取与工作台状态呈现

`xml-3` 对同一 Mod 的有效内容根执行两遍受控读取。第一遍只保存带 `Name` 的命名父 Def 子树，按有效内容根及文件顺序建立索引；同名父 Def 以后出现的有效定义覆盖先前定义。第二遍逐文件扫描：没有有效 `ParentName` 或显式 `Inherit=false/0` 的普通 Def 继续使用顺序 `FileStream + XmlReader`，只维护当前元素栈、父路径、同一父节点的 `li` 序号和纯文本叶子状态；声明继承的 Def 只构造当前单个 Def 子树，按父链合并后立即筛选并释放，不把全部 XML 或全部具体 Def 常驻 DOM。父链缺失或循环写入诊断，并以当前 Def 自身内容继续分析；子节点按同名同序覆盖父节点，列表项沿用追加语义。

继承解析完成后仍逐项调用冻结自 v3.0 的 `IsTranslationTarget`、黑名单、保护路径、引用值、列表强制翻译和已知路径规则，不增加大型数据子树剪枝、候选上限或熔断。继承候选继续使用子 Def 的 `defName + 字段路径` 形成稳定定位，来源文件归属子 Def；因合并节点没有可靠的原始叶子行号，行号记录子 Def 声明位置。Keyed／DefInjected 继续只读取文件根容器的直接元素子项；DefInjected 保留 v3 `LoadXmlFileToDict` 对 `\\n`、`\\r` 和 `/n` 的历史换行还原，Keyed 继续使用原始 `InnerText`。

Mod 内容指纹改为固定缓冲区流式 SHA-256；仍使用完整文件内容哈希形成稳定版本指纹，但不再同时分配整文件 `byte[]` 和字符串，也不再对整份源 XML 做文件级 Token 估算。候选自身的 Token 估算仍只针对通过 v3.0 规则的源文本。

分析进度不再把 XML、DLL 阶段换算成固定 1000 单位，也不使用 10%／90% 或 92%／8% 的人为阶段权重。总体层报告真实 Mod `x/y` 和当前 XML／DLL 步骤；文件层报告真实文件 `x/y`，流式读取大文件时报告已读取字节／总字节及可取得的当前行号；DLL 扫描与条目整理分别报告各自真实计数。没有真实分母的层级不显示伪造数字。

工作台把本地分析状态分为“未分析、已过期、当前有效、分析失败”。分析器版本（当前为不透明字符串 `xml-3`，后续小版本仍使用新的不透明字符串）和 Mod 内容指纹都按字符串精确比较，不作数字或小数解析；历史成功记录与当前任一值不匹配即为已过期，并在提示中说明分析器版本旧→新或 Mod 指纹变化。颜色语义固定为：未分析灰、已过期黄、失败红；当前有效正文白并附小绿状态标识。有效分类列按非零计数分别使用需翻译黄、待判定浅蓝、无需翻译弱化；译文列使用已译绿、未译黄、失败红、零值弱化，禁止整行无差别染色。

过期候选默认保留，以便相同稳定 `candidateId` 再次出现时复用仍与原文哈希匹配的译文；版本升级、启动和重新分析不得自动物理删除。用户可以从“管理 → 清理过期数据”主动清理：界面先统计过期候选及关联译文状态、文件索引绑定和文件操作记录，并明确警告删除后无法恢复和找回；确认后只删除 `is_present=0` 候选及这些数据库依赖，保留当前候选、分析运行历史、磁盘译文文件和模型配置，最后尝试压缩数据库回收空间。

分析器版本失效本身就是过期数据来源：初始化以不透明字符串精确比较当前 XML／DLL 分析器版本，并把版本不匹配的仍有效候选标记为 `is_present=0`。因此同一个“清理过期数据”入口必须覆盖这些版本过期行，无需另建按版本清理入口，也不得在升级时自动物理删除。

正常启动和首次打开工作台只允许执行数据库 Schema 版本检查、必要迁移和当前分析器版本失效标记，不得执行 `PRAGMA quick_check` 等按整个物理数据库规模扫描的完整性检查。数据库完整性诊断属于独立维护操作，不能成为读取当前 Mod 汇总结果的前置步骤。

范围与工具栏按当前实现分两排。第一排为“搜索｜范围：已加载 Mod / DLC｜分析状态：全部／具体状态｜刷新状态｜管理”，第二排为“已选择统计｜全选筛选结果｜反选筛选结果｜清空选择”。未加载 Mod 不进入翻译工作台或相关设置页列表；保护 Mod／DLC 只在“分析状态：全部”中出现，并固定置底、灰叉、不可选择；具体状态筛选全部隐藏保护项。全选／反选不改变筛选外已有选择，清空选择清除全部，统计在需要时显示筛选外选择数量。上方“刷新状态”仍保持当前已加载列表入口语义，本节不改变其内部同步算法。

译文编辑页在单条分类修改成功后保持当前筛选快照，不因条目新分类不再匹配筛选条件而立即移除；用户改变搜索、筛选、Mod 或页码时再重查。分类筛选除最终有效结论外，还提供“有手动分类”，直接按手动分类层非零筛选。分类层只绘制该条目 `source_domain` 对应的 XML 或 DLL 本地层，连同 AI、手工层展示，并明确高亮当前有效层。手工分类用“未设置（跟随自动结果）／需要翻译／待复核／无需翻译”四项下拉，详情区保留“清除本条”以只清除当前条目的 AI 复核结果。页面顶部针对当前 Mod 提供红色“清除分类数据”按钮，弹窗允许分别勾选 AI 复核结果、手动分类，或同时勾选两项；不在该弹窗提供译文清除。页面顶部同时提供与工作台相同能力和启用条件的黄色“热重载”按钮，保存或删除译文后可由用户显式重新注入 XML 译文并重载 DLL UI 译文，不触发分析或 AI 调用。

翻译状态是“当前有效分类为需要翻译”之后的下游状态。待复核或无需翻译条目即使数据库仍保留早期翻译尝试，也在界面显示“不适用”，不进入未翻译、已翻译或失败筛选；历史记录不得反过来覆盖当前分类。失败详情必须用用户可理解的原因说明校验规则，并在有现存旧译文时明确标注它不是本次被拒绝的模型输出。后续校验失败记录保存受限长度的本次模型输出及提供方、模型、提示词版本、运行和批次标识，输入正文与结构上下文继续以候选记录为准，不重复保存完整提示词。

任务进入 `Completed` 只表示调度流程正常抵达终态，不等于每个候选都成功。最终步骤禁止写“全部完成”；必须显示“本次所选 Mod／实际处理／跳过／候选／成功／失败”口径，存在条目校验失败时使用“处理结束（部分失败）”。工作台当前累计状态与最近一次运行报告是两种统计范围，任何摘要均需用“本次”或“当前累计”明确区分。

失败状态不是永久排除标志：后续 AI 翻译任务仍会选择当前有效分类为“需要翻译”的失败条目重试。一次批量响应中被本地校验拒绝的条目先逐条补试一次，补试仍失败才计入本次最终失败。已有当前云端、Mod 原生、第三方或手工译文的条目不进入本地 AI 翻译，即使历史状态位曾被失败尝试污染；同步步骤负责校正历史混合状态。

译文文件同步异常按候选条目隔离：读取错误、外部来源变化或未恢复文件操作只阻止对应条目写入，不得把同一 Mod 的其他当前失败候选一并排除。工作台汇总、编辑器筛选和条目状态标签必须采用与 AI 候选查询相同的“当前有效译文”判断，避免同一条云端译文同时显示为失败并再次送翻。

模型输入不直接暴露 RimWorld 占位符的语法名称。每条原文在请求前把受保护变量稳定映射为该条目私有的 `[0]`、`[1]` 等数字黑盒，模型只负责原样保留并放在译文对应位置；响应后由本地映射还原真实变量，再比较每种变量的拼写与出现次数。数字标记缺失、重复、未知或还原后结构不一致均不得写入译文文件。

逐条补试不是递归重试：每个首轮校验未通过条目最多追加一次请求，补试失败即形成该条目的本次最终失败。运行界面必须显示首轮未通过总数、当前补试序号／总数、补试成功和仍失败，补试阶段的子进度不得继续停留在首轮候选 `100%`。

所选 Mod 的批量清理由一个“清除结果…”确认窗承载，AI 复核、手工分类、AI 翻译三个选项默认均不选择，无选择时不能确认。AI 与手工分类同时清除即回落到当前本地层；AI 译文清除只处理 `TranslationOrigin.AiTranslation` 的数据库记录及其托管输出，不删除云端下载、手工、Mod 原生或第三方译文。AI 提供方与实际模型作为独立元数据记录，不混入译文来源枚举。分类清理覆盖所选 Mod 的当前与历史候选，避免历史稳定条目未来重新出现时恢复已明确清除的高层结果；受保护目标仍由后端排除。
