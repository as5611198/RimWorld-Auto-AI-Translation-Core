# 安全范围与适度设计

## 1. 项目与威胁模型

ATC 是在用户本机运行的开源 RimWorld Mod。安全设计必须以项目真实处理的数据、真实存在的信任边界和可说明的攻击路径为依据，不能因为某段代码使用 SQL、文件系统、反射或网络接口，就默认把所有内部数据当作外部恶意输入。

当前需要重点保护的资产是：

1. 用户为大模型服务配置的 API Key、Secret Key、访问令牌及同类凭据。
2. 项目实际采集、读取、保存或传输的用户隐私与设备信息，例如 IP、地址、机器码、MAC 地址等。当前功能没有涉及的信息，不得为了假设场景主动采集。

若以后新增云服务、多用户共享、远程管理、第三方插件输入或其他新的信任边界，必须根据新增数据流重新评估威胁模型，不能把本规则机械延伸，也不能继续沿用旧结论而不评估。

## 2. 必须实施的保护

- 凭据不得写入源码、提交到仓库、进入普通日志、诊断报告、运行记录、提示词快照或非必要数据库字段。
- 错误信息、调试日志和导出内容必须对凭据做可靠脱敏；不能只隐藏界面显示而在后台保存明文副本。
- 只有功能确实需要时才能采集用户或设备信息，并明确用途、保存位置、生命周期和是否传出本机；非必要信息不采集。
- 涉及网络发送时，只发送功能所需的最小数据，并在产品设计中记录接收方和用途。
- 本地配置和缓存应使用与实际风险相称的保护，不得以“安全”为由破坏用户对自己数据的访问、备份和迁移能力。

## 3. 禁止过度安全设计

新增安全机制前，必须能够明确回答：保护什么资产、输入来自哪里、攻击者是谁、越过哪条信任边界、成功后造成什么实际影响。无法回答时，不得擅自加入会增加复杂度、限制扩展、降低性能或改变功能语义的安全层。

具体约束：

- 用户本机的 ATC SQLite 数据库属于用户自己的数据，不是用来防止用户本人读取或修改的安全边界。不得为了阻止用户操作自己的数据库而增加加密、名称白名单、权限模拟或其他限制。
- 由仓库内部代码写死并在私有调用链中传递的常量，不按外部不可信输入处理。若这类值需要拼接到 SQL 标识符位置，只在拼接边界做通用语法校验即可；不得另建一份固定名称白名单，迫使每次新增内部临时表都同步维护授权列表。
- 参数化 SQL 继续用于实际数据值。SQL 表名、列名等无法参数化的内部标识符，应通过封装和通用标识符语法校验保证正确拼接；只有名称确实来自外部输入时，才需要额外映射或允许列表。
- 不得把普通正确性检查包装成额外安全架构。数据格式验证、空值检查、事务、原子文件替换、版本校验和错误恢复可以为了正确性保留，但应与真实风险和性能成本相称。
- 不得以假设的 SQL 注入、设备攻击、数据库篡改或用户误操作为理由，擅自改变已经确认的工作流、分页边界、数据模型或结果语义。

## 4. 变更准入

任何会改变产品行为、数据语义、数据库结构、调用链、性能或扩展方式的安全措施，都必须先记录其威胁模型、收益、代价和替代方案，并取得明确确认后实施。修复安全问题时只修改造成真实风险的最小范围，不得顺带重构无关功能。

代码评审发现潜在安全问题时，应先区分以下三类：

1. 已存在的真实外部输入或敏感数据泄露风险：优先修复。
2. 未来功能可能引入的风险：记录触发条件，等对应功能设计时处理。
3. 只有本地用户能够对自己文件、进程或数据库实施的操作：默认不视为需要产品代码对抗的攻击。
