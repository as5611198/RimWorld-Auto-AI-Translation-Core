# V4 Beta 新增功能、功能变动与简要使用说明

本文根据 2026 年 8 月 10 日晚间讨论、当前工作区相对 V4 Beta 基线的代码差异，以及 2026 年 8 月 12 日生成的最新测试包整理。面向测试人员、原作者和普通用户说明本轮实际发生的变化。

## 一、版本定位

本轮改动的重点不是增加更多“一键翻译”入口，而是让大批量 AI 翻译更加可控、可续作、可复用，并降低重复请求、格式错误和不同翻译来源相互覆盖的风险。

主要方向包括：

- 为一次翻译任务设置字符与内部 Token 用量上限；
- 任务中断后保留已完成结果和用量账本；
- 根据供应商与模型能力选择结构化输出格式；
- 为 DeepSeek 使用独立请求适配；
- 将模型按大量、中量、小量任务分级；
- 复用已经通过规则验证的翻译结果；
- 允许全局或按 Mod 调整翻译来源优先级；
- 为判断结果预留安全的云端判断缓存；
- 自动扫描和翻译已启用 Mod 的 DLL 硬编码 UI 文本；
- 在全域编辑器中统一查看、搜索和编辑 XML 与 DLL；
- 明确区分排队、超时、HTTP、429、配额、格式和取消错误；
- 可选地为指定 Mod/系列建立任务级术语，机械交叉验证后再由用户决定是否永久采用；
- 停止格式验证失败后的隐性自动重试，避免重复计费。

## 二、新增功能

### 1. 单次翻译任务用量上限与断点续作

设置页新增“启用本次翻译任务用量上限”。用户以源字符数设置本次任务规模，程序同时维护内部 Token 保护线。

请求发出前，程序会先预留本次请求可能消耗的字符和 Token；请求返回后，如果供应商提供 usage 数据，再用真实输入、输出及推理 Token 修正账本。达到上限后不再创建新请求，但已完成并验证的翻译会保留。

账本保存在本地翻译包的：

```text
Cache/TranslationUsageRun.v1.json
```

相同任务类型、目标语言和 Mod 集合再次运行时，可以读取未完成账本继续处理。无法确认是否已被供应商计费的断线请求会记录为“状态不明确”，不会由程序静默重发。

默认设置：

- 启用用量上限；
- 任务上限为 900,000 个源字符；
- 内部保护线约为 500,000 Token。

### 2. 多供应商结构化输出

每个 API 配置新增“结构化输出”选项：

- 自动（推荐）；
- 仅提示词约束；
- JSON 对象；
- 严格 JSON Schema。

自动模式会按供应商、模型和接口能力选择可用方式：

- Gemini 使用原生响应 Schema；
- 支持严格结构化输出的 OpenAI/OpenRouter 模型使用 JSON Schema；
- 只支持普通 JSON 的端点使用 JSON Object；
- 无法确认能力时退回提示词约束。

程序仍会在本地检查数量、稳定 ID、占位符、Grammar 结构和目标语言。结构化输出只负责提高响应格式可靠性，不能替代本地安全验证。

### 3. DeepSeek 独立适配器

已有 DeepSeek 供应商现在使用独立请求函数，不再完全依赖通用 OpenAI 兼容路径。

主要变化：

- 官方默认 Base URL 统一为 `https://api.deepseek.com`；
- 普通结构化请求支持 JSON Object；
- 官方地址在自动或严格模式下可使用 `/beta` Strict Function Calling；
- 强制调用 `submit_translations` 或 `submit_policy_decisions` 返回固定结构；
- 翻译请求显式关闭不必要的 thinking；
- 单独解析 tool call、普通内容、finish reason 和 usage。

自定义代理地址仍然支持，但不会自动继承 DeepSeek 官方 Beta 能力，避免把不兼容网关误判为严格接口。

### 4. 模型任务分级

每个 API 配置新增“任务用量分级”：

| 档位 | 典型用途 | 回退规则 |
| --- | --- | --- |
| 大量翻译（Bulk） | 普通批量翻译、连接测试 | 必须至少配置一个 |
| 中量标准任务（Standard） | Agent 预判等中量分析任务 | 未配置时回退到 Precision、Bulk |
| 小量精细任务（Precision） | 未解决项、手动重试等 | 依次回退到 Standard、Bulk |

Bulk 基础翻译只使用 Bulk 模型，不能用 Standard 或 Precision 反向替代；Standard 分析任务可按 `Standard → Precision → Bulk` 回退，Precision 精细任务可按 `Precision → Standard → Bulk` 回退。因此，只有先配置另一个可用的 Bulk 接口后，当前接口才能被设置为 Standard 或 Precision。

### 5. 已验证翻译结果复用缓存

新增持久化翻译缓存：

```text
Cache/ValidatedTranslationResults.v1.json
```

缓存键包含 packageId、目标语言和规范化原文。翻译结果只有通过本地机械规则验证后才会写入；读取缓存时还会再次验证。这样可以减少同一 Mod 内跨文件、跨批次以及任务恢复后的重复翻译，并提高相同文本的一致性。

设置页提供“清除已验证翻译复用缓存”按钮。清除后只影响复用能力，不会删除已经写入语言 XML 的翻译。

### 6. 可配置的翻译来源优先级

新增“配置翻译来源优先级”窗口。默认顺序为：

1. 用户手动修改；
2. 第三方人工汉化；
3. Mod 原生翻译；
4. 云端翻译；
5. 自动翻译。

用户可以修改全局顺序，也可以为单个 Mod 启用独立顺序。候选译文即使优先级更高，仍必须通过占位符、格式和目标语言等本地规则验证，不能仅凭来源直接写入。

### 7. 云端判断缓存客户端

新增可选的云端判断缓存客户端，用于复用“哪些稳定 Candidate ID 需要翻译”的判定结果。它与现有“云端共享翻译”是两套不同功能：前者缓存判断，后者下载或上传译文。

只有以下身份全部匹配时才会采用云端结果：

- packageId；
- RimWorld 游戏分支；
- Mod 源文件指纹；
- Policy 版本；
- Prompt 版本。

分析结果不会自动上传。用户必须在 Mod 列表中明确确认，普通接口才会提交只增不删的稳定 ID 贡献；不上传原文、译文或自动翻译结果。用户也可对单个 Mod 关闭加速并强制重新分析。每个 Mod 约定只保留最近三个内容版本，每条精确记录只保留当前与上一个管理修订。

此功能默认关闭，且需要服务端实现对应接口。当前测试不能把“客户端代码已存在”等同于“公共服务器已经可用”。

### 8. DLL 硬编码 UI 自动翻译链

开启 DLL 模式后，普通“开始翻译”会在 XML 流程后自动处理所选且程序集已经加载的 Mod，不再要求用户逐个打开 DLL 工作台：

1. 召回优先扫描 DLL 字符串；
2. Mono.Cecil 静态数据流给出三态判断；
3. 可选云端判断缓存以独立 `dll` 域查询静态不确定项；
4. 可选 Agent 预判只处理云端未命中的剩余不确定项；
5. 最终“需要翻译”的文本按 20 条一批调用翻译 API；
6. 复用已有有效译文，原子保存定向清单；
7. 禁用冲突的旧版全局拦截并请求定向热重载。

程序不会改写第三方 DLL。人工覆盖的优先级高于重新扫描、云端和 Agent；程序集哈希、MVID、方法指纹或条目身份不匹配时，旧条目不会继续应用。DLL 云端读取使用程序集身份源指纹和 `hardcoded-ui:` ID；在公共服务部署域感知契约前，DLL 判断贡献上传保持硬禁用。

智能补翻的 Mod 选择窗口顶部提供“全选/取消全选”“仅选未翻译 Mod”和“随机选择”。这些批量选择动作默认排除官方本体与 DLC，但官方内容仍留在列表中，用户需要时可以手动勾选。未启用但仍有可扫描 XML 来源的 Mod 也会显示；它可以手动执行 XML 分析，但列表会明确提示启用并重启游戏后才能分析 DLL。DLL 模式开启后还会显示“一键分析所有已启用 Mod”；它只分析已启用且程序集实际可供扫描的 Mod，不要求逐个选择。

窗口底部始终保留“本地规则试跑”和“开始翻译”，云端判断缓存或 Agent 预判开启后才显示对应的中间按钮。本地试跑、云端同步和 Agent 预判完成后窗口不会关闭；可从试跑按钮旁查看总结果，也可从每个已有结果的 Mod 行直接打开该 Mod 详情。DLL 摘要会显示程序集、方法、召回候选、诊断、三态数量、人工覆盖和分析器版本。若结果为 0 候选，界面会明确说明“当前分析器未识别到候选”，这不代表 DLL 中没有玩家可见文本。主翻译、API 请求或 DLL 批量扫描尚未结束时，这些启动入口会保持不可用，避免两个任务重叠。

### 9. XML/DLL 统一全域编辑器

全域编辑器新增“全部 / XML / DLL”来源树。XML 保留原 Def/Keyed 分类，DLL 按程序集分类，右侧搜索范围跟随当前节点。DLL 节点隐藏 XML 导入、导出等不适用按钮，并使用独立的原子清单保存后端。

新增“一键翻译当前范围”：处理当前来源、分类和搜索条件筛选出的全部结果，跳过已有有效译文，分批翻译且不自动保存。停止后已完成结果仍作为未保存修改保留。

### 10. API 生命周期、诊断和停止

请求状态统一为创建、排队、调度、已发送、等待响应和完成/失败/取消。并发排队及等待 Unity 主线程真正发送均不设置等待超时；只有 `SendWebRequest` 启动后才计算 API 响应超时。该规则同样覆盖普通翻译、连接测试和模型列表获取，连接测试不会再用全局中止误伤其他请求。前一个请求失败也不会连带使后续队列失败，明确未发送的请求会释放用量预留。

日志现在明确区分本地调度异常、响应超时、HTTP、429、余额/配额、返回格式、任务级模型配置、本地任务用量上限和用户取消；失败项附带条目数、源字符数、预计输入 Token、请求阶段、超时和受限响应摘要。结构化返回解析或术语验证失败也会保留这些请求诊断字段。普通、结构化和 DeepSeek 请求共用一个用户错误聚合入口，供应商底层只写完整开发日志；主扫描继续按任务范围聚合，因此同一失败不会先弹简化错误、随后再弹详细错误。

Policy Agent 与术语 Agent 使用和普通翻译相同的 API 故障说明：超时会明确写明请求已发出但未在时限内收到完整响应，并附条目数、源字符数、预计输入 Token、阶段和超时秒数；HTTP 或配额错误会显示对应类别；返回格式无效会显示最多 320 字符的响应摘要，完整响应写入开发日志。相同根因会聚合，不再只显示 `http_0`、`malformed_response` 等开发错误码。

上述分类现在由控制台与错误聚合共用同一套诊断策略。`0828` 历史独立回归曾逐一验证九类请求错误的用户标题互不混淆；当前源码又静态增加了第十类“本地任务用量上限”，尚未经运行验证。超时显示“没有收到响应”及输入规模，HTTP 200 但格式错误则显示实际返回摘要与解析阶段。

普通译文、Agent 预判和术语 Agent 遇到明确的超并发 429 时，都会降低有效并发并最多进行三次递增等待；仍失败时直接提示服务商并发/频率上限，同一供应商与模型的重复提示会合并。恢复探测锁及 3/8/20 秒等待可被停止或“跳过当前 Mod”立即取消；首次成功后有效并发按 1、约二分之一、约四分之三、配置上限逐段恢复，避免冷却结束瞬间重新冲到峰值。停止按钮由主流程、旧 UI 本地队列、排队、活动请求和重试等待共同决定，停止操作会清理全部这些状态。

停止现在具有明确的三阶段状态：收到停止请求后，界面先显示“正在排空请求”及排队、活动、重试计数，同时禁用重复停止和跳过；只有计数稳定归零后主流程才切回空闲，并记录“翻译已完全停止”。全域编辑器、DLL 工作台或后台 UI 单独发起请求时，也有独立且带代次保护的排空完成记录，不再依赖主扫描正在运行。这避免后台仍有请求时界面已经恢复“开始翻译”的假停止状态，也避免旧停止监视误伤下一项任务。单条翻译、当前范围翻译、未解决项重试、连接测试以及各扫描入口也会避让已有活动请求，不再通过重置取消状态强行插入另一个任务；启动时自动更新翻译会等待已有任务结束后再复核并启动。

### 11. 响应式主控制台

主控制台顶部按钮压缩为两行，当前任务、本次翻译和累计翻译合并显示；未解决项与过滤统计也共用一行，为生产日志和异常报告释放更多高度。ATC 设置窗口会按 RimWorld 的逻辑屏幕尺寸在 `900×700`～`1180×900` 之间动态放大并保留安全边距。正常尺寸下，全域编辑器不再显示最外层滚动条；空间不足或高 UI 缩放时才启用兼容滚动。最低完整布局基准为 1366×768、100% UI 缩放。

### 12. 可选的智能术语一致性

设置页新增独立的智能术语一致性开关，Beta 默认关闭。开启后还必须明确选择参与分析的 Mod；未选择的 Mod 不贡献语料、不调用术语 Agent，也不会增加此功能的 Token 消耗。系列 Mod 可以填写相同共享组，同组交叉验证、不同组隔离。

逐 Mod 选择现在由语料观察、候选抽取和术语 Agent 共用同一个边界。50 个 Mod 仅选择 9 个的机械回归确认：关闭总开关时没有 Mod 进入术语流程；开启后只有这 9 个 Mod 能出现在候选及 Agent 输入的来源记录中。

程序会从通过 Policy 的待翻译文本提取高频词、TitleCase 词组、Def 上下文和重复 N-gram；已有用户手工、第三方人工或 Mod 原生译文可按相同 Key 构造句对。只有可信锚点唯一、两个独立句对给出相同映射且无冲突时，机械结果才成为任务级临时术语。`Empire` 与 `Imperial` 等派生词不会只靠词干规则强行合并。

高价值但仍不明确的候选可以调用共享 Standard 模型池中的术语 Agent。每个源指纹任务最多调用两次、每次最多 12 个候选。普通翻译批次最多注入 20 条且不超过 2000 字符的相关术语；响应必须通过 `termApplications` 回执、目标词实际出现、占位符、授权目标词和冲突校验。

Agent 和机械结果最多先进入任务级状态。设置窗口中的“审核术语”可以检查冲突、修改目标词和语义角色，再明确批准到单个 Mod、共享组或全局；也可以拒绝。机械重扫不会静默覆盖人工批准。

## 三、已有功能的行为变动

### 1. 自动重试策略收紧

Agent 预判每个请求的自动重试次数改为 0。翻译格式或机械验证失败后，不再自动拆成更小批次或逐条再次请求，也不会为了修复英文残留、Grammar 右侧等问题再次产生付费调用。

失败项会保留并进入未解决工作流，由用户明确选择手动修改或重新送交 AI。

### 2. Agent 预判输出更加严格

Agent 预判没有独立 API 配置，而是从共享三级模型池选择 Standard，随后回退到 Precision、Bulk。它与普通翻译共用供应商结构化输出能力，并使用稳定 group ID 限制响应范围。返回结果必须覆盖预期 ID，不能增加未知 ID；最终放行仍由本地 HardDeny 和结构规则决定。

### 3. 翻译流程优先复用高质量现有来源

扫描时会结合来源元数据与用户设置的优先级，优先采用通过规则验证的人工、Mod 原生或云端译文，再对真正缺失的内容调用 AI。普通一键翻译不会重新审计或重写已有有效人工翻译。

### 4. 云端下载来源登记范围修正

过去云端 ZIP 下载完成后，可能把整个目标语言目录中的 XML 都登记为“云端来源”，从而误伤本地或其他 Mod 的翻译。现在只登记本次 ZIP 实际解压且位于目标语言目录内的 XML 文件，降低来源污染风险。

### 5. 全局 UI 拦截与定向硬编码 UI 原型互斥

开启全局 UI 拦截时会关闭定向硬编码 UI 原型；反过来开启定向原型时也会关闭全局拦截。旧配置若意外同时开启，加载时优先保留全局拦截。

全局 UI 拦截采用短周期后台队列：翻译线程约每 2 秒检查一次，只要队列中已有文本且 API 配置可用，就会立即取出最多 20 条组成一批；不足 20 条也会发送，不会为了凑满一批无限等待。这里的 20 是单批上限，不是启动翻译的最低条数。

这项改动减少重复 Harmony 处理和同一文本被两套机制同时改写的风险，但不代表 MOG 控制台兼容问题已经完成运行时验收。MOG 仍需在实际游戏中分别测试：

- 两种机制都关闭；
- 仅开启全局 UI 拦截；
- 仅开启已批准的定向原型。

## 四、简要使用说明

### 1. 启用本地测试版

本机开发副本位于：

```text
E:\Program Files\RimWorld\Mods\AI_TranslationCore_Dev
```

在 RimWorld 模组列表中：

1. 关闭正式版 `Auto.AITranslation.Core`；
2. 启用 `AI 智能漢化網絡 V4 DEV`；
3. 重启游戏；
4. 进入主菜单或存档后，打开底部“AI 翻译”按钮或 Mod 设置页。

不要同时启用正式版与 DEV 版，否则无法可靠判断实际加载的是哪套程序集和设置。

### 2. 配置翻译 API

1. 添加或选择供应商；
2. 填写 API Key、模型和需要时的自定义 Base URL；
3. 将“结构化输出”保留为“自动（推荐）”；
4. 至少保留一个“大量翻译（Bulk）”配置；
5. 使用“测试连接”确认端点可用。

只有确知代理或模型能力时，才手动强制 JSON Object 或 JSON Schema。手动选择不受支持的格式不会自动降级重试，以免一次任务产生多次费用。

### 3. 设置任务预算

1. 开启“本次翻译任务用量上限”；
2. 用滑块设置本次最多处理的源字符；
3. 正常执行“翻译全部”或指定 Mod 翻译；
4. 达到上限后，查看日志确认任务已暂停；
5. 如需继续，提高字符上限后对相同目标语言和同一组 Mod 再次执行任务。

请保留 `!Translation_AI_Pack` 目录；任务账本、已验证缓存和已完成翻译都保存在其中。该生成包不需要在 Mod 列表中手动启用。

### 4. 设置翻译来源

在设置页点击“配置翻译来源优先级”：

1. 调整左侧全局顺序；
2. 如某个 Mod 有特殊要求，在右侧选择该 Mod；
3. 开启“为这个 Mod 使用单独顺序”；
4. 调整顺序并保存关闭。

不确定时使用默认顺序即可。

### 5. 处理失败项

翻译结束后打开“未解决翻译”列表。对于格式错误、英文残留、网络状态不明确或规则拒绝的项目，可选择：

- 手动修改；
- 保留原文；
- 明确执行 AI 重试。

本版不会在后台替用户自动追加付费重试。

### 6. 启用智能补翻与 DLL 翻译

1. 在“详细系统与 API 设置”开启 DLL 硬编码 UI 扫描；
2. 按需开启云端判断缓存和 Agent 预判；
3. 返回终端控制台点击“智能补翻”；
4. 用“仅选未翻译 Mod”快速选择尚无翻译的非官方 Mod，或者手动勾选目标；
5. 可先执行“本地规则试跑”；如果需要，再分别执行“同步云端判断”或“Agent 预判”；
6. 用试跑按钮旁的结果入口查看整体结果，或在 Mod 行右侧查看单个 Mod 的 XML 诊断和 DLL 摘要；
7. 点击“开始翻译”，程序会自动执行当前开关要求的判断阶段并处理 XML，DLL 模式开启时再处理已启用且程序集已加载的 DLL；
8. 在“全域编辑”中用“全部 / XML / DLL”来源树检查、批量翻译或人工纠错；修改完成后按对应来源保存。

本地规则试跑不会调用 Agent，也不会写入译文。“同步云端判断”和“Agent 预判”是可选的预览、诊断入口，不是开始翻译前必须依次点击的步骤。Agent 预判只处理本地不确定且未被云端精确命中的条目；真正生成译文仍使用普通翻译模型。

### 7. 启用智能术语一致性

1. 在详细设置中开启“智能术语一致性分析”；
2. 点击配置按钮，只勾选确实需要统一术语的 Mod；
3. 同一系列 Mod 填写完全相同的共享组名称；
4. 正常执行翻译，程序会建立任务级候选并按需调用术语 Agent；
5. 返回设置窗口点击“审核术语”，检查冲突和目标词；
6. 选择作用域后批准，或拒绝不可靠候选。

此功能会增加预扫描时间和 Token 消耗，也不能保证术语及最终译文一定正确。不确定时保持默认关闭；不要把第一次 Agent 结论直接批准为全局术语。
