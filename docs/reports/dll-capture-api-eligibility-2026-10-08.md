## DLL 采集

只读检查本机隔离测试包的 `HardcodedUiRuntimeObservations.v1.json`：769 条历史记录全部归属 `brrainz.harmony`，示例位置为 `MonoMod.Utils.DynamicMethodDefinition` 中的本项目 `Patch_Widgets_Label_String.Prefix_Patch1`，方法 MetadataToken 为 0。该文件是已有运行证据，不是本轮复现；不能据此断言群友环境完全相同。

源码此前使用 `StackFrame.GetMethod()` 找到首个位于 Mod 根目录的调用帧。Harmony 动态包装可能显示为 `0Harmony.dll`，从而把实际界面文字记录在包装层；DLL 扫描产生的是原始方法中的字符串候选，双方无法按方法与原文键匹配。

修复为通过 `Harmony.GetOriginalMethodFromStackframe` 还原原始方法，再跳过本项目程序集，并拒绝没有有效 MethodDef token 的动态包装帧，继续向外寻找真实来源。已从项目引用的 Harmony 2.4.2 文件中静态确认该 API 名称存在；语义依据 [Harmony 官方源码](https://github.com/pardeike/Harmony/blob/master/Harmony/Public/Harmony.cs)。

另一处明确缺口：独立 UI 采集依赖全局翻译取消标志，停止翻译后该标志保留，重新开启采集仍可能完全不记录。采集现在仅由自身开关、时限及既有文本过滤控制，不清除或改变翻译任务的取消状态。移除结束采集时的重复 Flush 调用。

分析阶段使用同一份采集键快照匹配候选，报告未匹配和重复匹配数量。未匹配文字仍不能直接产生安全可注入的条目；运行时拼接、调用位置差异、旧 DLL 版本或动态包装记录均需区分。重复位置继续待判定，不按原文把多个位置全部强制翻译；已有人工/AI分类优先级不变。

历史错误记录没有足够信息反推真实 Mod，不自动改写或删除。使用修复后的代码重新采集并执行 DLL 分析，才能产生真实来源证据；当前不能声称游戏内已修复或旧数据已自动恢复。

## API 连接成功但正式翻译无可用配置

当前连接测试与真实翻译均调用 `InvokeWorkflowJsonAsync`。连接测试指定当前卡片，正式任务从设置列表选取；精细→标准→批量的档位回退已存在，没有发现仍然只认批量档的旧链路。

本轮将资格判定集中为一处：配置存在、启用、支持工作流 JSON、密钥与模型经过实际请求使用的 CleanInput 处理后非空。原检查只看原始字符串是否为空，会把全空白等请求时变成空值的配置误认为有效。连接测试和轮询候选均复用同一判定；有效配置的档位顺序与轮询算法不变。

无配置可用时按 API 卡片序号输出具体原因：未添加、未启用、密钥为空、模型为空、DeepL 不支持此协议。错误不包含密钥、URL、用户备注或请求正文。仍不允许空密钥配置，未新增厂商、工具调用、跨档位故障切换或其他协议改造。

这些修复不能证明历史群反馈的根因。若同一配置测试成功后仍报无可用配置，需结合新错误中的卡片序号和配置状态检查；不能以连接测试成功推断设置列表此后未变化。
