# 批量模型请求异常与响应完整性修复

日期：2026-10-07。状态：源代码已修改，仅静态审阅；未编译、未调用真实 API、未运行项目或游戏。

## 已修复的代码缺陷

1. Unity 请求协程只有 `SendWebRequest` 调用局部捕获异常。创建请求、设置上传/下载处理器和请求头、读取响应或诊断信息时的异常可能结束协程，却不完成 `SendStarted` 和 `Completion`，导致调用方继续等待。新增协程执行包装，在每次推进迭代器时捕获异常，统一完成失败响应并清理活动请求；`StartCoroutine` 启动异常和无协程返回也采用此路径。发送前失败标记为 LocalDispatch，发送后失败标记为 Transport。异常信息只保留类型，避免原生异常消息带出请求 URL 中的凭据。网络启动信号紧跟发送成功设置，不依赖诊断采集成功。
2. Google 的非 thought 文本片段和 OpenAI 兼容格式的内容数组之前只保留最后一个非空文本片段。改为按顺序直接拼接，保留片段边界处空白；仍只读取第一候选/第一 choice，不合并不同答案。原有结束原因、JSON 解析和条目完整性校验继续生效。
3. 顺序提交多个已经完成的批次时，提交循环内部没有取消检查。补充每批提交前的取消检查；当前短写入完成到安全边界后，下一批不再提交。仍排空在途请求并保留全局互斥，不提前释放任务租约。

## 保留的产品规则与未解决范围

- 发送前排队和主线程调度等待不计入响应超时，不增加固定秒数的发送前看门狗。
- 输出触顶仍按当前批次失败处理，不自动提额、拆批或重试。
- 校验拒绝条目仍按已确认规则逐条补试一次，不改变重试范围。
- 上述问题是当前源码中可指出的缺陷，不证明它们就是群反馈中卡住、大批失败或游戏退出的根因。实际反馈尚未闭环。

## 第二轮复审：代码实现

复审发现首轮修补没有把通知顺序、资源所有权和用量统计一起检查完整，因此首轮记录不应理解为问题已经彻底解决。本轮继续只做静态阅读和差异审阅。

| 检查点 | 首轮遗漏与本轮处理 |
|---|---|
| 协程异常 | 保留逐次推进迭代器的异常捕获；移除内部重复的局部捕获，发送后诊断失败不再被错误归为发送前失败；异常结束也进入统一收尾。 |
| 请求资源 | `FinishRequest` 统一中止并释放请求，清空资源引用；协程自身结束时不调用 `StopCoroutine` 停止自己。外部取消不再依赖 Unity 是否替停止的迭代器执行释放逻辑。 |
| 完成通知顺序 | 原先先发出“未发送”信号、后填充失败结果，等待线程可能抢先取到通用错误。改为清理后先发布真实响应，再补发发送状态。主线程调度的失败分支也先准备结果再通知。 |
| 取消与发送竞争 | 增加原子调度状态：仍在排队的回调可以取消；已取得发送执行权的回调必须发出收尾确认，调用方再释放名额和用量预留，避免请求 ID 尚未交回时取消提前结束。 |
| 用量统计 | 网络可能在 `StartCoroutine` 返回前已发出并失败。最终结算再次读取真实发送信号，不把该情况当作“未发送”释放预留；发送但无可靠用量的失败继续使用原有不确定用量记账。 |
| 正文片段 | Google 保留非 thought 的字符串片段；OpenAI 兼容数组支持 text/output_text 和无类型的历史文本对象，排除已识别的思考片段，其他类型或非字符串文本报协议错误；仍只读第一候选/第一 choice。 |
| 语言层面 | 人工核对了迭代器 yield 的 try/finally 边界、方法参数与调用处、异步 finally、捕获变量的原子操作及项目 .NET Framework 4.8 目标；未执行编译，不能据此声明编译成功。 |

这里的“正文片段”不指 stream。当前新版请求没有开启流式，HTTP 层拿到完整响应后才解析；一次完整 JSON 返回仍可能在 content/parts 数组中包含多段正文。本轮只修正数组读取，不新增流式能力。

## 第二轮复审：业务逻辑与时序推演

| 场景 | 静态判断 |
|---|---|
| 创建请求或设置请求头失败 | 形成 LocalDispatch 失败响应，完成等待信号并释放本次请求；不会因缺少发送信号永久等待。 |
| 已发出后读取响应/诊断异常 | 形成 Transport 失败，按已发送记账；失败不写入译文。 |
| 请求发送后立即结束 | 不依赖是否进入常规响应等待循环，仍根据发送信号结算用量。 |
| 排队期间停止 | 阻止尚未取得执行权的回调发请求；已取得执行权的回调清理后再确认结束。 |
| 请求进行中停止 | 取消传给在途请求，等待中止清理；批次调度器仍等待在途任务收尾，租约不提前释放。 |
| 批次提交前停止 | 新的取消检查阻止该批进入提交；不会把尚未写入的模型结果计为已保存译文。 |
| 当前批次写入过程中停止 | 当前短写入完成到安全边界；成功结果进入已完成条目集合，后续批次停止提交。 |
| 已保存部分译文后停止 | 页面取消恢复只处理未进入终态集合的条目；已有文件与数据库成功记录保留，已有刷新范围交给取消后的刷新路径。 |
| 单批模型或协议失败 | 原有逐批失败记录继续处理其余批次；不将业务失败变成整任务取消。 |
| 同一正文被分成多个文本片段 | 按原顺序拼接，保留边界空白；不拼接不同候选答案或思考内容。 |
| 拼接后仍有缺项、重复序号或输出触顶 | 继续执行现有结束原因、JSON 和条目完整性校验；不能因为拼接而接受不完整译文。 |
| 已有译文保护 | 本轮未改变候选选取、已有译文优先级、重试范围或输出上限规则。 |
