# Modern Dev Tools 试跑估算与实际消耗独立复审

日期：2026-10-09。只读源码、现有日志、用量账本与 SQLite；未编译、运行项目、测试或调用模型。实现解释属于静态判断。供应商 66 requests、412,341 tokens、1.99 元采用主人提供的后台截图记录，没有重新访问供应商后台。

## 结论

试跑基础估算 299,877 tokens，含 20% 余量预算 359,853 tokens；后台显示 412,341 tokens，超预算 52,488（14.586%），比基础估算多 112,464（37.503%）。本次余量不足，但不能把全部差额归为补试、候选数变化、Pro 路由或思考 token。

最明确的低估集中在输入侧：翻译首轮实际输入 172,016，比试跑输入 121,149 多 50,867（41.987%）；首轮实际输出 15,336，反而比预计 25,667 少 10,331。粗估算法与真实分词不同是可信贡献因素，但候选集合、文本长度和分批也发生变化，缺少逐请求原始提示词与对应 tokenizer 计数，不能把这 50,867 全部归因于算法。

## 候选、失败与补试

- 数据库当前 AI 复核位图显示：548 条中需要翻译 293、无需翻译 255；293/548=53.467%。试跑假设需要翻译 274（50%），少估 19 条。因此 463+274=737，而实际 463+293=756，仅增加 2.578%。候选条数增长不能按比例完整解释 37.503% token 差额；实际选中的条目长度与试跑选中集合也可能不同。
- 实际 756 条首轮处理：最终 707 成功、49 失败。首轮校验拒绝 20 条，逐页补试计划为 13+3+4，补试救回 5 条、仍失败 15 条；另有 34 条编号异常整批失败。因此首轮保存 702，702+5=707；34+15=49。
- 补试占 20/66 请求，但仅占总 token 4.207%（17,347/412,341）；不能把“请求数多很多”等同于“主要 token 都花在重试”。补试重复发送提示词的输入 16,889 明显大于输出 458。
- 第 25 批编号异常也已实际消耗 token；应用拒收响应不等于供应商未计费。现有账本可计入首轮总量，但没有该批原始响应，无法解释编号为何异常。

## 静态实现判断

1. **输入不是供应商 tokenizer 计数。** `Workflow/AI/ModelInvocation.cs:124` 的 fallback 算法将 CJK 字符按 3 字/token、英文按词及驼峰分段、其他字符按 4 字/token 粗估。`LanguageModelGateway` 在 simulation 分支统计每个完整业务 prompt，因此模板、语境与参考字典按批重复的内容已经进入基础估算，不能说“试跑完全漏了重复提示词”。实际 HTTP 层还增加 system 消息与消息协议开销，试跑只统计 request.Prompt；这一部分未直接建模。
2. **输出是启发式预测。** `AiWorkflowServices.cs:1134` 复核按每条 48 加 JSON 外壳估算；翻译约为原文粗估 token 加每条 24 和 JSON 外壳（约 1832 行）。翻译首轮输出实际小于预测，说明本次不能笼统称为输出漏估。
3. **试跑没有真实模型失败，无法出现实际补试。** 模拟返回空内容、simulation 结束原因并直接记预测 usage；真实返回后才有解析与校验拒绝、单条补试。20% 为预算余量，不是已经按此次 20 次补试逐项计算，也不保证覆盖所有误差。
4. **工作流路由固定精确档。** `AI/AutoTranslatorAPI.Workflow.cs:308` 的 GetNextWorkflowConfig 固定调用 `SelectEligible(..., Precision)`；`AutoTranslatorApiModelTransport` 未使用 request.ModelRoute 区分复核/翻译。日志确认此次两阶段均为 deepseek-v4-pro。因此若配置意图是复核走 Flash，这条工作流没有实现该意图。Pro 会影响价格，也可能改变响应和分词，但不能仅凭档位说明全部 token 偏差或计算应省多少钱。
5. **没有“这次翻译漏算思考 token”的证据。** 43 条翻译账本的 ActualReasoningTokens 都是 0，而且每条供应商 total=input+output；源码 DeepSeek 请求明确 thinking.type=disabled。账本的 reasoning=0 也可能来自供应商没有单列该字段，不能单独当作供应商绝无内部思考的证明；但现有证据不支持把超支归因于额外未计入 total 的思考量。复核原始账本不在，不能独立确认其分项。工作流 UI 的 ModelTokenUsage 只有 input/output，跨供应商确有展示边界；用量账本则会读取 total_tokens 与 reasoning 字段，应区分这两层。
6. **用量账本保留范围有限。** `Core/TranslationUsageCoordinator.cs:77` 固定写 Cache/TranslationUsageRun.v1.json；新阶段会用新 runKey 覆盖，当前 .bak 也是翻译倒数一次写入，只缺最后一次响应的实际值。因此此次无法再从这两份文件直接恢复复核 23 次的供应商 usage。宜保留已完成任务的独立账本与分阶段汇总，才能日后直接归因，而不是依赖后台日汇总相减；本报告未修改实现。

### 输入低估的具体机制与归因边界

- 当前 fallback 并非目标模型的 tokenizer：普通英文单词按一个片段计数，缩写/驼峰按规则拆分，标点按四字符一份，长标识按长度除四。真实模型对 JSON 符号、技术标识、路径、大小写与英文子词的切分未必与这些规则一致；复核 prompt 中 locator、context、currentAnalysis、historicalAi 等结构化字段很多，这些规则容易出现与供应商统计不一致的累计偏差。
- CJK 按三个字符一个 token 也没有按模型、语言适配。不过本次主要原文是英文，不能把所有输入差额都解释成“中文三字一 token 低估”。
- 每批完整业务 prompt 已经进入试跑输入，重复规则、字段和参考字典并非整体漏算。实际 HTTP 请求额外添加固定 system 消息及消息封装，试跑没有在供应商请求层计数；该遗漏应修正，但目前不能声称它足以解释十余万 token。
- 试跑选中的274条待判定候选与实际判定需翻译293条不是同一集合。增加19条仅解释条数，文本长度、语境体积和分批边界影响还未单独量化。首次翻译真实输入比试跑多50,867这一点已由直接账本确认，不依赖新截图；其内部原因仍无法精确拆账。
- fallback 还用于 SplitReviewBatches / SplitTranslationBatches 的 maxPromptTokens 判断。因此改进计数器可能改变分批数量、提示词重复次数与请求行为；实施时必须明确区分“只修报告估计”和“同步改变真实分批策略”，不要把行为变化藏在估算修正中。

### 输出高估的具体机制与归因边界

- 复核输出直接使用每条固定48加JSON外壳，未依据模型实际的简短理由长度、分类字符串和编号来预测。548×48=26,304，几乎占了全部26,373预测输出；这条常数缺乏模型/任务分层。小时窗口剩余输出12,607提示这部分可能明显偏保守，但由于复核账本缺失，不能把12,607当作直接实测复核输出。
- 翻译输出使用源文 token 粗估再加每条24及外壳。737×24=17,688，仅固定每条附加量已经超过首轮实际全部输出15,336；两边候选数不同，且这个附加量包含什么没有严格的分词依据，因此只能说明预测结构非常粗，不能直接说17,688全是实际不需要的JSON开销。
- 源语 token 数无法等同目标语 token 数；短标签、普通长句、代码/占位符混合内容的翻译长度不同。当前公式也没有按目标语言或模型学习实际长度分布。预测输出与实际输出的偏差不能用统一的输入纠偏系数一起放大，否则会进一步高估输出。

### 可行改进方向（建议，尚未实施）

1. **输入先建立同口径计数。** 对已知模型使用可核验版本的本地 tokenizer，计数完整发送的 system/user 文本及该提供方的消息开销；没有可靠 tokenizer 时保留明确标识的 fallback，不称为精确统计。不为获得预测而额外调用收费模型。缓存 token 数仍全入输入，价格另按命中/未命中拆算。
2. **输出按任务拆解。** 复核预测可拆成 JSON/编号/分类结构与理由长度分布；翻译拆成目标文本长度、保护标记与JSON结构。用多个既有或未来主人手动任务的 usage，按提供方/模型、阶段、目标语言、短标签/长句/技术混合文本等足够有数据的维度校准，并报告区间。不要用本次的0.55或1.55之类倍率硬套所有任务；具体选哪些维度要看数据量，避免稀疏样本过拟合。
3. **保留逐请求和逐阶段账本。** 记录用途、模型、条数、源字符数、提示词估计值、真实input/output/total、重试关联与估算器版本；完成任务后归档，避免下一阶段覆盖。无需为统计保存密钥，也不必持久化完整提示词。既有日志可被动分析，无需自动运行项目或模型。
4. **基础估计、补试预留、预算余量分开呈现。** 正常首次请求作基础，重试用历史失败概率与按条提示词大小给出单独范围，最后应用主人确认的30%余量。余量不能掩盖系统性输入低估；输出上限、输出预测与预算也不能混为同一数字。
5. **分类未定时展示情景范围。** 对待判定池保留50%默认情景，并显示其假设；可增加低/中/高入选比例与文本量范围，而不是承诺固定50%是真实结果。完成真实复核后若主人查看预算，可基于当前确定候选重新生成静态估计，使后续翻译预算不再依赖旧分类假设。
