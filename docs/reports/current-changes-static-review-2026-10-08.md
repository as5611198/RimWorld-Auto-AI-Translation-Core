## 发现

### 1. 初审判断已撤回：原生译文分析失败，一键翻译仍继续 AI 阶段

- 位置：`Workflow/WorkflowBackend.cs:817-847`，`Workflow/Analysis/NativeTranslationCatalog.cs:160-170`（以下源码路径均相对于 `src/RimWorld-Auto-AI-Translation_Core/`）。
- 触发：原生译文扫描抛错，而数据库中已有上次分析留下的可翻译候选。
- 实现：一键流程只收集本地分析异常，仍用原来的完整 Mod 列表执行 AI 复核和 AI 翻译。
- 影响：当前语种原生译文是否存在尚未确认，旧候选仍可被送去机翻；与“原生译文读取失败停止本次分析，不能当作缺译继续翻译”的设计冲突。没有旧候选时不一定实际发出翻译请求。
- 修复方向：把原生译文收集成功作为后续翻译的前提，失败时阻断依赖它的阶段；不要只在最后汇总异常。

### 2. P1：上传预览的手工改译会被数据库热重载覆盖

- 位置：`UI/Windows/UploadPreview/Window_UploadPreview.Persistence.cs:118-151`；`UI/Cloud/AutoTranslatorMod.CloudRenderers.cs:728-740`；`Workflow/WorkflowBackend.cs:298-369`。
- 触发：预览打开实际生成的语言目录，用户改译并保存，随后点击新版热重载；该条目已有数据库托管输出记录。
- 实现：预览保存 XML 和人工来源旁注，没有同步数据库。热重载直接从数据库重建托管文件，使用旧译文和旧来源。
- 影响：已保存的人工修订被旧机翻覆盖，来源也可能重新变成 AI。
- 修复方向：预览改译接入统一人工保存链，确保数据库、输出文件和来源共同更新，再允许重建。仅操作独立上传工作目录时不等同于这一触发场景。

### 3. P1：识别到原生译文后，旧机翻文件仍可能继续生效

- 位置：`Workflow/Analysis/WorkflowAnalyzers.cs:1431-1434`；`Workflow/Persistence/WorkflowRepository.cs:1894-1895`；`Workflow/WorkflowBackend.cs:876-895`。
- 关联：`Workflow/Synchronization/TranslationFileSynchronizer.cs:478-486`；`Scanning/AutoTranslatorScanner.MemoryInjection.cs:505-550`。
- 触发：该语种以前完成过同步，已有 AI 输出文件；之后作者补充翻译或启用翻译包，再运行分析/一键翻译。
- 实现：分析将数据库译文升级为原生来源，并标记托管文件 `SourceChanged`，但不写文件；一键翻译仅在该语种从未同步过时自动同步。有效原生译文又会被排除出 AI 待翻译项。
- 影响：数据库显示已采用原生译文，磁盘仍留着旧机翻；读取生成 XML 的内存注入仍可能使用旧文本。手动同步或显式从数据库重建可以另行纠正，不代表常规分析链已完成这一步。
- 修复方向：把本轮来源变化对应的托管文件同步和运行时更新接入分析后的流程，不能仅依赖首次翻译同步。

### 4. P2：切换目标语种后，XML 分类可能复用错误结果

- 位置：`Workflow/Analysis/WorkflowAnalyzers.cs:77-91,237-245,901-923`；`Core/AutoTranslatorMod.cs:357-390`。
- 实现：XML 分类会按目标语种判断“原文已经是目标语言”；分析指纹只有固定规则字符串和 Mod 文件指纹，没有实际目标语种。语言切换也不使 XML 分类失效。
- 触发示例：只有 Defs 文本的 Mod，中文目标下中文原文被标记无需翻译；切换英语/日语，相关文件集合未变，再分析时命中原指纹。
- 影响：依然沿用无需翻译的分类，漏掉新语种需要翻译的条目。跳过分支刷新已有译文覆盖层并不会重做原文语言分类。
- 修复方向：将实际目标语种纳入影响分类的指纹，切换后重算相应 XML 分类。

### 5. P2：原文更新后，旧译文哈希会挡住新扫描到的原生译文

- 位置：`Workflow/Persistence/WorkflowRepository.cs:2813-2821`；`Workflow/Analysis/WorkflowAnalyzers.cs:1387-1392`。
- 触发：同一 XML 定位条目的原文更新，同时已有当前版本的原生译文；旧翻译记录仍保留上一次原文哈希。
- 实现：更新候选时清空译文和来源，但保留旧 `source_text_hash_at_translation`；随后导入本轮扫描到的原生译文时，发现这个旧哈希不同，直接跳过。
- 影响：已经收集到的新原生译文不能写入该候选，条目继续缺译，可能进入 AI 翻译。后续普通重复分析仍可能遇到同一判断，直到其他同步流程清理旧状态。
- 修复方向：区分“旧译文失效”和“新扫描到的原生译文”；不能拿失效译文的哈希阻止接受当前扫描结果。旧输出文件的清理另行保持一致。

### 6. P2：延迟计算的 Tooltip 文本缺少原 Mod 调用位置

- 位置：`UI/Interception/UIInterceptor.Patches.cs:118-125`；`UI/UIInterceptor.cs:26-65`。
- 触发：游戏在后续绘制 Tooltip 时调用 Mod 提供的 `Func<string>`，而不是 Mod 当场传入字符串。
- 实现：包装器先执行原委托，等其返回后再按当前调用栈识别来源。原委托的 Mod 方法此时已经退栈，包装器也没有保存并传递原委托方法或注册位置。
- 影响：这一类文本虽然已取得，却无法可靠对应 Mod 和 DLL 方法，可能未进入正确候选分类。直接传字符串的 Tooltip 不受此原因影响。
- 修复方向：保留与 DLL 定位规则一致的委托方法/注册来源信息，并在实际显示时提交；不要为了取调用栈而提前执行 Tooltip 委托。
